## 已确认的业务缺陷

### B1 / P1：选择恢复失败后，允许按全选生成清单

位置：`frontend/src/components/agent/AgentChat.vue:447–453`；建单参数位于第 501 行。

复现步骤：

1. 有效预览原先已排除一条记录。
2. 重新打开会话，历史消息接口成功，`/selection` 接口失败。
3. 页面清空本地选择，吞掉恢复异常，释放 `openingHistory`。
4. 点击生成清单，实际发送 `excludedRecords: []`。

当前结果：原先排除的记录可能被加入待确认清单。REST 建单使用本次提交的排除列表，不会补入语义状态里的旧排除项。

期望：区分「确认全选」与「选择尚未恢复」，恢复失败后阻止建单，提供重试或明确重置选择。服务端可进一步使用选择版本防止覆盖。

证据：重新执行既有 `docs/review/production-readiness-ui.probe.cjs`，输出：

```json
{"conversationId":"conv1","previewId":"p1","excludedRecords":[]}
```

这是执行真实 Vue 方法、注入 API 失败的方法级复现，不是浏览器端到端验收。

### B2 / P1：预览过期后重新查询，静默丢弃语义排除项

位置：`backend/src/main/java/com/example/report/semantic/SemanticConversationService.java:130–139`；随后第 171 行使用清空后的排除集合建单。

独立 MySQL/Redis 集成复现：

1. 输入「A公司销售报表的」。
2. 输入「排除SO2026002」，确认服务端已保存一条排除记录。
3. 将该隔离测试预览设为过期，等价于超过预览 TTL。
4. 在请求不携带旧 UI 排除列表的情况下输入「剩下的帮我派单吧」。

当前结果：服务端生成新预览，将 `excludedRecords` 清空，生成的 PENDING 清单重新包含 `SO2026002`。独立断言验证了旧、新预览不同、排除集合变为 0，以及该单据确实进入清单。

触发边界：若客户端仍提交非空的旧预览排除项，第 146 行会拒绝本次建单；但无 UI 列表的对话调用、页面已清空过期卡片选择等路径没有这层保护。不能依赖浏览器长期保存服务端已知的业务意图。

期望：同范围刷新时校验并迁移稳定记录标识；无法安全继承时明确要求重新选择，并阻止本轮建单。范围或数据变化不能默认为用户撤销排除。

证据：`docs/review/CurrentSemanticReadinessProbe.java` 的 `expiredPreviewLosesExclusions`。使用现有隔离集成环境、真实 Planner/预览/清单服务和 测试替身 意图；没有执行确认，清单条目发送次数均为 0。

**B1 与 B2 都会扩大待确认清单，但确认按钮仍存在。本轮没有发现这两项缺陷直接绕过确认自动派单。**

### B3 / P2：纯数字单据号在语义解析前被误脱敏

位置：`backend/src/main/java/com/example/report/web/AgentController.java:58`，以及 `operations/SensitiveData.java` 的证件号正则。

使用合成单据号 `900000000000000001`，调用真实 Controller 并捕获传给聊天服务的文本：

```text
输入：排除单据900000000000000001
进入聊天服务：排除单据[证件号已脱敏]
```

结构化 `docNo` 字段会保留该号码，但自由文本在实体定位之前已丢失号码。接入使用 18 位纯数字单据号的业务后，自然语言无法准确定位并排除这些单据；符合手机号模式的数字单据也有同类风险。默认 SO 前缀示例数据不会触发该问题。

期望：在受信任的本地边界识别业务实体，再用可逆占位映射传给模型，或明确转为表格选择。保留日志与模型数据脱敏要求，不能通过取消全部脱敏解决。

证据：独立探针 `controllerRewritesNumericDocument`，真实 Controller 和脱敏逻辑、测试替身 下游捕获参数；不涉及真实个人信息或真实模型调用。

## 依赖安全风险

**S1 / P1（有触发条件）：Vite 开发服务器依赖存在高危受影响版本。**

构建实际使用 Vite `5.4.21`；`frontend/vite.config.mjs:17` 为 `host: true`，当前环境为 Windows。`npm audit --json` 返回 5 个受影响包条目：高危 1、中危 1、低危 3；这不是 5 个互相独立的漏洞。

其中高危公告为 [Windows 路径变体绕过 server.fs.deny](https://github.com/advisories/GHSA-fx2h-pf6j-xcff)。当前依赖及监听设置满足部分触发条件；本轮没有利用漏洞读取文件，也不声称已发生泄露。生产 Docker 前端运行 Nginx 静态产物，这项结论针对开发服务，不能直接等同于生产 Nginx 漏洞。

建议默认只监听回环地址，选择兼容 Vue 插件且已修复公告的版本升级并回归。不要直接使用 `npm audit fix --force`，当前审计建议包含跨大版本变更及不合适的降级候选。

## 正式上线门槛

这些是已知接入或验收缺口，与新增 Bug 分开计算：

1. **真实身份与组织权限。** `PermissionService.java:40` 按客户端 `X-User-Id` 查询硬编码身份；访问者可以提供 `admin`。Basic Auth 限制站点入口，但无法实现真实用户、租户和组织授权。需要可信登录态、权限撤销和跨租户验收。
2. **外部业务接入。** 本报告当时未验收外部业务系统。当前真实模型与独立 MCP 服务已实现，本地业务表的事务派单不等于外部 ERP 接入完成；外部幂等、超时未知结果、对账和重试契约仍须独立验证。
3. **普通报表的服务端分页。** `ReportService.java:34/42/50` 仍使用无上限的 `selectList`。Agent 预览分页不覆盖这些入口；业务记录增长会增大数据库、应用内存、网络和浏览器负载。本轮未压测，不能给出可承载数据量。
4. **真实模型验收。** V2 已移除 DOMAIN 解析优先路径，固定 测试替身 回放通过不代表真实模型准确率。需要按业务语料统计最终范围、误扩大范围率、澄清率、延迟和多轮状态；本轮真实模型测试跳过。
5. **目标环境可靠性。** 需定义数据规模、并发、P95/P99、错误率和恢复目标，再验证多实例、依赖中断、长时间负载、租约失效及在途任务升级。
6. **运维基线。** Compose 后端使用数据库 root，Nginx 模板仅监听 HTTP 80；正式环境需要 TLS、最小权限、密钥管理、监控告警和备份恢复演练。外部设施可能已提供部分能力，但仓库与本轮测试不能证明。
7. **接口及维护。** 普通异常仍返回 HTTP 200 加业务码，包括内部错误；生产监控必须识别业务码或统一 HTTP 语义。Vue 2/Element UI、镜像及后端依赖需持续升级和安全扫描。
