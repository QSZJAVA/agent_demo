## 持久派单任务的边界

- `POST /api/dispatch/jobs` 接受 CONFIRM、RETRY_FAILED、RECONCILE、DIRECT、OP_RETRY_FAILED、OP_RECONCILE，必须提供稳定的 `Idempotency-Key`。同号同负载返回原任务，同号不同负载拒绝；同清单只能有一份在途任务，新键不能悄悄替代旧任务。
- 接受时校验归属和当前数据权限，冻结清单执行版本；工作线程重新读取操作者及当前状态。确认与重试继续使用原清单事务/CAS，异步重试通过原版本条件认领，旧任务不能使用后来执行轮次。
- QUEUED 最多等待 10 分钟。数据库串行准入限制每租户 100、每用户 8 个在途任务；每实例最多 4 个工作线程。跨实例用 `FOR UPDATE SKIP LOCKED` 认领，RUNNING 的 5 分钟租约每 30 秒续租。
- 超时排队不启动。失去执行租约的 RUNNING 任务记 FAILED，不自动重新入队。清单仍按实际持久状态决定等待、核对或显式失败重试，任务失败不能当作全部业务记录未派单。
- 前端在 POST 前保存任务键，收到任务号后保存恢复线索；丢失 POST 响应时沿用原键，丢失轮询连接时只 GET 原任务。刷新执行卡片只读取已有任务。页面最多连续等待 5 分钟，此后用户可刷新执行结果，后台任务不因页面等待结束而重新创建。
- 运营工作台包含执行中的清单；操作失败或页面等待结束后重新读取实际持久状态，管理员仍可查看逐条结果，不能通过重复重试绕过在途任务。
- 任务 SUCCEEDED 表示所请求操作已完成，逐项派单成功/失败以真实结果为准。结果按照运营 resultDays 策略清理，任务幂等身份继续保留。任务耗时与结果另记 DISPATCH_JOB 指标。

原同步接口仍保留兼容，但新前端的上述动作默认走任务入口。自然语言解析和查询/生成 PENDING 清单的语义协议没有扩展；日期、金额、排序等未支持条件继续澄清。本轮没有把模型解析失败改成其他语义来源。

## 部署与文档

当前 Compose 使用私有 internal 网络放置 MySQL、Redis、业务服务，仅 Agent 同时连接页面/API 网络。内部 MCP 通过显式 allow-insecure-http 配置使用专网 HTTP，并保留服务 Bearer 认证；默认客户端在非回环地址继续要求 HTTPS。正式跨主机接入及公网入口仍需要实际 HTTPS、信任配置和验收。

deploy.sh 新生成的 .env 权限为 600，随机生成基础服务凭据，不打印秘密值；真实模型配置缺失则停止。更新顺序为业务服务 → Agent → 前端，各阶段等待健康，MySQL/Redis 不在更新重建列表中。已有账号不会因修改初始密码环境变量而重置。

README、Docker 部署指南、生成器和新日期流程图同步更新。运行 `node docs/diagrams/build-semantic-flows.cjs` 生成八页 HTML/SVG/Mermaid 和 draw.io；2026-09-29/30 图表保留为历史版本。
