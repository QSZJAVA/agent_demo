# 通用业务助手

当前助手在同一会话中提供报表查询、派单记录查询、工单进度和总结，并保留 V1 派单规划。链路为 `real,mcp`、`agent.semantic.mode=active`，真实模型使用原生 JSON Schema、thinking 关闭；业务事实来自带服务认证的 HTTP MCP。RAG 暂不引入。

页面工具栏、手工派单记录抽屉及运营治理的用法见[工作台操作与运营治理](工作台操作与运营治理.md)。对话查询的派单记录与报表页手工记录入口范围不同。

## 使用方式

| 要做的事 | 示例 | 返回依据 |
| --- | --- | --- |
| 看报表业务数据 | 查询 A 公司的销售报表数据，金额超过五万元 | 授权来源记录，包含已派单和不满足派单规则的记录 |
| 排序与翻页 | 按金额从高到低排，每页两条；下一页 | 相同筛选条件和稳定排序，卡片总数代表全部匹配 |
| 数据总结 | 总结这批销售数据的金额和状态分布 | 服务器精确统计，按已声明币种分别合计 |
| 单条派单资格 | 查一下销售报表服务器的数据；这条数据符合派单条件吗 | 唯一记录的当前状态、生效规则和实际字段值；只读核验，不生成候选或清单 |
| 派单记录 | 查询失败的派单记录，按公司汇总 | 持久清单条目；普通用户仅看本人，管理员仍受公司和报表权限约束 |
| 工单进度 | WO-DEMO-001 到哪个环节了，谁来处理 | 业务接口返回的当前环节、处理人和完整流程 |
| 工单总结 | 总结 A 公司全部工单；只看待审批的 | 全部匹配工单的状态分布、当前审批人和金额 |
| 准备派单 | 查一下我有哪些可以派单 | 原 V1 派单规则、预览、勾选及待确认清单流程 |

来源字段名称、类型和说明来自授权目录，支持有界 AND/OR 条件、空值判断、数值和日期比较、文本包含等。未声明字段、任意 SQL、跨数据域关联计算、催办、审批或修改工单会澄清或拒绝。详情匹配多条时要求明确编号，不能猜测“某一条”。

“报表名 + 字段值 + 的数据”可以省略字段名，由真实模型依据目录字段含义识别产品、费用类别等筛选。能够确定字段时保留该值；存在歧义时澄清，不把未理解的业务值直接丢弃后返回整张报表。无条件草稿还会核对本轮实际读取的字段值：用户明确说出某值的数据或明细，而当前授权结果中已存在该字段值时，将遗漏证据交回模型修正；校验不会自行拼接查询，也不会把当前页没有出现的值伪称为已验证事实。

对单条记录询问是否符合派单条件时，使用上一成功查询的明确记录引用，业务服务重新读取其当前事实。核验同时检查报表是否启用派单、记录是否未派单及当前生效规则，不把“未派单”本身当作符合条件。具体公司规则优先于通配规则，并遵守规则生效时间和版本；结果展示结论、规则说明及实际参与求值的字段。已派单、未命中规则、没有适用规则分别说明原因；规则计算失败明确告知暂时无法判断。多条记录中的含糊指代须澄清，不扩大为全部报表候选。核验不继承可能遮蔽当前状态的旧金额或状态筛选，也不会创建预览、修改勾选或生成清单。

连续追问只引用上次成功查询及已展示行的序号；翻页后序号沿用列表中的实际位置。独立新查询重新确定范围。失败不会把不完整读取当成成功，也不能以含糊追问沿用过时查询。

查询卡片的翻页和工单“查看进度”按钮会发送明确的连续对话请求，经过真实模型规划及业务读取；它们不是浏览器本地切片。只有最新查询卡片可继续翻页，历史卡片保持原查询时点的快照。

当前页已展示的标量字段与编号一同作为追问依据，便于根据产品、费用类型等明确引用记录；未展示的行不进入指代上下文。询问如何确认、能否审批属于功能说明，不能被当作执行请求。独立语义复核核对公司范围、数量及条件组合，程序继续验证授权和稳定身份，防止遗漏公司或把区间上下界错误地取并集。

上一成功查询另提供完整匹配条数、已展示条数及是否已完整展示的标记。第一页确实包含全部匹配记录时，可以据此定位唯一最高或最低记录；总数未知、分页未展示完整或查询失败时不能把当前页当作全集。完整客户名称查找使用精确相等条件，明确要求包含或局部名称搜索时才使用相应运算。

成功查询的零条结果仍有明确范围，继续询问总额、数量或分组时可按原条件返回零值/空分组。零条结果不等于查询失败，不要求用户重复给出原范围。

切换业务域时，新查询的报表限定须有本轮依据，不能把已结束的报表话题带入工单过滤。按极值展开单笔详情时，需要依据已展示事实给出稳定标识；仅排序后取第一条不能证明对象唯一，完整读取和多条歧义保护仍由业务服务执行。

查询草稿会先经过认证 HTTP MCP 的只读校验，匹配多条等确定性错误可用于最多两次草稿修正。成功事实只在本轮缓存，经独立语义复核和当前权限复查后发布；失败草稿不写卡片、不更新成功查询上下文。追加状态条件不能静默移除未撤销的日期等其他字段限制；无字段条件时使用空条件数组，不能生成空的 AND 组。

追问中明确撤销旧条件时，模型计划使用 `removedFilters` 记录被撤销的字段及本轮连续原文证据；未被撤销的其他字段继续保留。此结构只属于规划协议，不改变业务查询接口，也不能用历史原文或模型解释代替用户依据。普通只读查询后，模型修正也不能把被拒绝的建单改成无明确范围的旧预览刷新。

连续查询只继承上一成功查询中仍然有效的条件。较早对话中已经撤销的条件不会因之后修改金额、翻页或查看汇总而自动恢复。复核必须逐条声明条件来自本轮要求、当前有效查询或实际已展示对象；历史对话用于解释本轮指代，不能单独恢复旧限制。

同一字段的上限和下限分别保留。只调整上限不能删除原下限，反之亦然；同范围追问中被替换或删除的每个旧条件，都须在复核的 `priorConditionChanges` 中给出完整旧条件、变更作用域和本轮依据。完整新条件仍由规划器输出，程序不自动合并或补写。独立新查询直接按当前要求重建条件，两个旧条件撤销数组均为空。

金额等数值字段的“以上／至少／不少于”包含恰好等于阈值，“以下／至多／不超过”同样包含等于；“超过／大于”和“少于／小于”排除等于。区间分别核对两个端点，显式不含本数的说明仍须保留。候选排除和恢复操作中的条件描述被操作集合，不能再次反转比较符。对于原文中阈值和数学关系明确且唯一的比较，程序独立核对方向与等号；该校验只拒绝冲突，不生成意图或自动修正模型计划，其他语境仍由真实模型复核。

会话分别记录最近尝试和持续业务焦点。帮助或澄清不清除原来的查询/派单焦点；派单预览中的选择操作不能因出现字段条件被静默改成普通查询。统一规划及独立语义复核核对动作和选择含义，程序校验结构、权限和稳定引用；语义偏差共用有界草稿修正预算，不通过词语表生成意图。

普通查询不变更现有派单预览、排除集合或清单。成功查询已唯一定位记录后，可以直接说“帮我派单这条”；程序按原身份和公司重新核验当前状态及规则，再生成精确预览与待确认清单，不要求用户重复查询候选。准备全部查询结果要求已完整展示且范围有界；失败或不完整查询不能提供未经核实的目标。继续使用原派单候选时须明确指向该候选，不能拿旧预览替代刚查询的对象。确认派单仍使用清单卡片和独立确认接口。

候选调整在规划或复核阶段失败时，原选择虽然仍保存，但不能作为调整已经成功的证据。没有新的完整范围或选择操作时，后续建单须先重新展示核对候选；也可按本轮明确的完整选择重新预检。帮助说明保留这一未完成状态，不把帮助回复当作选择成功。询问助手是否支持审批属于能力咨询，回复会说明工单只读、不能代为审批。

汇总查询表达统计范围，不提供可用于派单的记录引用；先列出具体记录或可派候选，再准备清单。候选被新的业务查询话题打断后仍保留，但需要先重新展示核对，才能再次从该候选准备清单；明确的具体记录仍可通过当前查询来源准备。界面重新建立候选也会恢复其业务焦点。这些来源约束由程序执行，不由模型自行声明已核对。

## 工单的演示范围

本机工单提供者使用固定环节和固定演示审批人：提交登记、部门审批、财务复核、业务处理、归档。固定示例覆盖待审批、处理中、已完成和已驳回，另有 B 公司示例用于权限验证。它们标注为“固定演示示例”，不是实际派单记录。

当前用户有权查看的成功派单条目具有稳定请求号时，可以映射为 `WO-<请求号>` 工单，来源标注为“实际演示派单关联”。派单成功只证明提交结果，因此关联流程停在首个审批环节，不自动变成审批成功。

查询不会推进流程。终态工单没有当前处理人；未来环节的审批人不计入当前待办。工单详情和总结由接口事实确定性生成，模型不编造办理原因、审批意见或完成时间。真实工单系统尚未接入，后续替换 `WorkOrderProvider` 实现并进行实际接口验收。

## 数据、统计和权限

- 报表全部状态读取使用配置适配器的 `dataRowsAfter`，未实现该能力的自定义适配器明确拒绝，不以待派单子集代替。
- 当前实现每轮在限定公司和报表范围内有界读取，再统一筛选、排序和统计；默认最多扫描 100000 条、120 秒，保留事实另外限制为 16 MiB。条件筛选尚未普遍下推来源数据库。超限时整体失败，可缩小公司或报表范围，不能把截断集合当作全部数据。
- 列表每页最多 50 条；金额和长标识按字符串传输，金额使用精确十进制。没有声明币种的金额不参与合计。本仓库三张演示报表在业务服务配置中明确声明 CNY；外部报表应由其来源字段或可信配置声明单位。
- 查询前由当前目录展开可见报表，业务服务再次检查租户、公司、报表及派单归属。身份由服务器注入，模型不能提供用户或管理员标记。
- “我创建的派单”使用服务端计算的 `createdByMe` 条件，按当前认证标识匹配，不把“我”当作姓名。同名用户不会相互匹配，管理员查询本人时也只返回本人记录。
- 查询没有匹配行仍保留其业务数据域；继续筛选、分组或翻页不能静默切换成另一类对象。明确发起另一类对象的查询时，作为独立查询处理。
- 卡片持久化查询时点、实际范围、当前页和完整统计；刷新恢复历史快照，不把旧时点当作实时数据。会话保留曾查询报表的范围并集，权限变化后拒绝展示该会话，需新建会话重新查询。
- 数据库继续使用 `report_demo`，本次未新增业务表或迁移，不清库、不重置已派单状态。固定工单资源不写回来源表。

## 实现与验证入口

`ModelAssistantPlanner` 一次生成包含动作与对象来源的完整 `AssistantPlan`，先执行严格解码、身份引用和无写入业务预检，再由独立模型调用依据原文与受控上下文形成完整期望。独立调用不读取草稿动作、结果集合或修正历史。只读查询使用 HTTP MCP `business_query`；派单将同一已复核的 `DispatchDirective` 交给确定性流程，执行层不再次解释原文。

两个阶段共同读取 `assistant/task-contract.txt` 和派单动作契约，避免规划与复核采用不同的能力、字段或生命周期规则。独立复核输出本轮语义要求及完整任务期望，由 `TaskPlanComparison` 比较操作字段和条件逻辑；说明文字不能另发与结构化期望相反的修改命令。要求的证据固定引用本轮原话，历史只在含义说明中解释指代；恢复、撤销和排除不能用被引用的历史指令代替本轮授权。集合顺序可以规范化，AND/OR、否定、匹配算子及分页不能因为当前结果恰好相同而被视为等价。澄清措辞不参与操作比较，行为一致时使用已复核的澄清表达；可执行字段仍来自通过预检的规划草稿。

独立期望中的 `conditionChecks` 按字段、比较符和值绑定每个不同条件，与数组排列顺序无关；条件分组仍由完整计划比较核对。每项都接受当前来源与明确数值边界校验。无效期望先修正复核自身，不会要求规划器把正确条件改为错误条件；通过校验后才冻结本轮期望。权限、执行版本及业务服务失败仍直接返回，不进入条件修正来更换目标。

`priorConditionChanges` 覆盖同范围续查中消失的旧谓词，区分下限、上限、整个字段及其他谓词。仅命名一个端点的原文不能证明另一端点已获授权删除；金额字段仍在也不能掩盖另一端点遗漏。该结构只供复核，不执行增量补丁。新查询、跨范围查询、单条资格核验和非查询均不继承这类旧谓词，数组为空。

同一次复核中的业务前提、原文证据及条件来源错误一并反馈，避免逐个发现问题耗尽重试次数。前提失败时不使用不完整事实校验目标数量；权限、版本和服务故障仍立即终止。准备当前选择不重放历史排除，澄清计划没有实际字段条件，条件证据也须为空。

报表范围的追加、移除和记录勾选分别保留其语义。完整指定报表集合用一次替换；“全部授权范围”使用明确的 `ALL_AUTHORIZED`，不能当成空集合再追加。模型填写报表简称或别名时须逐字引用本轮原话；输入会列出本轮实际命中的授权报表原词，不从历史焦点或记录类型补造报表名。反馈指出错误字段和值，不能通过删除用户的报表限定来通过预检。“先准备、不要提交”允许生成待确认清单，禁止提交执行；禁止声明使用独立的动作类型，执行值不属于可执行任务动作。实际派单仍只能由用户在页面确认。

首次草稿之前，先只看本轮原文及请求前焦点进行独立目标判断，区分只读筛选、查看候选、准备清单、查询数据域、查询承接及最终总条数。目标阶段仅提供当前焦点中的查询：展示候选后，背景中的旧查询不能抢占后续勾选操作。续查须有当前成功查询且数据域相同；报表、派单记录与工单之间的切换必须独立重建。新查询不自动保留旧排除条件，真正的追问继续保留有效限制。目标判断不读取草稿、复核期望或它们的错误反馈；自身结构和上下文前提错误只在本阶段修正，最多重试一次，并为完整复核保留至少一次调用。目标与完整复核共用三次独立判断预算。明确要求的最终条数不能因详细复核漏填而消失；漏填和实际数量不足会同时反馈。局部排除、恢复条数不等于最终总数。对象不唯一或能力前提不足时仍可澄清，不能根据目标类别绕过权限和业务预检。

目录上下文包含业务用途与字段说明，派单子流程的默认动作不作为统一入口默认值。`BusinessTermEvidence` 从本轮已通过校验的只读事实中提取原文实际命中的授权字符串字段值，最多64项，作为独立复核的词义线索；不提供行身份、草稿条件或数量，不把未命中视为不存在，也不据此生成意图。产品、费用类型、客户等省略字段名的限定仍由真实模型结合原文解释；正向、否定、撤销和完整匹配不能互相替代。

正常轮次依次包含一次独立目标判断、一次规划和一次完整复核。契约或语义错误最多修正两次草稿，整轮最多三次规划及三次独立判断。三个阶段均发送原生 JSON Schema，并在规则文本中提供同一结构；服务端仍严格拒绝类型错误，不把数组隐式转换成字符串。不可解析的草稿先修复结构；可解析草稿的契约错误与独立语义差异在首次修正时一起反馈，避免耗尽格式修正次数后才检查完整目标。复核仍看不到草稿及其错误，任何无效草稿都不执行。合法独立期望在本轮固定，后续修正不能改变已经确定的要求；用户明确指定最终选择或清单总条数时，还要与完整只读预检数量核对。本轮修正保留先前草稿、只读事实及全部结构化差异。复核格式、证据或前提无效时，仅修复复核自身并消耗共享预算；不把错误意见交给规划器执行。错误反馈包含具体协议字段与约束，查询行引用和候选选择引用不能混用。权限、版本和业务服务故障直接返回，不引导模型换成另一组目标。实际延迟和费用按运行记录评估，首次澄清和失败原因会保存到会话状态及轮次证据，成功查询可恢复就绪状态。各阶段均遵从已配置的思考模式，当前验收基线仍关闭；配置开启不代表所有供应商端点都支持该能力。
