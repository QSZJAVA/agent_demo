## 1. 现存问题

### F1 / P1：预览请求序号分配不原子，旧任务仍可能覆盖新任务

- 位置：`backend/src/main/java/com/example/report/dispatch/store/MybatisPreviewRepository.java:49-54`；`mapper/AgentConversationMapper.java:22-26`。
- `beginRequest` 先 UPDATE 递增，再 SELECT 读取；方法和调用它的提交路径没有把这两步包进同一事务。事务锁只在后面的快照激活阶段取得，不能补救序号重复。
- 可行时序：A 递增为 1 → B 递增为 2 → B 读到 2 → A 也读到 2。两个任务随后都通过 `isLatestRequest`；A 后完成仍能作废 B 的新预览。
- 独立复现：调用真实 MybatisPreviewRepository，用 mapper 替身和 latch 控制两次数据库操作的交错，输出 `A=2, B=2, both latest=true`。未连接真实 MySQL；复现的是仓库方法允许的交错。
- 现有回归测试未覆盖：InMemoryDispatchStore 把递增和返回放在同一个 synchronized 块中，测试替身比生产实现更强。
- 建议：在真正生效的事务内递增并读取同一会话行，或使用可原子返回新值的分配方式；增加针对真实仓库/事务的并发测试。
- 影响：P0-07、P1-02、P1-04；上一轮 R3 仅部分修复。

### F2 / P1：停滞恢复没有阻止旧执行线程继续发送和写回

- 位置：`dispatch/DispatchService.java:434-472`（首次执行）、`:212-228`（重试）；`dispatch/store/MybatisPlanRepository.java:153-172、184-221`；`dispatch/DispatchRecoveryService.java:26-30`。
- 心跳超过五分钟未更新后，恢复任务把清单改成 REVIEW_REQUIRED，但旧线程没有被可靠停止。恢复后继续执行的线程仍调用网关，`updateItem` 只按条目 ID/清单 ID 更新，`finish` 和心跳也没有执行版本约束。
- 触发示例：旧线程在发送前暂停、心跳过期 → 恢复为待核对 → 网关查询 NOT_FOUND，将该条核对为 FAILED，清单收尾为 EXECUTED → 旧线程恢复并成功派单，写回 SUCCESS。
- 独立复现：用真实 DispatchService 和 DispatchRecoveryService，测试替身模拟六分钟前的心跳及上述核对交错；最终 `plan=EXECUTED, successCount=0, item=SUCCESS`，原确认请求还抛出 IllegalStateException。
- 影响：条目与清单汇总冲突；若同时开启下一轮重试，旧线程还可能覆盖新轮次状态。请求号幂等只能保护网关副作用，不能保护本地结果一致性。本次未声称已复现重复外部派单。
- 建议：认领后取得执行版本/执行所有者令牌，心跳、条目写入及收尾都校验它；恢复时撤销旧执行权，发送前检查执行权。已在途的请求仍按幂等号核对，并定义明确的“未收到”与在途请求处理协议。
- 影响：P0-07、P1-04、P1-05；现有核对 CAS 加了版本，但普通执行路径尚未闭合。

### F3 / P2：管理员无法追溯普通用户清单，权限增加也会封锁历史

- 位置：`dispatch/DispatchTraceService.java:52-58`；`dispatch/PreviewService.java:233-240`；`permission/CurrentUser.java:33-37`。
- trace 先允许同租户管理员，再调用 `requireReadable`；后者要求读取者权限指纹等于创建预览者的指纹。指纹包含公司集合、权限码和 admin 标记，默认 admin 和 user1 必然不同。
- 独立复现：user1 创建销售预览和清单，同租户、拥有 A/B/C 公司及全部报表权限的 admin 调用真实 trace 服务，返回 403。
- 同一判断还会让用户仅新增一个报表权限后，原本有权读取的全部旧预览/会话被隐藏。
- 建议：区分执行版本校验与历史读取授权。历史读取依据当前租户、身份/管理员资格、公司和报表权限判断；旧执行清单继续严格校验版本。不要把两个不同用户的权限指纹相等当作管理员访问条件。
- 影响：P0-08、P0-09；上一轮 R2 修复引入的可用性回归。

### F4 / P2：断线发现“最新任务”排序不代表提交顺序

- 位置：`dispatch/PreviewJobService.java:89-94`；`resources/db/migration/V8__preview_jobs.sql:10-11`。
- 任务使用无小数位的 DATETIME，按 `created_at DESC, updated_at DESC, id DESC` 取最新；id 是随机 UUID。V13 的请求序号只在会话表中，没有写入任务行。
- 同一秒内提交 A、B 两个任务，A 较晚失败/完成时，它的 updated_at 可能更大，恢复接口因此返回 A；更新时间也相同时由随机 ID 决定。这在正确阻止旧任务激活以后仍存在。
- SSE 丢失任务编号或另一设备恢复时，前端会轮询错误的旧任务，可能提示旧失败而遗漏新成功预览。
- 验证：表结构、排序 SQL 和前端发现任务调用链静态确认；未运行真实 MySQL 或浏览器端到端复现。
- 建议：把原子分配的会话请求序号持久化到任务表，恢复按请求序号定位最新任务；同步入口与异步入口的恢复语义也应明确。
- 影响：P1-02、P1-06。
