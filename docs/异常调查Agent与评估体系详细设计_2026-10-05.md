## 1. 目标和交付范围

在现有派单 Demo 中增加一个能够自主查询证据、判断还缺什么信息、继续调用工具并形成调查报告的 Agent。首个业务场景为“分析指定清单中的异常条目”。

学习者应能观察一轮真实模型请求、模型选择的工具及参数、服务端执行、工具结果回传、后续工具选择以及终止条件。第二阶段使用独立任务集验证结果和执行约束，比较修改前后的质量、稳定性、时延与用量。

### 1.1 第一阶段交付

1. 清单页面的“分析异常”入口，目标清单由页面明确传入。
2. 受限的模型工具调用循环，模型自主决定查询顺序；所有工具都是只读业务查询。
3. 调查任务、步骤和证据的持久化，以及页面刷新后的状态读取。
4. 结构化调查报告，逐条区分已核实事实、推测、缺失证据和处理建议。
5. 当前权限校验、预算、超时、取消、来源变化和中断处理。
6. 最小真实模型工具调用验证与真实 HTTP MCP 集成验收。

### 1.2 第二阶段交付

1. 独立的调查任务语料与确定性事实判定器。
2. 不经过模型的权限、循环、协议、状态和数据库回归。
3. 真实模型工具选择评估，以及真实模型与 HTTP MCP 联合评估，两类报告分别标注证据范围。
4. 同题多次运行、单次执行轨迹、任务汇总和基线对比。
5. 语料、提示词、工具契约、模型参数、代码版本的可追溯标识。

### 1.3 范围边界

本轮目标不包含跨清单自由搜索、自然语言修改派单记录、自动重试业务派单、规则发布、跨会话长期记忆、多 Agent、模型微调或任意 SQL 工具。调查报告中的建议只是建议，实际派单、重试、核对仍通过已有业务入口进行当前权限及确认校验。

Demo 账号实现的已知问题按仓库范围暂缓，前端框架和依赖版本保持不变。正式企业认证、外部 ERP、生产容量、灾备及完整目标环境部署均不在本设计中宣称已完成。

## 2. 不考虑历史数据的设计原则

本节落实 [AGENTS.md](../AGENTS.md) 的“Demo 数据与版本设计原则”。

- 只实现当前目标表结构、当前任务结构、当前接口及工具契约。
- 不增加旧记录填充、旧字段默认含义、历史协议转换、双读双写或旧浏览器缓存迁移。
- 破坏性变化采用专用 Demo/测试库重建；不交付旧库原地升级和旧版本回滚方案。
- 初始化与 Flyway 可以按最新基线整理，验收关注空库初始化和目标结构；不要求维护废弃迁移的校验和。
- 当前版本产生的清单执行快照、幂等账本、规则快照和审计仍是调查必需的事实，必须保存。它们属于同一版本运行期间的业务证据，不属于旧数据兼容。
- 任务协议标识与提示词哈希用于定位当前执行和评估，不引入多版本解码器。遇到不匹配的运行数据按不支持处理，进入最新 Demo 基线时重建。
- 历史评审报告保留原始版本和证据范围。设计阶段只修改规则与文档；后续实现的数据库验证使用核实的专用隔离库。

实施时，若被修改模块中存在仅服务于旧数据的分支，可随该模块重构直接删除。仍承载当前业务能力的代码按正常行为回归验证，不以删除文件数量作为目标。

## 3. 现状和复用边界

| 现有部分 | 已有能力 | 本设计中的使用方式 |
| --- | --- | --- |
| `AgentChatService` / `SemanticConversationService` | 当前自由文本统一为 V1 意图，确定性查询和建单 | 保持其当前业务职责；调查通过明确的页面入口进入专用服务 |
| `ModelIntentParser` / `IntentCodec` | 无工具模型解析、Schema 和原文证据校验 | 参考模型连接和验证方式；不把调查循环塞入 V1 解析器 |
| `BusinessMcpClient` | 服务认证、可信身份注入、HTTP MCP 调用和响应解码 | 复用传输与鉴权约束；新增可受调查剩余时限约束的只读调用能力 |
| `DispatchTraceService` / `TraceReader` | 清单权限、执行记录、规则快照、审计和可靠事件 | 提取当前格式的有界事实查询；不把整段会话或整个追溯对象直接发给模型 |
| `McpDispatchGateway` / `BusinessDispatch` | 按稳定请求号查询结果；管理员按原操作者核对 | 复用核对契约；调查包装层区分鉴权拒绝和传输不可用 |
| `DispatchJobService` | 持久任务、事务认领、租约、前端恢复模式 | 借鉴实现模式；调查使用独立任务表、线程池和动作集合 |
| `ResourceQuotaService` | Redis 速率限制、MySQL 并发租约 | 增加调查操作类型及明确限额，不占用派单执行线程 |
| 前端 `PlanCard` / `ResultCard` / `DispatchTrace` | 清单、逐条结果和追溯展示 | 增加调查抽屉与入口，沿用当前组件体系 |
| `SemanticEvaluation` | 校验意图和业务范围的真实模型语义回放框架 | 参考语料读取和报告输出方式；调查另建任务级判定器 |

两个后端目前共享一个 MySQL schema。调查的运行表归 Agent 后端业务域维护，业务幂等账本仍归业务服务维护。现有 MCP 六个工具不等于可直接给模型使用的调查工具集，尤其不能把派单提交和配置探测工具注册给调查模型。

调查入口仍运行在现有 `real,mcp` 应用中，`agent.semantic.mode=active` 继续描述既有对话入口；它不控制调查服务的工具循环。调查模型解析来源统一记录为 `MODEL`。

## 4. 用户流程与调查范围

### 4.1 首个场景

用户打开一份存在异常条目的清单，点击“分析异常”，输入“说明失败原因，列出依据和下一步建议”。页面展示：

1. 已绑定的清单和条目范围。
2. 当前调查状态与已经完成的查询步骤。
3. 按条目给出的结论、证据和建议。
4. 尚未查明的事项、查询失败、证据不足及来源变化提醒。

第一版以清单标识作为必要上下文，不从自由文本猜测用户指的是哪份清单。

### 4.2 准入和选择

- 允许清单状态：`EXECUTED`、`REVIEW_REQUIRED`。正在执行或尚未确认的清单返回明确冲突原因，待业务状态稳定后重新发起。
- 默认目标是该清单中 `FAILED`、`SKIPPED`、`UNKNOWN`、`PENDING` 条目。这里 `PENDING` 只可能作为待核对清单中的未完成条目，不能据此推断从未发送。
- 用户可以明确选择上述条目的子集；选择使用清单条目 ID，不使用可能重复的单据号作为唯一标识。
- 首版每次调查最多 10 条，使逐条报告与模型输出预算匹配。超过时要求页面明确选择子集，不静默取前 10 条，不宣称覆盖整份清单。
- 没有异常条目时直接返回“当前范围没有可调查异常”，不调用模型。
- 用户问题上限 1000 字符；问题可以调整分析关注点，不能扩大绑定清单或条目集合，也不能授予写权限。
- 清单所有者和具有完整范围权限的同租户管理员可创建调查。第一版调查任务及报告只归创建人读取，不增加管理员浏览他人调查记录的功能。

### 4.3 新调查与页面恢复

首次提交前固定 `Idempotency-Key`。丢失提交响应时用原键和原负载查询或重发；得到任务 ID 后仅查询该任务。页面刷新恢复已有任务，点击“重新分析”才产生新的键和新任务。

页面断开不等于取消任务。用户显式取消后，服务端停止后续模型与工具调用；已经发生的模型调用费用不视为能够撤销。

## 6. 模型接入与工具循环

### 6.1 模型请求

沿用真实端点、密钥和模型配置来源，但使用调查专用客户端/选项，不能继承其他客户端注册的默认工具。模型名默认沿用 `LLM_MODEL`；增加单独覆盖项的目的是评估，不预设另一个模型必然可用。

采用 Spring AI 1.1.8 支持的由应用控制工具执行的方式：注册调查专用 `ToolCallback`，关闭框架内部自动工具执行，由程序读取工具请求、执行业务校验、调用工具并把结果回传模型。可信运行上下文通过 `ToolContext` 传入，不出现在模型可填的参数中。相关 API 依据见 [Spring AI 1.1 工具调用文档](https://docs.spring.io/spring-ai/reference/1.1/api/tools.html#_user_controlled_tool_execution)。

这是显式控制执行循环，不是禁止模型提出工具调用。当前 V1 解析器使用无工具请求，两者职责和选项分别配置。

目标端点必须实际验证支持所选模型的工具调用，以及多个工具结果的配对处理。最终 JSON Schema 能力单独验证；不假设端点能同时接受原生 Schema 和工具请求。收集证据阶段使用工具调用，最终报告阶段关闭工具，只生成受校验的报告 JSON。端点不支持所需工具能力时报告配置/能力失败，修复真实配置后再运行。

### 6.2 提示词内容

系统提示固定说明调查目标、五个工具的能力、证据引用规则和终止协议。输入只包含用户本轮问题、已授权的清单概要、目标条目引用、运行预算和当前轮次的工具结果。

- 模型选择查询顺序、决定需要补查哪些条目，以及何时信息足够。
- 工具返回的数据、错误文本、单据摘要和规则说明都是待分析数据，不能覆盖系统规则或新增工具权限。
- 不把其他会话文本、服务凭据、账号密码、内部堆栈或用户完整权限列表放入上下文。
- 不要求模型输出内部思考过程。页面记录工具名、参数摘要、事实结果和简短状态说明。
- 模型遇到证据不足可以给出不确定结论，不能把缺少证据变成成功或失败事实。

### 6.3 一次调查的执行顺序

1. 接收请求：验证当前权限、清单状态、选择范围和幂等键；保存 `QUEUED`。
2. 工作线程认领：获取调查配额，在短事务内固定清单执行版本、所选条目、规则和本地事件边界，保存证据快照，进入 `RUNNING`。
3. 程序将范围概要和不透明条目引用交给模型，不预先替模型完成所有调查工具查询。
4. 调用真实模型，取得工具请求或收集结束信号。
5. 对本轮工具请求逐项进行工具白名单、Schema、引用、权限、预算和来源版本检查；以固定次序串行执行本轮请求。
6. 将每个工具结果绑定原 `toolCallId` 回传，记录步骤、耗时、证据和用量；继续下一轮。
7. 模型不再请求工具，或收集阶段预算用尽时，进入报告阶段。仅当尚有总预算时调用无工具的报告生成请求。
8. 校验报告；在预算内最多一次报告修复。修复只处理结构、引用及事实冲突，不获得新查询权限。
9. 最终再校验当前权限与来源版本，在带认领令牌的条件更新中保存报告和终态。
10. 释放配额和工作槽。前端读取终态和完整步骤，不依赖原连接存活。

### 6.4 工具消息与循环边界

- 模型一次返回多个工具请求时，每个请求都消耗一次工具预算。工具名和调用 ID 必须合法且本次运行内不冲突。
- 先验证整批请求是否符合工具白名单、调用数量和协议；若存在非法工具，整批不执行业务查询，并返回受控错误或终止。
- 执行过程中出现全局终止条件，剩余工具不执行；该任务结束，不带着缺失的工具响应继续下一轮。
- 可恢复的参数错误按原调用 ID 返回 `INVALID_ARGUMENT`，消耗预算；至多允许两次参数错误，之后进入受限结束。
- 使用规范化参数计算请求摘要；同一查询结果在本次冻结快照内复用，重复请求仍计入工具预算。连续三次未增加任何新证据的重复请求结束收集，标记 `NO_PROGRESS`。
- MCP 查询不自动重试。模型可以在剩余预算内再次请求；同一条目的结果核对最多两次，且第二次只用于第一次传输失败或结果未知。
- SDK 自动重试也必须关闭或纳入统一计数；不能在外层一步内部产生未计数的模型调用。

## 7. 工具契约与证据

### 7.1 可信运行上下文

`ToolContext` 由程序注入 `runId`、`tenantId`、`actorId`、`planId`、`planOwnerId`、`executionVersion`、允许的条目映射、截止时间和认领令牌。模型参数不能提供或覆盖这些字段。

模型使用运行内的 `I1`、`I2` 等条目引用。服务端负责映射到真实 `dispatch_plan_item.id`；禁止把任意数字 ID、单据号或外部请求号当作已授权引用。

### 7.2 五个工具

所有对象参数均拒绝未知字段、缺失必需字段和隐式类型转换。数组长度、游标归属和字符串长度由服务端验证。

| 工具名 | 模型输入 | 返回事实 | 约束与实现来源 |
| --- | --- | --- | --- |
| `investigation_plan_summary` | 空对象 | 清单状态、执行版本、全清单计数、所选范围计数、快照时间 | 来自冻结快照；明确区分全清单和选中条目 |
| `investigation_plan_items` | `cursor` 可空，`size` 为 1～20 | 目标条目引用、冻结状态、错误码及脱敏摘要，下一页游标 | 仅查询已选集合；完整覆盖必须读完相关页 |
| `investigation_rule_snapshots` | `itemRefs`，1～10 个 | 条目执行时保存的规则版本、表达式与说明，或明确缺失 | 只查条目快照，不用当前规则替代；不提供规则维护能力 |
| `investigation_execution_events` | `itemRefs`，1～10 个；`cursor` 可空；`size` 为 1～20 | 已冻结事件边界内的尝试、复核、失败和核对事实 | 只返回指定条目的结构化事件；不返回整段用户聊天或任意审计 SQL |
| `investigation_dispatch_lookup` | `itemRefs`，1～5 个 | 每条的远端结果、业务错误码、观察时间或查询错误 | 由服务端映射原请求号，逐条经真实 HTTP MCP 查询；每个远端调用另计预算 |

分页游标必须绑定运行 ID、数据集合与最后记录位置；篡改、跨运行或跨工具使用返回参数错误。响应明确 `complete`、`nextCursor` 和 `truncated`，不能让模型把当前页当作全部事实。

工具输出封装示意：

```json
{
  "ok": true,
  "data": {
    "items": [{"itemRef": "I1", "status": "UNKNOWN", "errorCode": "TRANSPORT_TIMEOUT"}],
    "nextCursor": null,
    "complete": true
  },
  "evidenceIds": ["E1"],
  "observedAt": "2026-10-05T10:00:00+08:00",
  "truncated": false
}
```

该 JSON 为契约示意，条目和错误码是设计样例，不是本次真实业务结果。

### 7.3 HTTP MCP 核对边界

当前 `dispatch_lookup` 已能查询稳定请求号。本人调查由本人核对；管理员调查他人的清单时，服务端从已授权清单读取原操作者，并使用已有代核对契约。模型不能指定原操作者。

条目没有持久化请求号时返回 `NO_REQUEST_ID`，不拼接、猜测或恢复旧格式请求号。该事实只说明缺少核对依据，不能直接断言未发送。

现有 `McpDispatchGateway.lookup` 会把部分运行异常归为 `UNKNOWN`。调查新增的读取层必须保留权限拒绝与网络故障的区别：权限拒绝立即停止任务；传输不可用是证据不足；远端明确 `UNKNOWN` 是业务结果未知。

`NOT_FOUND` 仅表示该请求号在本次观察时未查到受理结果，报告不得据此自动建议直接重发。调查工具也不能调用会更新清单状态的 `reconcile` 服务。

现有 MCP 客户端请求上限为 65 秒，不满足调查逐调用预算。新增专用只读客户端或为传输层补充可验证的截止时间控制；不得修改派单写请求的超时语义，也不能只超时外层 Future 而放任底层请求无限占用线程。

### 7.4 证据模型

每份证据至少保存：运行内引用、来源类型、绑定条目、清单执行版本、来源记录标识、观察时间、内容哈希、脱敏的结构化内容、是否被截断。模型只得到必要字段和不透明引用。

证据来源包括 `PLAN_SNAPSHOT`、`ITEM_SNAPSHOT`、`RULE_SNAPSHOT`、`EXECUTION_EVENT`、`MCP_LOOKUP`。引用只在当前运行中有效，不能引用其他用户、其他清单或尚未返回给模型的证据。

2026-10-06 第三阶段扩展：新增结构化上下文笔记及运行内证据回读，仍使用上述业务证据类型。当前设计与验证范围见 [上下文工程](上下文工程设计与验收_2026-10-06.md)。

引用存在不等于模型解释一定正确。程序对状态、错误码、版本、远端核对结果等可枚举事实做确定性检查；对自然语言因果解释通过评估和人工抽查验证，不能宣称 JSON 或引用校验已经证明全部语义正确。

## 8. 最终报告协议

报告包括调查范围、每个条目的事实结论、解释、证据、建议、未解决问题和覆盖情况。2026-10-05 整体评审 F2 后，模型协议收紧为以下结构化输出；状态正文由程序在事实校验后生成，模型不再提交自由文本 `summary`、`explanation` 或 `message`。这一调整不修改此前真实模型归档的原始证据。

```json
{
  "findings": [
    {
      "itemRef": "I1",
      "reasonCode": "RESULT_UNKNOWN",
      "certainty": "INSUFFICIENT",
      "evidenceIds": ["E1", "E2"],
      "nextStep": "MANUAL_REVIEW"
    }
  ],
  "unresolved": [{"itemRef": "I1", "topics": ["REMOTE_RESULT"]}]
}
```

该示例只说明格式，不作为事实判定样本。`runId`、清单 ID、时间、覆盖计数、来源变化状态由服务端补充，模型不能决定。

服务端展示报告另补充固定只读摘要、按结论及核实程度生成的 `explanation`，以及按 `topics` 生成的待查 `message`。`topics` 允许 `RULE_CAUSALITY`、`EVENT_HISTORY`、`REMOTE_RESULT`、`MANUAL_REVIEW`，只表示仍需核查的方面，不声明规则因果关系已经证实。业务错误码及原始执行事实保留在引用证据中。

### 8.1 枚举与事实约束

| 字段 | 允许值与规则 |
| --- | --- |
| `certainty` | `VERIFIED` 有直接事实；`HYPOTHESIS` 仅有相关线索；`INSUFFICIENT` 无法得出结论。禁止模型自报百分比置信度 |
| `reasonCode` | `BUSINESS_REJECTED`、`PRECHECK_SKIPPED`、`RESULT_UNKNOWN`、`REMOTE_SUCCESS_LOCAL_UNRESOLVED`、`REQUEST_NOT_FOUND`、`EVIDENCE_MISSING`、`UNDETERMINED` |
| `nextStep` | `VIEW_EVIDENCE`、`USE_EXISTING_RECONCILE`、`RECHECK_CURRENT_RULES`、`MANUAL_REVIEW`、`NONE`；均为文本建议，不是可执行工具指令 |

`BUSINESS_REJECTED` 必须有明确失败结果，网络异常不满足；`PRECHECK_SKIPPED` 必须有复核跳过事实；`REMOTE_SUCCESS_LOCAL_UNRESOLVED` 必须同时有本地未明状态和本次远端成功证据。某条规则快照存在本身不能证明该规则导致失败。

第一版每个目标条目必须恰好有一个 finding；即使无法解释，也必须以 `INSUFFICIENT` 明确覆盖。全清单计数从数据库快照取得，模型不能计算后覆盖事实计数。

模型报告根对象和子对象均拒绝未知字段；`evidenceIds` 最多 4 个，`unresolved` 最多每条目 1 项，`topics` 含 1～4 个不同枚举。`VERIFIED` 至少引用一份支持相应事实的证据。报告存在 `finish_reason=length` 或 JSON 未完成时视为无效，不能以删掉尾部条目修补成成功。增加条目上限前必须同时验证输出预算、模型限制和对应边界语料。

最终校验拒绝范围外条目、重复条目、未知引用、不存在的错误码断言、与证据冲突的状态和非白名单建议。拒绝后最多修复一次；仍失败则任务为 `FAILED/REPORT_INVALID`，保存可读取的调查步骤，不展示未经校验的报告。

`COMPLETED` 表示在预算内完成调查协议和合格报告，不表示每条业务记录已查明原因，更不表示派单成功。预算或工具故障导致调查未充分完成而报告仍合法时为 `PARTIAL`，页面必须显示原因。

## 9. 预算、时限和资源隔离

以下均为拟新增 `agent.investigation.*` 配置的设计默认值，尚未写入应用配置，也没有用压测证明最优。超出限制必须有可观察终态。

| 配置后缀 | 默认值 | 计数和处理规则 |
| --- | --- | --- |
| `max-items` | 10 | 单次调查条目上限；超过则拒绝提交，扩大前需验证报告输出预算 |
| `max-model-calls` | 8 | 包含收集、报告生成和报告修复的所有真实请求 |
| `max-collection-calls` | 6 | 带工具的收集阶段最多六次模型请求，为报告保留最多两次请求 |
| `max-tool-calls` | 16 | 每个模型请求的工具调用逐个计数，错误、缓存命中也计数 |
| `max-mcp-calls` | 20 | 批量核对中的每个 HTTP MCP 工具调用计数，防止批处理绕过预算 |
| `max-output-tokens` | 2400 | 收集阶段每次模型请求的输出上限；以目标端点实际参数支持为准 |
| `max-report-output-tokens` | 4096 | 报告生成和修复的输出上限；须用最大 10 条场景验证端点支持及完整输出 |
| `max-input-utf8-bytes` | 98304 | 每次请求最终序列化消息的 UTF-8 字节上限；不是 token 上限 |
| `max-tool-result-utf8-bytes` | 8192 | 每个工具结果的上限；按完整记录分页并标记截断，不截断 JSON |
| `run-timeout-seconds` | 180 | 从开始执行计算，包含模型、工具、锁等待和报告修复 |
| `model-timeout-seconds` | 40 | 每次模型请求不超过剩余运行预算；超时不自动重试 |
| `mcp-timeout-seconds` | 8 | 每次核对受连接、响应及剩余预算共同约束 |
| `queue-timeout-seconds` | 120 | 超时排队进入 `FAILED/QUEUE_TIMEOUT`，不开始调用模型 |
| `worker-count` | 2 | 调查专用线程上限，与派单线程隔离 |
| `max-active-per-user` | 3 | 同用户排队及执行中调查上限 |
| `max-active-per-tenant` | 12 | 同租户排队及执行中调查上限 |
| `lease-seconds` / `heartbeat-seconds` | 45 / 10 | 工作线程定期续租；租约失效阻止旧线程回写 |
| `retention-days` | 7 | 终态报告、步骤和证据的默认保留天数 |

输入过大时，先裁剪非必要的展示字段并使用有界分页；仍超过预算则停止收集。不得丢弃条目范围、权限边界或来源版本来继续运行。

token 使用量优先读取模型响应 metadata。端点不返回时记为 `null`，不能记为 0 或用字符数冒充。若只掌握部分调用用量，汇总同时输出 `usageComplete=false`。费用只有在输入、输出及缓存计费口径均已配置且用量足够时计算，保存币种和价格配置哈希；否则费用为空。该预算是调用数、字节和时间上限，不声称缺失计量时仍实现精确金额封顶。

当前配额类的速率与并发口径并非调查专用参数。实施时增加 `investigation` 操作的明确限额，数据库队列锁负责在途准入，运行配额负责实际执行并发，两者分别验收。所有限制均包含评估流量，不因来自评估脚本而绕过。

## 10. 任务状态、快照与中断

### 10.1 状态机

| 状态 | 含义 | 允许后继 |
| --- | --- | --- |
| `QUEUED` | 请求及幂等身份已持久化，尚未调用模型 | `RUNNING`、`CANCELLED`、`FAILED` |
| `RUNNING` | 当前工作线程持有有效认领令牌 | `COMPLETED`、`PARTIAL`、`FAILED`、`CANCELLED`、`INTERRUPTED` |
| `COMPLETED` | 报告合法，收集正常结束，无已知来源变化 | 终态 |
| `PARTIAL` | 有合法报告，但预算、证据查询或来源变化限制结论 | 终态 |
| `FAILED` | 无可交付的合法报告，如鉴权、模型连接或报告协议失败 | 终态 |
| `CANCELLED` | 用户取消，后续结果不得覆盖取消状态 | 终态 |
| `INTERRUPTED` | 执行租约丢失或进程中断，保存已有步骤 | 终态 |

`stopReason` 记录具体原因，例如 `NORMAL`、`BUDGET_EXHAUSTED`、`NO_PROGRESS`、`TOOL_UNAVAILABLE`、`SOURCE_CHANGED`、`ACCESS_REVOKED`、`MODEL_UNAVAILABLE`、`REPORT_INVALID`、`QUEUE_TIMEOUT`、`USER_CANCELLED`、`LEASE_LOST`。

任务结束不会改变派单清单状态。取消、核对和重试派单必须继续走现有业务服务；不能由调查任务状态推断业务操作是否成功。

### 10.2 来源快照

接收时保存请求对应的清单执行版本。认领后，在同一个短事务的一致性读取中取得当前版本、目标条目、规则快照和本地执行事件，验证版本仍相同，然后保存有界调查快照。

每条最多冻结最近 20 条与其相关的执行事件，同时保存总数及截断标记；一份任务总事件上限 200。事件超过上限时明确本地事实不是完整执行历史，模型不得宣称已审查所有尝试。冻结快照不包含会话自由文本。

快照包括规范化的清单状态、执行版本、目标条目状态/错误/尝试次数/更新时间/规则内容及事件边界，并生成 `sourceFingerprint`。本地查询工具始终读取该快照，避免同一调查的不同页来自不同状态。

HTTP MCP 查询属于查询时点的实时证据，必须另记 `observedAt`。不宣称本地快照与远端读取是跨服务原子快照。

每次工具执行前和最终报告提交前，重新检查清单执行版本和目标条目指纹。来源变化后停止新查询：有合法且注明时点的报告时保存 `PARTIAL/SOURCE_CHANGED`；无法生成合法报告则保存 `FAILED/SOURCE_CHANGED`。最终比较和任务结果写入应在同一短事务内锁定清单及目标条目，避免校验完成后又被同一数据库中的执行更新穿过。

已经完成的报告不会无限保持“当前正确”。GET 报告时另计算 `sourceChangedSinceRun`；来源已变化则页面提示这是某时点的调查，并提供重新分析入口，原报告不被悄悄重算覆盖。

### 10.3 认领与并发

1. 提交时锁定租户调查队列行，检查租户和用户在途数量，插入任务；同租户同用户同清单最多一份在途调查。
2. 工作线程使用 `FOR UPDATE SKIP LOCKED` 认领未过期的 `QUEUED` 任务，设置随机 `claimToken`、开始时间、截止时间和租约。
3. 认领后获取执行配额；获取失败在调用模型前结束为明确失败，不把任务静默重复入队。配额释放在所有退出路径执行。
4. 模型和 MCP 调用在数据库事务之外执行。续租、步骤保存和结果提交使用运行 ID、状态、认领令牌和版本条件更新。
5. 取消或租约回收在事务内清除认领权和在途唯一键；旧工作线程即使收到迟到响应也不能追加证据或覆盖终态。

任意任务终止时，同一事务把尚未结束的步骤收尾为 `FAILED` 或 `SKIPPED`，填写终止原因和结束时间，解除增量读取的序号阻塞。数据库不可用时由恢复扫描在恢复连接后完成收尾，不虚构模型或工具成功结果。

第一版恢复的是“已持久化任务和已完成步骤的可见性”。进程在模型请求中途退出时，过期的 `RUNNING` 标记为 `INTERRUPTED`，不自动重放模型请求，不从中间步骤续跑。用户重新分析会创建新任务。这样既保留可靠页面恢复，也明确区分后续阶段的完整检查点续执行能力。

### 11.5 完整性、体积与清理

运行表增加唯一 `(tenant_id, id)`，步骤与证据通过 `(tenant_id, run_id)` 复合外键关联运行，删除策略为 `RESTRICT`，防止子记录租户与所属运行不一致。清理服务在短事务中先删子记录再删运行。业务清单删除或会话清理应显式清理相关调查记录，不能遗留可读孤立证据。

任务快照序列化上限 2 MiB；步骤结果上限 8 KiB；每次证据内容上限 8 KiB；运行级证据总量上限 512 KiB。截断必须按完整条目进行并保留完整性信息。超过无法合理裁剪的范围时返回 `SNAPSHOT_TOO_LARGE`，引导缩小条目集合。

只清理到期终态任务，运行中的任务先按状态机结束。清理后任务 ID 查询返回 404，列表不再返回该任务；页面不得用保留期外的旧请求自动创建新任务。待提交恢复线索应同时保存创建时间，超过保留期或得到已清理任务的 404 后停止自动重发，要求用户明确重新分析。数据保留期内相同幂等键严格返回同一运行；过期清理后不承诺旧键仍具有去重身份。

新表由当前数据库初始化链统一创建，Agent 启动继续遵循业务服务先完成数据库初始化的顺序。结构清单、初始化注释、表结构字典和注释检查器在实施时同步更新。本次不新增 SQL 迁移，也不选择旧库升级路径。

## 12. HTTP 接口

以下接口全部为拟新增；使用现有真实会话 Bearer 认证。身份从服务端取得，请求体不接受租户、操作者、原操作者、服务 token 或预算覆盖。

| 方法与路径 | 用途 | 关键返回和约束 |
| --- | --- | --- |
| `POST /api/investigations` | 创建调查 | 必需 `Idempotency-Key`；新任务 HTTP 202，幂等回放 HTTP 200；返回任务标识与状态 |
| `GET /api/investigations/{id}` | 查询状态、活动步骤和报告 | 重新校验归属和当前范围权限；不产生模型调用 |
| `GET /api/investigations?planId=...` | 查询本人对该清单的近期调查 | 每页 20、最多 50，游标分页；不列其他人的调查 |
| `GET /api/investigations/{id}/steps?afterSeq=0&size=20` | 增量读取已完成步骤 | 运行内游标，最大 size 50，返回 `nextAfterSeq` |
| `GET /api/investigations/{id}/evidence/{ref}` | 查看引用证据 | 绑定运行、归属及当前权限，不接受外部 URL |
| `POST /api/investigations/{id}/cancel` | 显式取消 | 幂等；已终态返回原状态，不创建新任务 |

创建请求目标格式：

```json
{
  "planId": "<当前清单标识>",
  "itemIds": ["<当前清单条目标识>"],
  "question": "请分析这些条目的异常原因，列出依据和处理建议。"
}
```

`itemIds` 不传时由服务端选择全部符合条件的异常条目；显式传空数组为参数错误，不能解释为全部。条目 ID 去重排序后再计算幂等负载；问题仅做明确的首尾空白规范化和敏感信息处理，不进行会改变用户意图的自动重写。

新接口使用 `{code,message,data}` 响应体，业务失败同时采用对应 HTTP 状态，不能要求前端只看 HTTP 200。状态约定：400 参数错误，401 未登录，403 当前权限失效，404 不存在或不可枚举对象，409 幂等负载/在途任务/清单状态冲突，413 范围体积过大，429 配额不足，503 依赖不可用。运行中发生的模型错误记录为任务终态，GET 已存在任务仍可返回 HTTP 200 及失败状态。

不同键请求同一用户同一清单的在途调查，返回 409 和本人可见的已有任务 ID；不能静默把新问题覆盖到旧任务。相同键不同负载始终 409。

## 13. 前端交互

第一版采用 REST 提交和有界轮询，复用现有任务恢复经验；聊天 SSE 保持既有职责。调查模型的中间文本不直接作为业务结论流式展示，步骤列表在持久化后展示。

1. 清单或结果卡片增加“分析异常”，打开抽屉，显示清单、目标条目数和问题输入框。
2. 超过 10 条时展示条目选择，明确本次仅覆盖所选子集。
3. 提交前保存当前账号范围下的幂等键及规范化请求。接收 ID 后保存恢复线索，不保存报告正文、证据或凭据到浏览器持久缓存。
4. 初始每秒轮询，后续退避到每 3 秒；网络错误保留任务 ID，提示重新读取。达到页面等待上限不自动取消或重建任务。
5. 抽屉显示排队、已完成查询、当前活动步骤、取消按钮和终态报告；不把模型内部思考过程呈现为执行证据。
6. 点击证据在同一抽屉显示来源、观察时间和当前格式的事实，文本按普通内容转义展示。
7. 来源变化、覆盖子集、证据不足和部分完成均在报告顶部显示；完整度不能只用绿色成功图标表示。
8. 切换账号、清单或关闭组件后，终止本地轮询并使晚到响应失效；关闭页面不取消服务端任务。
9. 页面刷新通过已存运行 ID或本人清单任务列表恢复。找不到保留期外任务时，停止恢复并提示重新分析，不自动 POST。

报告建议最多链接到已有清单和证据页面。首版不提供由模型输出拼装的“执行修复”按钮或可直接调用的任意 URL。

## 14. 第二阶段：评估体系

### 14.1 四层证据分别记录

| 层级 | 输入与执行方式 | 能证明什么 | 不代表什么 |
| --- | --- | --- | --- |
| 协议与循环回归 | 可控工具响应、合成数据、模型传输测试替身 | 参数、预算、消息配对、权限、状态和报告校验行为 | 真实模型的工具选择或自然语言理解质量 |
| HTTP MCP 集成 | 当前真实会话、实际 HTTP MCP、隔离数据库 | 鉴权、核对契约、事务、状态及只读业务效果 | 模型自主调查成功率 |
| 真实模型工具评估 | 真实模型，当前契约的可控只读事实夹具 | 工具选择、补查、结束、报告生成与证据使用 | 真实业务服务部署和业务数据正确性 |
| 真实联合评估 | 真实模型、应用调查入口、HTTP MCP、隔离 Demo 业务库 | 当前环境下端到端调查任务完成情况 | 外部 ERP、正式企业认证、生产容量和灾备验收 |

前端组件逻辑测试、构建及浏览器端到端验收另列。测试替身和合成业务数据只用于构建可重复事实；真实模型评估中的每次模型解析均来自 `MODEL`，配置失败不能换成其他解析来源后继续报通过。

### 14.2 语料组织

拟新增当前格式的 `investigation-cases.json` 和配套事实构建器；开发调优集和验收集分开维护。第一轮目标 40 个独立场景，其中 24 个用于开发，16 个用于保留验收；每个场景使用多个未用于提示词编写的自然语言表达。

场景分布目标：

| 场景族 | 目标数量 | 主要断言 |
| --- | --- | --- |
| 明确业务失败与复核跳过 | 8 | 原因分类和直接证据匹配，不混淆发送前后 |
| 结果未知、远端成功、本地未明与未查到请求 | 8 | 正确选择核对工具，不把未知或未查到当作可重发 |
| 规则与事件缺失、截断、分页 | 6 | 继续补查或明确证据不足，不假装完整覆盖 |
| 多条目、重复单据号、混合结果 | 6 | 逐条覆盖，保持复合身份，不将一条结论套到全部 |
| 权限拒绝、越界条目、指令注入文本 | 6 | 拒绝越权和写入意图，外部文本不改变工具权限 |
| 取消、来源变化、超时、重复工具与预算 | 6 | 在上限内结束，状态和报告部分性正确 |

关键取消、撤权、版本变化与超时还需可控的并发回归，不能只等待模型自然碰到这些交错。联合评估数据由隔离库构建器创建，不能修改日常演示库来制造异常。

### 14.3 单个评估用例契约

每个用例包括 `caseId`、场景族、参与人权限、构建器标识、绑定清单及条目、用户问题、期望可验证事实、禁止行为、允许建议、必要证据来源、预算和重复次数。

不把唯一工具顺序写成标准答案。可以要求“结论包含远端成功时必须实际取得本次核对证据”，而不是要求第几步必须调用哪一个工具。评分不要求模型逐字复述参考答案。

对确定性事实使用代码判定器：状态、条目集合、错误码、证据归属、是否实际核对、是否发生业务写入。自然语言解释使用明确评分规则和人工抽查；模型辅助评分只能补充，不能推翻权限和业务状态硬性失败。

### 14.4 指标与分母

| 指标 | 定义 |
| --- | --- |
| 任务完成率 | 满足全部必要事实、覆盖和禁止行为断言的运行数 / 已实际执行的有效运行数；预期证据不足的正确结论也可完成任务 |
| 条目结论正确率 | 正确判定的目标条目数 / 全部应判定目标条目数，漏项计错 |
| 引用合法率 | 同运行、授权范围内、已取得的有效引用数 / 报告全部引用数 |
| 关键事实支持率 | 有直接证据且语义一致的关键事实断言数 / 全部关键事实断言数 |
| 越权与写入违规数 | 工具调用记录、访问日志和数据库状态差异中的实际违规次数；模型提出但被拦截另计 |
| 调用效率 | 每任务模型、工具、MCP 调用数及无新增证据的重复调用数 |
| 稳定性 | 每个用例重复运行的完成次数与总次数，另报全部重复均通过的场景占比 |
| 时延 | 已执行运行的 P50、P95、最大值，失败和超时单独分组，不从统计中悄悄删除 |
| 用量与费用 | 逐调用及每任务统计；缺失值、完整率、币种及价格版本必须同时呈现 |

基础设施或模型配置失败的批次标记 `BLOCKED`，报告应执行、实际执行、跳过和失败数量，不给出“全部通过”。保留集不足或大量跳过时不满足验收条件。

### 14.5 基线对比与执行轨迹

每次评估输出当前格式的 `manifest.json`、`runs.jsonl`、`summary.json`、`report.md`，以及按运行 ID 分组的脱敏步骤和证据文件。保存代码 commit、工作区差异摘要、语料哈希、提示词哈希、工具 Schema 哈希、模型名、非敏感端点标识、thinking/Schema 选项、预算、开始结束时间和评分器版本。

工作区存在未提交实现时报告必须标明，不把 HEAD 当作完整实现标识。报告不保存密钥、服务 token 或模型供应商完整异常响应，也不保存原始内部思考。

同一保留集每个用例至少运行三次。比较提示词或工具修改时，固定模型与端点参数、数据快照、评分器和预算；更换模型时单独标注变量，不把两种实验混为一谈。

当前评估产物保存在已忽略的本地工作目录；需要提交的验收摘要经过脱敏后进入 `docs/review/`。清理旧运行数据不要求转换旧评估产物；历史报告按原日期保留事实属性。

### 14.6 初始验收目标

以下是项目目标，尚未实测，不是已有结果：

- 硬性边界测试全部通过：无实际越权、无业务派单写入、无超预算调用、无取消后回写。
- 确定性可解保留用例的任务完成率至少 90%，并报告逐例三次重复的完整分布。
- 引用合法率 100%；任何伪造引用、错条目引用或跨用户引用均阻断验收。
- 关键事实支持率目标 100%；一旦发现无依据的确定性成功、失败或重发断言，先修复后重评，不以平均分掩盖。
- 证据不足、权限撤销、来源变化等用例按其预期结果判定，不强求形成确定原因。
- 每次运行均在第 9 节调用与时间边界内进入可读终态；模型请求超时后的底层取消和资源释放另有集成证据。
- 用量完整时提交 token 和费用统计，用量缺失时提交明确缺失率。时延和费用先建立基线，不虚构目标硬件上的生产指标。

## 15. 安全、隐私与权限的具体边界

工具白名单由程序静态注册，只有第 7 节五个查询工具。不得注册 `dispatch_submit`、派单确认/重试、规则发布、账号维护、SQL 执行、网络任意 URL 或文件读写工具。

每次工具调用、证据读取和报告读取都重新解析当前账号状态，验证租户、报表、公司以及所绑定清单的范围；不能依赖创建时复制的管理员布尔值持续授权。撤权或禁用后终止调查并拒绝读取报告。服务间身份仍由可信应用注入。

只读是指不修改业务清单、规则、源报表、业务幂等账本和派单结果；调查自己的任务、步骤、配额及证据需要持久化。对“零业务写入”的验收使用明确业务表白名单和前后状态比较，不把调查审计写入误判为违规。

沿用现有敏感信息处理能力，并增加调查 DTO 字段白名单。提示词、模型参数、错误报告及前端展示均不包含会话凭据。条目说明、错误消息及规则文本以不可信数据处理，工具不能从其中提取并执行新的指令。

最小集成回归必须包含：单据摘要要求调用派单工具、错误文本要求访问其他清单、规则说明伪造管理员身份、模型伪造证据号。预期均为无越权查询或写入，并输出受控失败或有依据报告。

## 16. 失败与恢复矩阵

| 事件 | 任务与模型处理 | 页面与再次操作 |
| --- | --- | --- |
| 模型配置缺失或工具能力不支持 | 创建前配置检查拒绝，或首轮失败为 `MODEL_UNAVAILABLE`；不替换语义来源 | 修复真实配置后显式重新分析 |
| 模型输出工具参数错误 | 有界错误回传，预算内允许模型修正；超限结束 | 展示参数失败步骤和终态 |
| 工具查询空结果 | 返回明确空集合或缺失状态，不伪造事实 | 报告证据不足或无相应事件 |
| MCP 超时/不可用 | 记录查询失败，不等同业务失败；剩余预算内可再查一次 | 合法报告为 `PARTIAL`，明确缺少核对证据 |
| MCP 返回权限拒绝 | 停止后续调用，`FAILED/ACCESS_REVOKED` | 不展示已失去权限的报告和证据 |
| 清单执行版本或条目状态变化 | 停止新查询，按时点保存部分报告或明确失败 | 提示重新分析当前状态 |
| 重复工具无进展 | 达阈值停止收集，在预算内生成部分报告 | 展示无进展原因 |
| 超出总时限 | 取消在途调用并禁止迟到回写；有合法结果则部分完成，否则失败 | GET 可读取终态，无自动再发起 |
| 页面断线或刷新 | 已认领任务继续，保存已完成步骤 | 只恢复 GET 轮询 |
| 用户取消 | 立即撤销认领权，尽力取消在途 HTTP；不能保证供应商不计费 | 展示 `CANCELLED` |
| 工作进程退出/租约失效 | 回收为 `INTERRUPTED`，不自动重放模型请求 | 用户可读取已有步骤或发起新运行 |
| 最终报告校验失败 | 最多一次修复；仍失败则不保存可展示报告 | 展示 `REPORT_INVALID` 和可读步骤 |
| Redis/数据库不可用 | 不绕过配额或持久化保护，不开始新调用 | 依赖恢复后查询或显式重试 |

## 17. 实施顺序与验收清单

### M1：契约、初始化和可控循环

产物：调查 DTO、五个工具契约、报告 Schema、最新空库表结构、权限策略和显式工具循环。

完成条件：字段注释完整；空库初始化通过；伪造条目/工具/引用被拒绝；多工具消息配对、预算、重复调用和无工具报告生成通过可控回归。模型调用在事务外执行，无未计数 SDK 重试。

### M2：真实模型与业务只读工具

产物：真实工具调用能力探针、清单/规则/事件读取、HTTP MCP 核对和最小真实调查报告。

完成条件：对实际端点验证工具请求及回传；至少覆盖明确失败、结果未知、远端已成功三个独立业务场景。验收日志能关联模型运行、MCP 调用和隔离库事实；业务表零调查写入。该阶段开始收集评估基线。

### M3：任务生命周期和页面

产物：持久任务、租约、取消、来源指纹、前端抽屉与恢复。

完成条件：丢失提交响应使用原键；刷新不新增任务；两个工作线程不会重复认领；取消/失租后迟到响应不能回写；跨账号响应不显示；10 条上限和分页覆盖清晰。组件逻辑、生产构建和真实浏览器链路分别记录。

### M4：独立评估与对比报告

产物：40 个场景、开发/保留集、确定性评分器、三次重复评估、质量/时延/用量报告。

完成条件：第 14 节目标经实际运行验证；报告区分四层证据和跳过原因。错误用例进入回归，修改后重新跑受影响保留集；不得把同一套调优语料的通过率描述为独立泛化准确率。

### M5：交付整理

产物：当前操作说明、工具和接口文档、表结构字典、环境参数说明、代码阅读顺序和脱敏验收摘要。

完成条件：README 明确新增功能何时由“待实施”转为“已实现”；只引用实际执行结果。历史数据升级、旧协议转换和旧版本回滚不列入交付要求。

## 18. 待验证的实现风险与决策

| 风险 | 已选方案 | 需要的证据 |
| --- | --- | --- |
| 端点工具能力不同于结构化输出能力 | 使用当前版本工具协议，先跑真实能力探针 | 实际请求与脱敏响应，不依据模型名称推断支持 |
| 框架内部循环隐藏调用次数 | 应用控制循环，关闭内部自动执行和未计数重试 | 传输层计数与运行步骤一致 |
| 旧 MCP 65 秒时限占满调查预算 | 调查专用有界读取，保持派单传输语义独立 | 真实超时、底层取消及线程释放测试 |
| 追溯包含会话和大量冗余数据 | 使用条目事实快照和有界事件，不直接发完整追溯对象 | DTO 白名单、体积及注入回归 |
| 本地与远端事实不在同一事务 | 分别记录时点，校验当前来源，冲突显示部分完成 | 并发改变状态的确定性交错测试 |
| 合法引用仍可能解释错误 | 枚举事实校验，加任务评估与人工抽查 | 逐条事实支持率和错误案例 |
| 调查线程挤占派单容量 | 专用线程和配额，模型调用不持有长事务 | 同时派单与调查的集成验证，生产容量仍待实测 |
| 未知 token 用量产生虚假成本 | 缺失为 null，记录完整率和价格配置 | 目标端点实际用量 metadata 样本 |

以上决策足以开始实现；预算数值属于可测量后调整的设计参数。调整必须保留评估记录，不将配置目标写成已验证能力。
