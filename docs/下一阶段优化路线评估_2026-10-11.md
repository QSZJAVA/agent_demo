语义精度改进应从下面几个共同能力入手。

1. **把业务定义从长段说明扩展为可校验的元数据。** 当前 `FieldInfo` 只有名称、类型和说明，报表已有别名，客户已有稳定身份。下一步补充字段别名、业务定义、枚举值、单位、币种来源、可用运算、敏感等级、指标口径和生效版本。例如“销售额”“已收款”“应收余额”只有在业务定义确实一致时才能作为同义词；“未处理”可能对应多个状态，应由词典和当前业务域确定候选，再由用户消歧。词典维护需要冲突检查、试算和版本发布，用户一次纠正不能自动变成全租户规则。

2. **明确时间与数值的上下文。** 当前规划输入已提供上海时区的当天日期，但完整企业时间语义还需要参考时刻、租户时区、自然月/财务期间、工作日历，以及“截至”“本期”“近三个月”等口径。金额要区分元、万元、币种、含税与未税；缺少来源字段或可信定义时先澄清。模型输出结构化含义，程序校验类型、区间和单位一致性，不能从孤立关键词直接生成另一套业务意图。

3. **把已有语义证据展示给用户。** 当前查询卡片已展示范围和筛选，下一步增加条件来源、继承/新增/撤销差异，以及明确的字段修改入口。例如用户先要求“A 公司上月销售单，金额不少于 10 万元且不超过 20 万元”，随后说“上限改成 15 万元，其他不变”，界面应显示仅上限改变，公司、时间和下限保留。若以 2026-10-11、Asia/Shanghai 为参考，上月显示为 2026-09-01 至 2026-09-30。该示例是拟新增交互的验收场景，不宣称本次已执行。澄清优先提供当前有权查看的少量实体或口径选项，并保留已确定条件。

4. **让上下文按业务状态组织。** 继续使用现有成功查询、已展示对象、当前焦点与未完成状态，给可恢复的条件和结果绑定版本及来源。话题切换、回到旧查询、刷新、撤销条件和权限变化需要统一处理。较早文本不能恢复已撤销条件，也不能把旧预览变成新建单依据。大目录可按当前权限检索相关字段与术语，同时保存召回不足的标记；检索仅提供模型解释所需的上下文，不把候选排序当作最终身份或意图。

5. **保留独立复核，并度量它的收益与共同错误。** 当前正常轮次是目标判断、规划、完整复核三次模型调用，语义阶段上限分别为 2、3、3 次；底层网络行为另计。三个阶段使用同一模型配置，分开上下文能减少草稿牵引，但不能排除共同误解。用独立业务标签、确定性边界检查和真实结果核对验证质量。优化先从阶段计量、重复上下文、授权目录规模和结构化交互入手；自然语言的新目标或条件变化仍须完整复核。

6. **形成纠错到评估的闭环。** 收集用户标记“理解错了”的请求、当时有效上下文、确认后的正确含义及失败分类，经脱敏和人工业务审核进入回归集。开发集、日常回归集和封存盲测集分开管理；已经用于修改提示或代码的样本不再作为独立盲测证据。已有主集、保留集、数值专项及调查评估可以继续复用为回归资产，另补未参与调优的新语料。

业务词典也决定知识检索如何落地。第一阶段优先检索目录、字段、指标和实体定义；制度类知识问答随后接入带版本和权限的文档。模型回答应引用实际来源及生效时间，不能把制度描述当成已经完成的 ERP 操作。向量检索、额外模型路由或微调适合在错误分布和受控对比证明收益后投入，实施时继续保持现有技术栈约束。

查询性能与数据一致性需要作为同一项设计处理。

当前 `BusinessReadService` 对单次读取采用 `REPEATABLE_READ`，已经具有事务内一致性；`BusinessQueryEngine` 在完整有界事实集上计算准确结果。扩展时，将通过校验的条件、排序和聚合下推到业务服务及数据源适配器，按租户、公司、报表和查询类型设计索引。不要让模型生成可直接执行的 SQL。十进制、空值、大小写/排序规则、日期和 AND/OR 语义必须与接口契约一致，避免数据库下推后同一请求产生不同集合。

为分页、导出、对比和 Top N 引入明确的查询运行标识，关联查询定义、目录与权限版本、观测时间及来源快照/水位。当前跨分页请求不能仅凭单次事务保证持续使用同一数据时点。来源无法提供稳定快照时，应如实展示刷新时点和一致性边界；多个外部来源不能自动宣称具有全局事务快照。执行派单仍在当前来源事实与版本上重新核验，查询快照不授予执行权。

普通查询卡片的翻页目前会发出新的连续对话并经过模型。可以为明确的按钮操作增加结构化接口，复用已经通过复核的查询定义，重新验证当前权限、查询版本和允许的页码变化。这能减少确定性操作的等待；任何通过自然语言改变范围、条件或目标的请求仍走原有规划与独立复核。

功能完整性的下一步应围绕重复使用和业务闭环展开。

常用查询保存的是当前有效的查询定义、命名和可见范围，而非永久授权。相对时间需区分“每次运行重新计算上月”和“固定某一期间”。导出应读取完整且明确的结果范围，使用异步任务、精确金额、受控下载和到期清理；下载时复查权限，文本单元格不能被表格软件解释成可执行公式。查询对比需要记录两次的范围、口径和数据时点，避免把条件变化误说成业务增长。

现有汇总已支持按币种合计、状态分布及单字段计数。新增多维统计、同比环比、逾期和阈值提醒前，先定义字段和指标：没有到期日就不能准确计算逾期，没有可比较期间和币种口径就不能生成可信增长率。图表与文字应引用同一确定性统计结果，模型负责解释，不计算或补造缺失数值。

“我的任务”可扩展为任务入口，涵盖派单、核对、异常调查和导出，各自保留已有状态机与执行约束。优先做站内通知、未读状态、异常原因分类和下一步入口；外部通知渠道在明确对象、内容范围、频率及订阅授权后接入。提醒不会自动确认、重试或审批，重复事件也不能反复发送同一通知。

真实工单应先接入只读进度与历史，再按业务需要增加催办、转交、撤回、审批等独立操作。每种写操作都需定义操作者权限、可操作状态、业务版本、确认内容、幂等键和结果核对能力。当前 `WorkOrderProvider` 只读接口是合适的接入边界，新增写入不应混入它的查询职责。

外部 ERP 的提交、回查与状态同步复用当前稳定请求号和执行版本。对于新增异步事件链路，可按实际需要增加事务事件记录、接收去重、来源版本和对账账本，处理重复、乱序、延迟与丢失。消息重复投递下的业务去重依赖真实接收方契约，不能仅凭本地任务表宣称跨系统恰好执行一次。结果未知进入核对或人工处置，不能自动推定失败后重发。

| 第四阶段：生产准入 | 目标环境部署、容量和多实例故障验证；监控告警；备份恢复；发布与值守流程 | 在约定负载下达到实际 SLO；告警确实送达；恢复演练达到约定 RPO/RTO，并核对在途任务和外部提交结果 |

正式身份与 ERP 的接口调研可与第一、二阶段同时推进；真实写入试点必须等其确认、幂等和核对契约齐备。时间安排取决于团队、业务范围和外部环境，当前证据不足以给出可靠总工期。

第一阶段建议收敛为四个可评审交付物：一份统一任务语义评估报告，一个公司/字段/单位/状态词典维护入口，一套条件差异与澄清交互，一张按阶段展示耗时、修正与失败原因的诊断页面。实现分别主要落在 `ModelAssistantPlanner` 与其调用封装、目录和字段元数据、查询卡片/会话状态、运营统计及评估工具。目录和提示仍使用共同契约，避免另建一套与现有状态流转冲突的解释流程。

质量验收建议采用以下口径。数量和百分比均为拟议试点目标，需在真实基线测量和业务审核后确定，不是当前达标声明。

| 维度 | 建议验收办法 |
| --- | --- |
| 独立泛化 | 建立约 300–500 个业务审核任务，包含单轮与完整多轮；按会话、实体和表达来源隔离开发/盲测，关键任务至少三次独立运行并恢复受控初始状态 |
| 语义正确性 | 核对动作、业务域、公司/报表、实体、运算符、边界、否定、条件继承/撤销、展示类型、最终数量及实际结果；核心支持范围的任务通过率可先以 98% 为试点目标 |
| 澄清质量 | 歧义样本的正确澄清召回率可先以 95% 为目标，明确且能力范围内的请求不必要澄清率以不高于 5% 为目标；两者单独统计，不能靠一律拒绝提高安全评分 |
| 高风险边界 | 发布门禁样本中出现越权、未确认执行、对象替换、错误金额或未知结果盲目重发即失败；有限样本零违规不能解释为总体风险为零 |
| 稳定性 | 同一句不同表达、同名对象、并列极值、空值、无结果、大额、跨日/月、长对话、话题切换、刷新、撤权/恢复和外部状态变化均有覆盖 |
| 延迟与费用 | 按阶段记录 p50/p95/p99、调用/修正次数、实际 token 与费用完整性；区分模型、业务读取、排队及渲染。先测固定负载基线，再设改进目标 |
| 结果依据 | 业务标签和预期结果应有独立依据，不能仅以模型自评或同一查询实现生成的结果作为正确性证明；每轮冻结模型、Schema、提示、词典、评分器与数据版本 |
| 发布验证 | 程序与状态机、真实模型回放、真实认证 HTTP MCP、真实浏览器分别记录；在可信流水线环境增加真实链路发布门禁，保留失败、未执行及跳过事实 |

当前调查模块已记录部分 token 与费用，不必重新建设全部计量；应统一接入普通助手的目标、规划与复核阶段。`BusinessMetrics` 的解析采样目前缺少公司归属，因此明确不可用；新增诊断要定义当前授权范围及多公司/未解析请求的可见性，不能把租户全量采样直接展示给受限管理员。费用缺少实际计量或可信价格时继续标注未知。上一轮恢复查询记录的 10305 ms 仅为一个样本，不能用于推导 p95 或生产承诺。

生产准入还需完成几项现有功能不能代替的验证：正式身份到租户、公司、报表及操作权限的服务端映射；凭据轮换和实际 TLS；应用与迁移数据库账户的最小权限；镜像构建及目标环境升级；多实例租约认领、旧实例迟到回写、限流与队列公平性；监控业务错误码及 SSE 失败；备份恢复后对稳定请求号、在途任务和外部业务流水的核对。已有配额、就绪探针、审计和 Compose 文件可复用，告警送达、容量与恢复必须通过实际演练取证。

本阶段继续保留现有前端及依赖版本，Demo 账号生命周期问题仍按约定暂缓；正式身份接入单独完成生产验收。代码与元数据重构面向最新目标结构，不增加历史协议兼容。任何 Demo 重建或会创建独立数据库的验证，必须先核实目标并取得针对数据操作的明确授权，固定演示库仍为 `report_demo`。本次路线评估没有执行这些操作。
