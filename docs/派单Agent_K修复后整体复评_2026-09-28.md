## L1：布尔下推会排除本来命中的记录

位置：`backend/src/main/java/com/example/report/catalog/query/RuleSqlPredicate.java:47–49、61–65`；`StandardReportAdapter.java:256–258`。

触发条件：标准报表把一个 TINYINT 列映射为 `boolean`，源表存有正数 2，规则为 `eligible == true`。当前配置校验允许此映射，发布探测只核对列存在，没有验证物理列为 BIT 或具有 0/1 约束。MySQL 的 TINYINT 接受值 2。

两条路径：

- 试算不做规则下推，JDBC `ResultSet.getBoolean` 把 2 转为 true，Aviator 判定命中。
- 正式预览先由 RuleSqlPredicate 把 true 作为布尔参数绑定，生成 `eligible = :rule0`，在 MySQL 中相当于与 1 比较。值 2 被提前过滤，后续 Java 复核已经看不到它。

实库复现：隔离表有三条待派单记录，eligible 分别是 1、2、0。真实 StandardReportAdapter 配置解析和 probe 通过；直接读第二条事实得到 Java true；同一 DispatchCandidateService 下 `dryRun` 命中 2 条，`findCandidates` 仅返回值为 1 的 SO1，漏掉 SO2。

影响：合法接入的布尔字段可能出现试算与正式预览不一致、应派记录漏出清单。没有证据表明现有三张演示报表正好含此数据，不能声称演示数据已经漏派；问题针对目录化接入允许的源字段类型和值。K2 的有界试算没有引入这种 SQL 转换，它只是让该差异更容易观察。

建议：只有能证明 SQL/JDBC/Aviator 类型语义一致的字段才允许下推。未验证物理类型和取值约束时，布尔比较回退 Java 求值；或者统一转换并补充真实数据库回归。覆盖 0、1、2、负值、NULL、各比较操作，不应只测返回 SQL 文本。回归要求是试算与正式候选在同一数据上语义一致。

诊断：`docs/review/RuleBooleanReviewProbe.java`；输出保存在 `backend/target/review-l/boolean-probe.log`。使用 UUID 隔离库 `review_l_<UUID>`，结束后校验当前数据库名称并仅删除本次库，没有读写演示业务表。

## L2：旧试算结果会被当成当前规则的结果

位置：`frontend/src/views/RuleAdmin.vue:217、242–248`，展示位置 87–94 行。

已复现：

1. 对表达式 A 试算成功，显示命中 1 条；修改为表达式 B 后再次试算，接口返回 422。runDryRun 只在 finally 清理 loading，没有清空或标记旧结果，页面仍显示 A 的命中数。K2 超过 10,000 条的保护会触发这条正常错误路径。
2. 销售规则试算仍在请求中，关闭并打开费用规则编辑器。openEditor 虽然清空了结果，迟到的销售响应仍无条件赋值，导致费用规则编辑器显示销售试算结果。

影响：管理员可能以旧结果评估当前规则。结果不会自动执行派单，本轮也未证明发生错误规则发布，因此列为 P2。

建议：试算结果绑定报表、公司、表达式和请求序号；输入变更、关闭/重新打开编辑器时使旧结果失效；失败时清空或明确标注旧结果不适用于当前输入；只接收当前请求的响应。

诊断：`node docs/review/rule-editor-review.probe.cjs`。执行当前组件真实方法，API 使用替身；没有进行浏览器端到端操作。
