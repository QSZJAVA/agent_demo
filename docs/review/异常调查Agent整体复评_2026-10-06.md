## 新发现

### N1 / P2：批量核对的后续参数错误会丢失前面已经取得的明确结果

位置：[InvestigationTools.java](../../backend/src/main/java/com/example/report/investigation/InvestigationTools.java)，第 97～104、119 行。

`dispatch_lookup` 在逐条循环内部检查可核对次数，整批完成后才保存证据。复现顺序如下：

1. 查询 I1 得到 SUCCESS，I1 按设计禁止再次核对。
2. 模型请求 `[I2, I1]`。程序先真实执行 I2 查询，得到 SUCCESS 并将其计数置为不可再查；随后遇到 I1 的次数限制，抛出可恢复参数错误。
3. 整批证据尚未保存，I2 的成功结果没有进入工具响应或证据集合。
4. 模型修正参数后单独查询 I2，又被“同一条目最多核对两次”拒绝，已取得的成功事实永久不可引用。

离线复现调用实际工具实现，只有 MCP 返回值和仓储使用受控测试替身。结果为：合成远端查询实际发生 2 次，I2 计数为 2，I2 证据不存在，纠正后的查询仍被拒绝。未连接真实模型、业务 MCP 或数据库。

影响：一个可以修正的参数错误会消耗其他合法条目的查询机会，并丢掉明确成功或失败事实，导致调查无法给出本可核实的结论。只读保护没有被突破，但事实完整性受到影响。

建议：在任何远端查询之前验证整批引用的剩余核对资格；或逐条保存有效结果，并按条目返回错误。增加“新条目在前、已结束条目在后”的反例，验证纠正参数后能取得新条目证据。

### N2 / P2：同一原归档仍能被两个续跑进程重复执行

位置：[InvestigationEvaluationJournal.java](../../backend/src/test/java/com/example/report/investigation/InvestigationEvaluationJournal.java)，第 54～71 行；[InvestigationLiveEvaluationTest.java](../../backend/src/test/java/com/example/report/investigation/InvestigationLiveEvaluationTest.java)，第 30～34 行。

`readCompleted` 只在读取原检查点时持有原归档锁，返回后立即释放。续跑随后创建另一个目录，并只锁住新目录；原归档的检查点保持不变。因此第二个进程再次对同一个 `ResumeFrom` 路径操作时，仍能读到相同的未开始题次，创建自己的归档并再次执行。

离线复现创建计划 `{one:1,two:1}`，原归档只完成 `one:1`。第一个续跑保持打开并开始 `two:1` 后，第二个续跑仍成功读取原归档并开始同一个 `two:1`。该复现只操作本仓库 `.runtime` 下的专用目录，没有产生模型费用。

影响：当前锁能保护同一归档的检查点写入，但不能保证同一续跑来源仅有一个执行者。重复启动续跑会重复模型调用和费用，也违背“已开始题次不自动重放”的预期。

建议：在读取原归档前取得续跑来源的执行权，并持有到整个续跑结束；记录续跑子批次或已消费的题次，避免后续再次使用同一父归档重放已执行部分。回归须启动两个续跑者，而不只是验证原批次仍打开时不能读取。

### N3 / P2：基线对比忽略实际模型请求路径变化

位置：[compare-investigation-evaluations.cjs](../../tools/compare-investigation-evaluations.cjs)，第 14 行。

模型配置已记录 `completionsPath`，续跑校验也已经检查它；对比工具的控制变量列表仍未包含该字段。相同 `endpoint` 是相同基础地址，不等于相同的模型请求地址。不同路径可能路由到不同服务或部署，不能作为固定模型端点的对照实验。

使用两份离线产物，除 `completionsPath` 从 `/v1/chat/completions` 改为 `/v2/another-provider/chat/completions` 外，其余配置、题次和事实摘要完全相同。实际对比脚本输出 `comparable=true`，`changedControls=[]`。

建议：对比与续跑共用明确的端点控制变量定义，将 `completionsPath` 纳入对比；同步核查新增的业务时区等影响输入事实的配置，避免两处名单继续分叉。对路径变更的测试应断言不可直接比较。
