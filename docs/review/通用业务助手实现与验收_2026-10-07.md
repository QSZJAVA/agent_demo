# 通用业务助手实现与验收

实施开始于 2026-10-06，验收完成于 2026-10-07，时区 Asia/Shanghai。当前状态：本轮约定范围内的实现、完整程序回归、真实模型回放和浏览器恢复验收完成；结论只覆盖以下已执行场景。

对象为 V1 / 1.0.0、`real,mcp`、`agent.semantic.mode=active`。真实模型和认证 HTTP MCP 继续使用当前配置；不引入 RAG，不升级前端依赖，不修改既定账号生命周期范围。用户已授权本轮创建并清理临时测试库，未授权且本轮没有清空或重建 `report_demo`。

## 实现范围

| 目标 | 实现及业务边界 |
| --- | --- |
| 通用入口 | ModelAssistantPlanner 生成严格计划，区分只读查询、派单规划、帮助和澄清；现有派单使用原 V1 协议及确认入口 |
| 报表数据 | 从授权目录读取全部来源状态，包括已派单和不符合派单规则的记录；支持字段条件、排序、分页和统计 |
| 派单数据 | 查询持久清单条目；普通用户仅看本人，管理员仍须满足公司和报表权限；待确认清单过期按查询时点展示，不因查询更新业务状态 |
| 工单进度 | 通过独立 WorkOrderProvider 返回固定环节、固定演示审批人和多状态示例；明确区分固定示例与实际演示成功派单关联 |
| 工单总结 | 状态分布、当前审批人、分币种金额、单项办理过程及结果由接口事实确定性生成，不由模型补造 |
| 连续对话 | 记录成功查询、当前页有序引用及持续业务焦点；帮助/澄清不清除焦点，跨轮敏感样式标识通过临时占位符恢复 |
| 恢复及权限 | 卡片通过可靠事件持久化，刷新可恢复；历史公司和报表范围累计保存，权限撤销后不能从历史或管理员追溯泄露结果 |
| 派单保护 | 普通查询不改变旧预览及勾选，但跨入普通查询后，即使失败，也必须重新取得候选再生成清单；确认、幂等、租约、规则和执行版本继续生效 |
| 有界处理 | 模型输入 128000 字节、模型计划 24000 字符；来源最多 100000 行/120 秒，保留事实 16 MiB，展示结果 240000 字节；超限整体失败 |
| 文档图表 | 更新 README、查询说明、MCP 契约、基线检查和十页流程图生成器，同步 HTML/SVG/Mermaid/draw.io 产物 |

查询条件仍在受限完整读取后处理，尚未普遍下推来源数据库。这是有明确预算的 Demo 实现，不代表生产大数据量查询性能已验收。无币种声明的金额不合计；NULL 不满足普通比较，排序时空值始终置后。

## 已保留的中间失败及修复

1. 最初前端测试夹具没有注册新增查询组件，导致装配失败；补齐夹具后原有 91 项通过，随后加入查询卡片测试，前端共 96 项。
2. 初次通用查询真实回放为 [23/23](business-assistant-2026-10-06/query-initial.json)，首组独立问法为 [5/7](business-assistant-2026-10-06/query-holdout-initial.json)：单工单办理小结被当成集合统计，状态分布请求被错误缩为两个状态。明确详情/统计/过滤语义后重新运行，不删除原失败。
3. 第一次扩展查询三组共 [23](business-assistant-2026-10-06/query-round1.json) + [7](business-assistant-2026-10-06/query-holdout-round1.json) + [10](business-assistant-2026-10-06/query-reserve-round1.json) 步全部通过，但同轮旧派单回归失败，不能因此宣称整体通过。
4. 旧派单首轮为 [11/14](business-assistant-2026-10-06/dispatch-fields-round1.json)、[10/20](business-assistant-2026-10-06/dispatch-holdout-round1.json)、[5/8](business-assistant-2026-10-06/dispatch-reserve-round1.json)。新路由曾把选择操作改成正向查询，澄清丢失焦点，派单追问又误用了普通查询上下文检查，导致当轮或后续范围不符。
5. 修复持续焦点与最近尝试分离；查询上下文条件只约束只读分支；增加只拒绝、不生成意图的选择路由一致性校验，并共用一次修正预算。补充成功/失败查询转派单、澄清恢复、历史范围及管理员追溯测试。
6. 一项历史恢复测试在展示投影完成前断言失败。可靠事件先提交、投影按顺序异步补写是既有契约，改为有界最终恢复断言；整组会话集随后通过，未把 SSE 卡片显示当作持久化证明。
7. 补齐长字段字节预算、NULL 升降序置后、只读清单过期展示及脱敏标识跨轮恢复。模型传输测试验证实际 HTTP 请求的原生 Schema、thinking 关闭和无工具执行权。
8. 下一轮新增查询仍为 40/40，原派单为 14/14、19/20、8/8；唯一失败已正确拒绝且未扩大范围，但缺少“未应用修改”的说明。统一错误提示后保留原断言重新验收。
9. 第八轮完整程序回归通过后，七组真实模型回放为 83/84。失败见[查询验收记录](business-assistant-2026-10-06/query-main-acceptance.json)：空派单查询后的状态汇总被改查报表；人工核查又发现前一步把“我”错误当成创建人姓名。增加服务端计算的本人归属字段、按域提供状态说明及同域追问校验；主用例增加本人归属断言，另补六步中英文问法，没有删除旧用例或降低预期。
10. 最终构建的首批回放中，配置的模型端点发生连接重置，未取得 HTTP 响应。[连接错误摘要](business-assistant-2026-10-06/model-connection-outage.json)、[查询失败](business-assistant-2026-10-06/query-reserve-connection-failure.json)及[派单失败](business-assistant-2026-10-06/dispatch-fields-connection-failure.json)保留原结果。连接恢复后，在不修改代码、构建包或语料的前提下完整重跑受影响的四组；这些失败不算语义正确，也没有用关键词或预置样本替代真实模型。

## 仍然明确的边界

工单环节和审批人是用户要求的固定演示实现，真实工单系统、真实 ERP、正式统一认证没有在本轮接入。审批、催办、修改工单没有实现写入能力。生产并发、时延目标、容量、灾备及外部部署继续需要实际验收。

有限用例通过不能保证任意自然语言都成功；真实模型失败、安全拒绝和业务正确必须分别记录。源码、构建包和最后实际执行结果以最终归档为准，历史失败不得由后续成功覆盖。
