# 项目整体生产就绪评审

日期：2026-10-06（Asia/Shanghai）。对象：当前工作区 V1 / 1.0.0，固定演示库 `report_demo`。本轮只评审，未修改运行代码、部署配置或数据库；未新建测试库、未确认派单、未调用真实模型。结论依据当前代码、离线回归与探针，以及明确标注日期和范围的历史证据。

## 结论与适用范围

项目已经达到“有较完整业务保护的工程原型”，适合演示、业务方案验证及准备单企业受控试点；**尚不满足直接承接真实客户、长期运行和真实 ERP 写入的生产上线条件**。

主要差距集中在业务事实变化保护、结果完整性、真实系统接入、数据出站控制和运行验证。继续增加提示词或功能页不能代替这些工作。代码数量、测试数量和十四步演示回放不能换算成可信的“生产完成百分比”。

| 应用目标 | 当前判断 |
| --- | --- |
| 学习、演示、内部方案验证 | 已有较完整能力；保留当前明确限制 |
| 单企业、少量业务、人工核对的受控试点 | 可以进入上线准备；先解决下述 P1 项、完成真实接口及环境验收 |
| 单企业正式生产、持续真实写入 | 未就绪；还缺生产运维、容量、故障和恢复证据 |
| 多客户共库、多租户 SaaS | 未就绪；当前有数据权限隔离，但身份和后台工作线程仍带单租户部署假设 |

账号生命周期已知问题和前端升级仍按 [AGENTS.md](../../AGENTS.md) 暂缓，不计为本轮 Demo 交付阻断，也没有执行修复。真正上线仍需接入正式身份系统并落实授权生命周期；这些事项未因“暂缓”而变成已经完成。

## 已具备的工程基础

当前设计将真实模型限制在结构化意图解析；模型不直接执行 SQL，也不能凭回复确认派单。字段和可用能力来自授权目录，Schema、原文证据、实体范围与服务端校验共同约束输出。

业务侧已有租户、公司及报表权限复核；预览和清单持久化；复合记录标识；明确确认；幂等请求号；认领租约；执行版本；失败重试与未知结果核对。HTTP MCP 业务服务会复核已确认清单、条目及执行版本，在事务和来源行锁内检查业务状态。异常调查使用独立预算、只读证据及引用校验，不能代替派单授权。

两模块聚合 CI、独立 MCP 服务编排、认证 MCP 就绪检查、持久派单任务和前端恢复均已实现。早期报告中“CI 没有业务模块”“没有双服务编排”“派单只能同步等待”等结论不再直接适用于当前代码。仍不能把这些实现与程序回归等同于完整生产环境验证。

## 优先处理的问题

### R1 / P1：执行前未保护用户筛选字段的变化

位置：[BusinessDispatch.java](../../business-service/src/main/java/com/example/business/BusinessDispatch.java)，63–68、79–96 行；[DispatchService.java](../../backend/src/main/java/com/example/report/dispatch/DispatchService.java)，480–483 行。

当前业务服务检查提交的字段快照与已确认清单一致，然后复核当前公司、稳定客户 ID、规则和待派单状态；它没有把当前来源的金额、日期等字段与已确认快照比较，也没有重新执行用户的字段条件。

隔离内存探针用已确认金额 **50,000**、当前来源金额 **128,000**、业务规则 `amount > 20` 验证，当前复核谓词仍允许处理。若用户之前要求“只保留不超过 100,000 的记录”，来源变化后便可能超出用户理解的操作条件。

这与当前文档声明的“按冻结快照选择、不实时重新执行所有自然语言条件”一致，属于生产业务语义与一致性缺口；不是已经证明发生了真实误派单。探针中的 JDBC 与来源写入均为测试替身，只证明现有判断路径允许该变化。

上线前必须定义一种明确契约：绑定来源行版本/关键字段摘要，变化则失效并重新确认；或保存确定性筛选条件，并在业务行锁内重新求值。不应在真正写入时再让模型解释一遍自然语言。若业务明确授权“对已选定记录身份操作，接受字段随后变化”，也必须在确认契约和界面中清楚表达，不能由实现默认决定。

验收：金额跨阈值、日期跨边界、字段从空变非空、预览后改单、确认后等待期间改单，均有明确拒绝或重新确认行为；重试仍沿用稳定请求号。

### R2 / P1：规则求值失败导致结果不完整，却仍作为正常预览返回

位置：[DispatchCandidateService.java](../../backend/src/main/java/com/example/report/rule/DispatchCandidateService.java)，119–131、184–189 行；[PreviewPayload.java](../../backend/src/main/java/com/example/report/agent/PreviewPayload.java)，35–46 行。

普通查询中的规则求值异常被捕获，出错行按“不命中”处理，只汇总日志；预览载荷没有相应的不完整标记或错误行数。管理员试算有 errorCount，但普通业务查询没有同等信息。

探针用两条记录验证：一条产品名正常、一条产品名为空，规则求值失败一条，调用方正常得到一条候选而没有失败信号。现有 `DispatchCandidateServiceTest` 也明确测试并接受这一行为。

生产影响是漏处理和“查询到的就是全部”的错误印象，尤其在定时业务、财务对账或用户说“剩下的全部处理”时。拒绝把未知记录写入是必要保护，但求值失败不能被描述为完整查询成功。

建议返回完整性、错误计数及可定位的脱敏记录引用；视业务要求阻止基于不完整结果建单，或要求用户明确接受部分范围。验收应区分“零匹配”“来源数据错误”“来源查询失败”。

### R3 / P1（多租户共库条件）：后台任务认领没有租户归属限制

位置：[DispatchJobService.java](../../backend/src/main/java/com/example/report/dispatch/DispatchJobService.java)，202–205、226–227、244–247 行；[PermissionService.java](../../backend/src/main/java/com/example/report/permission/PermissionService.java)，39–40 行；[IdentityStore.java](../../backend/src/main/java/com/example/report/security/IdentityStore.java)，31、35、47–48 行。

身份存储绑定一个配置租户，但派单工作线程从全表认领 QUEUED 任务，随后按本实例租户解析 userId。若为不同客户部署两个实例、共享同一业务库，一个实例可以认领另一租户的任务，再因租户不匹配将其写成 FAILED。调查队列也采用全表认领，需一起审查。

该项依据明确代码路径，未在本轮建立多租户数据库或进行跨实例实测；**不宣称当前单租户环境发生了跨租户泄露**。当前单企业部署不因此自动不安全，但不能仅凭表里有 tenant_id 就承诺共库多租户生产支持。

建议先确定部署模型。单企业专有部署保持清晰边界；共库多租户需要租户感知的身份解析、认领范围或统一可信工作池，并验证公平性、配额、服务凭据隔离及跨租户故障影响。

### R4 / P1（真实敏感数据条件）：现有脱敏不是完整的模型出站控制

位置：[SensitiveData.java](../../backend/src/main/java/com/example/report/operations/SensitiveData.java)，17–21、39–49 行；[ModelIntentParser.java](../../backend/src/main/java/com/example/report/semantic/ModelIntentParser.java)，53、73、79–81 行。

自由文本主要识别手机号、证件号和邮箱，JSON 特定字段名单提供额外脱敏。任意客户商业信息、自由文本中的口令/密钥样式及其他敏感标识没有通用阻断机制。探针使用完全合成的密钥样式字符串，确认它会保留在模型输入文本中；没有使用真实秘密，也没有发送网络请求。

需要在真实数据接入前明确允许出站字段、禁止内容、供应商保留策略、日志保留和租户配置。对明确禁止的内容阻断或稳定占位，不以模型提示词代替出站策略。当前存在脱敏措施，但不能因此宣称已经完成生产数据治理。

### R5 / P2：扫描与执行有界，但没有目标容量证据

位置：[McpReportQueryAdapter.java](../../backend/src/main/java/com/example/report/mcp/McpReportQueryAdapter.java)，44–46 行；[BusinessQueries.java](../../business-service/src/main/java/com/example/business/BusinessQueries.java)，60–66 行；[DispatchCandidateService.java](../../backend/src/main/java/com/example/report/rule/DispatchCandidateService.java)，111–125 行；[DispatchJobService.java](../../backend/src/main/java/com/example/report/dispatch/DispatchJobService.java)，54、95–97 行。

真实 MCP 游标路径没有传递筛选规则，由业务服务以空规则参数分页读取待派单事实，再由 Agent 逐条求值。低命中率时数据传输量仍接近全部待派单数据；每页 500 条不代表整次操作成本小。工作线程固定 4 个、租户队列上限 100、用户上限 8；单清单条目逐条执行。

这些限制提供保护，但不能从九条演示记录推导万人使用或百万记录容量。应先定义记录量、字段宽度、报表数量、并发、最大清单、P95/P99 时延和模型成本，再按真实接口时延做压测。可评估以可信规则 ID/版本下推安全谓词，保留行级复核；不要让模型提交查询代码。

### R6 / P2：交付门禁与说明仍有遗漏

[CI 工作流](../../.github/workflows/regression.yml) 已运行根聚合 verify 和前端回归，但尚未接入新增 `check-demo-baseline.cjs`、`check-no-legacy-compat.cjs` 门禁；本轮没有读取远端 CI 执行结果，不能断言远端已全部通过。未见镜像发布、签名、生产批准或容器端到端验证成为当前工作流的门禁。

[application.yml](../../backend/src/main/resources/application.yml) 第 27–28 行仍描述版本 0 自动接管及 V2+ 升级，与当前单一 V1、baseline-on-migrate=false 不符；DataRetentionService 的工作记忆说明也已陈旧。静态注释检查通过不能代替人工确认。这些是维护缺口，本轮仅记录，没有顺带改动代码或配置。

## 推荐推进顺序与工作量

估算前提：约 2 名后端、1 名前端，另有测试/运维配合；ERP 和身份系统提供明确接口、联调环境及对接人。以下是基于当前工作包的计划区间，未包含外部审批等待，不是工期承诺。

| 目标 | 参考时间 | 范围 |
| --- | --- | --- |
| 单企业受控试点 | 4–8 周 | 一至两类真实业务、少量用户、明确人工确认与兜底；处理 R1/R2/R4、身份/ERP、基础告警和备份恢复 |
| 单企业正式生产 | 8–12 周或更长 | 包含上项，补容量与故障演练、交付门禁、值班流程及至少一段真实流量观察；这两个区间不累加 |
| 多客户共库 SaaS | 3–6 个月或更长 | 在前述基础上建设租户调度、身份、数据/服务凭据隔离、客户接入、配置治理、公平配额与运维体系；尚需专项设计才能排细工期 |

优先顺序：先确定真实业务动作和数据变化契约，处理 R1/R2；再做一家企业、一类业务的正式身份和 ERP 纵向接入；随后用真实数据规模完成部署、告警及恢复演练；最后扩大客户、业务和并发范围。模型评估与出站数据策略应贯穿上述阶段。没有必要先增加更多自然语言功能再处理生产闭环。

建议试点出口至少包括：所有关键权限/确认/幂等用例通过；故障注入中无重复业务副作用；模型出现不确定时不扩大范围；数据变化可识别并按契约阻止或重新确认；备份可实际恢复；每个 UNKNOWN 结果可追踪并由明确角色处理。具体业务成功率、P95、RPO/RTO 由业务方先批准，不能用通用数字代替。
