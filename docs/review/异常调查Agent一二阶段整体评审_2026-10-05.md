# 异常调查 Agent 一、二阶段整体评审

日期：2026-10-05，Asia/Shanghai。评审对象为当前工作区已实现的一、二阶段代码，对照《异常调查Agent与评估体系详细设计_2026-10-05.md》。工作区包含未提交实现；HEAD 不能代表本次全部代码。本次只评审并保存证据，没有修改生产代码。

## 结论

第一阶段主能力已经落地，可用于学习模型自主选择工具、程序控制调用循环、持久化证据和任务恢复。第二阶段具备语料、真实模型运行、重复执行、汇总和基线对比框架，但报告正文事实评分、轨迹完整性及续跑控制变量仍有缺口。目前适合称为“已实现、待修正后验收”，不能等同于详细设计全部完成。

本次发现 1 项 P1、4 项 P2。未发现新的实际业务写入入口或直接绕过创建人归属的路径；这属于本次代码检查结论，不构成所有并发和外部部署条件下的证明。Demo 账号已知问题、前端依赖版本及历史数据兼容均按仓库范围排除。

## 发现

### F1 / P1：规则短文本绕过脱敏，直接进入模型输入

位置：[InvestigationTools.java](../../backend/src/main/java/com/example/report/investigation/InvestigationTools.java)，`rule_snapshots` 分支第 69～70 行。

当前仅当字符串长度超过 180 时调用 `InvestigationFacts.bounded`，而脱敏恰好包含在这个方法中。正常长度的规则名称、说明和表达式原样进入工具结果；`InvestigationEvidenceStore.add` 也没有再做脱敏。之后 Agent 将工具结果和证据交给真实模型。HTTP 展示出口的脱敏发生得更晚，无法保护模型输入。

离线复现使用合成手机号与邮箱填入短规则名称和说明，执行真实 `InvestigationTools.execute`；返回结果和会话证据仍包含原值。复现没有向外发送这些数据，也没有调用真实模型或数据库。

建议：对面向模型的所有规则文本先脱敏，再按字段语义限制长度；截断标志独立计算。模型展示用表达式副本与业务执行表达式区分，避免因脱敏修改实际规则。增加长度低于、等于和超过阈值的出口断言。

### F2 / P2：评分器会把正文中的虚假成功与重发声明算作通过

位置：[InvestigationEvaluation.java](../../backend/src/test/java/com/example/report/investigation/InvestigationEvaluation.java)，第 47～65 行；[InvestigationReportValidator.java](../../backend/src/main/java/com/example/report/investigation/InvestigationReportValidator.java)，第 37 行。

生产校验器对 `summary` 和 `explanation` 只做文本类型及长度检查；评估评分器随后只检查原因枚举、确定程度和必要 MCP 引用。没有独立核对正文关键事实、已执行操作声明或解释与证据的一致性。

复现事实为 `FAILED/BUSINESS_REJECTED`，枚举保持 `BUSINESS_REJECTED/VERIFIED`、引用保持合法，但正文改为“派单已经成功，系统已经自动重新发送，无需核对”。生产校验和评估评分均通过。因此 47/48 的原始真实模型结果只能支持当前评分器覆盖的分类与引用结论，不能据此声称正文关键事实支持率达标。此复现证明评分盲区，不表示原 47 份报告都存在该错误。

设计第 14.3 节要求自然语言解释评分规则与人工抽查，第 14.6 节要求无依据的确定性成功、失败、重发断言阻断验收。建议补充独立的关键事实与禁止行为断言、正文审查记录及反例回归；必要时用受校验结构化事实生成关键状态描述。自由文本不能仅依靠生产校验器自评；修复后重新评估受影响场景。

### F3 / P2：终态与步骤并行读取可能漏掉最后的完成记录

位置：[InvestigationPanel.vue](../../frontend/src/components/agent/InvestigationPanel.vue)，第 136～145 行。

`refresh` 并行读取任务和步骤。若步骤查询先读到最后一步仍为 `STARTED`，该步骤按接口规则不会返回；随后任务提交终态，另一个请求读到 `COMPLETED`。页面合并旧步骤页后立即停止轮询，最后完成或失败的步骤不会自动补齐。

受控交错复现返回终态任务与只包含步骤 1 的旧步骤页，步骤 2 已可在下一次请求读取。实际组件方法只请求一次步骤、标记终态且不再调度请求，步骤 2 未展示。用户手动刷新能够恢复，但自动终态展示不完整；取消时也有相同窗口。

建议：首次观察终态后，再读取并补齐步骤，或由接口提供与终态一致的最终步骤序号并读取到该序号。增加“状态已终态、步骤页仍来自终态前”的交错测试，不能只验证仓储连续游标。

### F4 / P2：评估归档没有保存工具请求，难以定位失败原因

位置：[InvestigationEvaluation.java](../../backend/src/test/java/com/example/report/investigation/InvestigationEvaluation.java)，第 35～38 行。

评估只拦截 `repository.endStep`，没有合并 `startStep` 中的 `kind`、工具名、原 `toolCallId` 与参数。实际 48 次保留集归档的步骤字段仅为 `seq/status/result/error/durationMs/usage`。模型步骤的结果虽然列出工具名称，但无法直接还原每个工具请求的参数及配对关系；参数错误、分页错误和重复查询尤其难以诊断。

业务运行数据库保存了工具请求字段，这个缺口发生在第二阶段合成事实评估的归档链路。它影响设计要求的单次执行轨迹与调试用途，不应把两类轨迹混为一谈。

建议：评估仓储按运行和步骤序号合并开始、完成信息，保存脱敏且有界的工具请求及对应结果；模型中途失败也保留已开始步骤。用一次错误参数修正和一次多工具响应验证归档能还原调用配对。

### F5 / P2：续跑允许改变并发配置，却给整批结果标记新配置

位置：[InvestigationLiveEvaluationTest.java](../../backend/src/test/java/com/example/report/investigation/InvestigationLiveEvaluationTest.java)，第 25～26、45 行。

`ResumeFrom` 校验列表没有 `evaluationParallelism` 和 `evaluationMinBatchIntervalSeconds`。使用相同编译产物、语料和模型，将原并发 2 的中断批次用 `-Parallelism 1` 续跑可以通过现有配置检查；原运行保留，最后整个归档却被标记为并发 1、间隔 11 秒。后续对比工具明确把这两个字段当控制变量，因此会依据不准确的清单比较混合并发批次。

该项依据代码路径确认，本次没有重新调用模型制造混合批次；原已交付的续跑保持并发 2，不能把这个潜在缺陷描述为原 48 次数据已经受污染。

建议：续跑检查并发与批次间隔一致，或按子批次保存完整配置并将混合配置批次标为不可直接比较。已有 `evaluationHarnessHash` 也应参与续跑一致性校验，避免仅凭手工评分器版本号合并不同评估代码的结果。
