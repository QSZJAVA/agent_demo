## I1：手工派单未纳入未知结果恢复状态机

- 位置：`backend/src/main/java/com/example/report/dispatch/DispatchService.java:397`，返回值见 408 行；`frontend/src/components/ReportTable.vue:129`。
- 触发：`/api/dispatch/direct` 发出请求后连接异常，后端将结果标为 UNKNOWN。用户再次提交相同记录。
- 当前行为：每次生成新的 `manual-UUID`；响应的 `planId/previewId` 都为空，失败条目也没有请求号。已有核对/重试接口要求 planId，无法处理这次手工请求。页面把 UNKNOWN 也计入“失败”汇总提示。
- 影响：操作人无法通过现有界面核对，重复提交无法利用原请求号去重。接入真实外部系统且首次请求实际已被受理时，有重复执行风险。
- 证据：真实 DispatchService、网关异常替身连续提交同一条记录两次，均返回 UNKNOWN、无 planId，网关收到两个不同请求号。没有证明当前 Mock 网关会造成两次业务写入：Mock 另有未派单状态条件更新保护。
- 建议：手工派单也创建持久化清单/条目并使用稳定请求号，UNKNOWN 进入核对状态；页面展示“待核对”，不引导按普通失败重新提交。

## I2：分页的共享 loading 标志不能隔离重叠请求

- 位置：`frontend/src/components/agent/PreviewCard.vue:156-163`，选择恢复见 134-143 行。
- 触发：第 2 页请求尚未结束又点击第 3 页；第 2 页先返回并完成恢复勾选，使 `loadingPage=false`，随后第 3 页返回。
- 当前行为：第 3 页替换 `pageRecords` 时，Element UI 对 `reserve-selection=false` 的表格清空旧选择并发出 `selection-change([])`。此时 `loadingPage` 已为 false，组件将新页记录记为排除项；之后 selectAll 按这份错误排除集恢复，无法纠正。
- 影响：用户没有取消勾选，新页记录却被取消，父组件收到错误排除集，生成的待确认清单会少记录。反序返回还会使旧页覆盖最后点击的页。
- 证据：执行真实 PreviewCard 方法，受控两页响应并模拟 Element UI 数据替换时的清空选择事件，150 条的已选数变为 149，记录 101 进入 excludedRecords。事件语义核对了本地 Element UI `packages/table/src/store/index.js:19-20` 和 `watcher.js:125-131`。这不是浏览器端到端验证。
- 建议：分页请求增加序号，只应用最新响应；赋值前开启选择事件抑制并持续到恢复完成，或加载期间禁止再次翻页。补重叠及反序返回测试。

## I3：历史加载不阻止发送，返回后整表覆盖实时消息

- 位置：`frontend/src/components/agent/AgentChat.vue:321-334`；busy 判断见 193-194 行。
- 触发：打开历史会话后，历史接口仍未返回，用户马上发送消息。
- 当前行为：activeId 已切换，但初次历史加载没有进入 busy。send 正常建立 SSE 并追加用户/助手消息；历史响应版本仍匹配，随后整表赋值 messages。SSE 后续更新的是已脱离消息数组的助手对象。
- 影响：本轮用户消息和流式回答从界面消失，容易让用户误以为请求没发出去并重复操作。服务端日志是否已保存是另一件事，本复现只确认客户端展示丢失。
- 证据：真实 AgentChat 方法，先挂起历史响应，再 send 并收到 text，最后返回旧历史，界面数组只剩旧消息。
- 建议：初次历史加载期间禁用发送/操作，或按消息身份合并响应并保护本轮实时消息；会话版本校验本身无法识别同会话中新发送的一轮。

## 修复记录（2026-09-28）

### I1：手工派单持久化及恢复

- 每条手工记录先创建无会话的预览和清单，再复用已有认领、发送前 UNKNOWN 落库、执行版本隔离、心跳和停滞恢复流程。记录身份按租户、报表 ID、记录 ID 生成稳定的系统幂等键，数据库唯一约束处理创建竞争；相同记录在重复或重叠批次中重用原清单。
- UNKNOWN/EXECUTING 不会因再次提交 `/direct` 而重发；明确失败必须通过原清单的失败重试接口处理，使用原外部请求号。核对仍使用既有 `/plans/{id}/reconcile`，未知结果未解除时拒绝重试。
- 手工派单保留人工选择语义，不套用自动规则；发送和重试前按主键复核当前未派单状态、租户和公司范围，继续校验目录和权限版本。审计 source 保留 manual。
- 从未发送过的过期、取消或被跳过的清单可释放旧创建键后重新准备；已经发送过的条目保留原键，不能借此绕过核对。其他账号不能重放或接管原手工清单。
- 保留 `manual:`/`retired:` 创建键前缀，普通清单接口不能占用这些键，也不能从手工快照另建清单。
- 报表页新增手工派单记录及分页，可刷新恢复、查看逐条失败原因、核对结果、重试失败项、继续未完成清单。一次限制 1～50 条，未知结果单独提示“待核对”。
- 协议变化：`POST /api/dispatch/direct` 返回 `total/successCount/failedCount/reviewCount/plans`，`plans` 含每条记录的 `planId/docNo/status/retryableCount/outcome/message`。新增 `GET /api/dispatch/direct/plans?reportType=...&page=1`，只返回当前租户、当前用户、指定报表的手工清单，每页 50 条。前后端应一起发布；原直接派单响应的 `success/failed` 数组不再使用。
- 不新增数据库迁移，复用现有预览、清单、条目及幂等唯一索引。修复前没有清单的历史手工 UNKNOWN 请求不会自动补建，应按原审计请求号核对。

### I2：分页请求隔离

PreviewCard 为每次分页分配请求序号，只应用最新响应；旧失败不能释放新请求的 loading 状态。表格数据替换及恢复勾选期间持续抑制选择事件，恢复回调也校验请求序号。加载期间禁用勾选和派单按钮。

### I3：历史加载与发送互斥

初次历史加载通过 openingHistory 进入 busy 状态，发送、派单等操作等待历史加载完成。请求失败也释放状态；同会话的新一轮消息不会再被迟到的初次历史响应覆盖。
