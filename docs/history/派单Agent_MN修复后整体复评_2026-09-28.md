## O2：回写条件没有保持锁定时的公司范围

关联 P0-01（接入契约）、P0-08（派单安全）、P1-05（结果一致性）。

位置：`StandardReportAdapter.java:162–178、196–199`；`历史单体派单网关:39–60`。配置及发布探测目前没有验证 `idColumn` 是否能在租户内唯一标识记录。

触发条件是接入标准报表时，源表使用 `(tenant_id, company_code, id)` 作为复合主键，配置把 `id` 作为 idColumn。同一租户 A、B 公司可以合法拥有相同的 id。这样的配置当前会通过配置校验和零行发布探测。

现有保护存在一个条件不一致：

1. `markDispatchedGuarded` 以租户、公司、ID、待派单状态 `SELECT ... FOR UPDATE`，对 A 公司取到一条并通过复核。
2. 它随后调用 `markDispatched`，UPDATE 只保留租户、ID、待派单状态，丢掉了公司条件。
3. A、B 公司同 ID 的两条记录都被改为已派单。UPDATE 返回 2，`== 1` 判断返回 false，并不会撤销已经发生的数据库更新。
4. 历史单体派单网关 把该结果作为明确 FAILED 保存，正常返回并提交整个事务。

### 实际复现

`docs/review/CompositeIdReviewProbe.java` 在独立测试库创建上述复合主键表，插入 `T001/A/7` 与 `T001/B/7` 两条未派单记录。真实配置校验和 adapter.probe 通过后，使用真实本地网关，在真实 TransactionTemplate 中提交仅针对 `A/7` 的手工派单请求。

事务提交后的断言：

- A 记录状态为 1。
- **B 记录状态也为 1。**
- 网关返回 `success=false, errorCode=RECORD_CHANGED`。
- 持久化请求流水状态为 **FAILED**。

日志：`backend/target/review-o/composite-id.log`。目录引用及规则缓存用测试替身，派单适配器、网关、SQL 和事务是真实代码；未通过 HTTP 控制器发请求，也未调用真实外部派单系统。

这不是说当前三张演示表必然发生跨公司回写：它们的全局 ID 路径已有回归通过。问题在于当前目录允许接入不满足唯一性假设的来源表，却没有拒绝接入或在更新时保留已验证范围。只读 A 记录的行锁保护不能约束随后范围更宽的 UPDATE。

### 修复及验收建议

- 派单 UPDATE 必须保持与行锁复核一致的完整记录身份和公司条件。
- 异常影响行数必须回滚事务，不能将“返回 false”当成数据库已经撤销。
- 当前 Candidate/RecordKey 模型采用 reportId + recordId，因此发布时还应验证 idColumn 在租户内唯一且不可为空；不支持的复合标识应拒绝接入 STANDARD 派单，或通过明确的完整主键模型/专用适配器支持。仅补公司 WHERE 并不能解决全部记录键碰撞问题。
- 回归覆盖不同公司同 ID、不同租户同 ID、无唯一约束的重复数据、正常单主键、返回异常行数后的源状态和网关流水一致性。

## O1：大预览异常清理会删除已激活的明细

关联 P1-01（完整分页结果）、P1-02（异步任务恢复）、P1-07（快照持久化）。

位置：`PreviewService.java:512–514`；`MybatisPreviewRepository.java:103–106`。

大预览先分批写入 BUILDING 快照，再在事务中激活。`previewLarge` 对 RuntimeException 统一执行 deleteBuilding。该仓储方法先无条件按 previewId 删除明细，只有随后删除头记录时才加 `status=BUILDING` 条件，也没有在同一事务内锁定并检查头记录。

当数据库实际提交了激活事务，但提交确认丢失或调用方收到提交异常时，不能据此断定事务已回滚。当前清理会删除已经 ACTIVE 的快照明细，头记录因不满足 BUILDING 条件而留下。

### 实际复现

`docs/review/PreviewCommitReviewProbe.java` 使用真实 MySQL、Flyway V1–V16、MyBatis 预览/清单仓储、TraceJournal 和 PreviewService。候选记录使用测试替身，将 maxItems 临时设为 1，以两条合成记录进入原有大预览分支，避免制造大量数据。

在提供给 PreviewService 的 TransactionOperations 包装器中：

1. 先用真实 TransactionTemplate 执行并提交激活。
2. 查询确认库中确有一张 ACTIVE 预览和两条明细。
3. 再向调用方抛出 TransactionSystemException，模拟提交确认异常。
4. 原有 catch/清理路径运行后，数据库剩下 **ACTIVE、total_count=2 的头记录，但明细为 0 条**。

日志：`backend/target/review-o/preview-commit.log`。这是“真实提交 + 人工注入确认异常”的故障测试，没有实际切断 MySQL 网络。探针成功表示缺陷存在，不是验收通过。

影响是已完成的大预览分页数据丢失，汇总/可靠卡片和实际明细不一致，无法完整回看。此测试没有派单，也没有证明重复派单；超过清单上限的大预览原本就不允许直接生成执行清单。

### 修复及验收建议

- 清理应在事务内锁定头记录并确认仍为 BUILDING，然后删除明细和头记录；与激活共享同一状态互斥边界。
- 对提交结果不确定的异常先读取可靠状态或保留待恢复记录，不能无条件进行破坏性清理。
- 回归至少覆盖真实提交后确认异常、正常回滚清理、清理与激活竞争、已 ACTIVE 快照拒绝清理、孤儿 BUILDING 快照回收。

### O2：源记录唯一性与回写范围

- STANDARD 报表在发布探测、候选读取、按 ID 读取和派单写入时验证源记录身份：idColumn 不可为空，并须具有 ID 或租户+ID 的唯一约束。公司参与的其他复合主键、普通非唯一索引、可空唯一键均拒绝使用；不自动修改源表结构。
- 已发布配置在实际使用时也检查，不会因绕过重新发布而继续使用不安全的键。校验使用真实列元数据和 information_schema.STATISTICS；查询遵守 JDBC/当前事务超时。写事务持有表元数据锁，避免验证之后被并发 DDL 改掉约束。
- guarded UPDATE 保留 SELECT FOR UPDATE 中的租户、公司、ID 和待派单条件。
- 实际影响多于一行时抛出异常回滚源更新和网关流水，不再将其作为可正常提交的 false 返回。旧的无公司参数回写方法同样要求事务和唯一性校验。
- SourceIdentityDatabaseTest **7/7**：复合公司键发布/读取/回写拒绝，跨租户同 ID 正常隔离，发布后 DDL 变化拒绝，nullable/非唯一键拒绝，异常影响行数事务回滚，以及实际 SQL 公司参数验证。

### O1：快照清理、追加和激活共用状态锁

- deleteBuilding 在事务内以 SELECT FOR UPDATE 读取当前状态；仅在仍为 BUILDING 时删除明细和头记录。ACTIVE、SUPERSEDED、EXPIRED 等状态均保留明细。
- 分批追加也在同一头记录锁下检查 BUILDING，写入后更新心跳，防止清理后又产生孤立明细。
- updateBuilding 增加 BUILDING 条件，旧构建对象不能把 ACTIVE 状态覆盖回去。
- 定时回收先有界读取候选 ID，再通过同一仓储方法在锁内重新核对状态和过期时间，避免旧扫描结果误删刚续写或激活的快照。
- TracePersistenceIntegrationTest 从 8 项扩展为 **14/14**。新增 6 项覆盖：真实提交后确认异常保留明细、实际回滚后清理、激活先赢/清理先赢两种交错、心跳重新校验及删除后追加拒绝、旧汇总更新拒绝。

提交确认异常仍可以返回错误，由持久化任务/历史记录恢复真实状态；修复保证不把这种异常当作“肯定没有提交”而删除已生效数据。

### 后续复评补修：异步任务生命周期

代码复查确认并补修了三个异常边界：

1. 超时逻辑在读到 RUNNING 后，激活可能先提交成功。现在只有条件 UPDATE 实际改变任务状态时才取消本地 Future、释放配额，避免中断刚完成的任务。
2. 用户取消或超时时，将被取消的 FutureTask 同时移出执行队列，及时归还排队空间。
3. 队列拒绝任务后，即使 FAILED 状态写库也失败，仍在 finally 中释放配额，避免无人执行的请求泄漏本地许可引用。

PreviewJobLifecycleTest **4/4** 验证以上场景。使用实际服务方法、受控 JDBC 返回和真实 FutureTask/执行队列；不把它描述为完整多实例超时故障演练。

### 后续复评补修：规则发布及草稿并发（P1）

追加实库测试在修复前确认：

- 两个持有旧读视图的发布请求执行后，同一范围出现两条 published 规则。
- 在另一个请求发布完成后，旧事务中的草稿保存仍可覆盖已发布规则。
- 同时新建草稿可能取得同一版本号并触发唯一键冲突。

修复前日志：`backend/target/review-rule-races.log`，三项测试均未通过，包含 published 数量从期望 1 变成 2 的断言。修复后：

- 规则新建、编辑、发布、停用、回滚、删除先锁定所属报表行，再访问规则行；目录修改使用同一报表行锁，避免交叉修改。
- 规则状态、当前 published 集合和版本分配使用锁定的当前读，不依赖旧的 REPEATABLE READ 快照。
- 锁定目录行后核对缓存版本；缓存尚未追上当前目录时返回 409，不能以旧字段定义发布规则。目录发布校验也锁定读取当前 published 规则。
- 草稿的报表和公司归属均不可通过保存接口修改，与现有前端禁用归属编辑的行为一致。
- RulePublicationConcurrencyTest **4/4**：两个并发发布最终只剩一条 published、旧草稿不能覆盖已发布规则、并发建草稿独立分配 4/5 版本、旧目录版本不能发布规则。

未新增数据库表或迁移；复用已有目录行和规则行锁。修改较少发生的规则/目录维护操作按报表串行化，可能增加同报表并发维护时的等待。
