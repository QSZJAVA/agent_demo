## 新确认的缺陷

### R1 / P1：旧密码登录可在改密完成后生成有效会话

位置：`backend/src/main/java/com/example/report/security/IdentityStore.java:57–67`、`:77–93`。

`login` 读取并验证密码后直接插入 `app_session`，没有与账号更新共享的原子性或账号版本检查。`saveUser` 虽然事务内锁定账号、更新密码并删除已有会话，但阻止不了尚未插入的登录会话。

确定性复现顺序：

1. 登录请求用旧密码完成校验，在插入会话前暂停。
2. 管理员通过真实 `saveUser` 更新该用户密码并撤销会话，事务提交。
3. 放行步骤 1；旧请求插入新会话，返回的 token 通过真实 `authenticate` 验证。

影响：改密／安全处置声称的会话撤销边界失效，持旧密码的在途请求仍可获得默认 8 小时会话。本复现不代表旧密码在更新完成后重新发起的普通登录仍会成功；问题是并发窗口。持续禁用状态仍会被 `resolve` 拒绝，本轮没有证明禁用账号可以正常访问。

建议：用凭据／会话版本与原子条件写入，或用一致的账号行锁及事务，将“验证的凭据仍有效”和“生成会话”绑定；改密递增版本并撤销会话。增加真实数据库并发回归，覆盖改密、禁用与重新启用、权限更新。仅给方法补事务而不保证相同锁定／重读语义，不足以证明修复。

### R2 / P2：账号大小写变体可禁用最后一个管理员

位置：`backend/src/main/java/com/example/report/security/IdentityStore.java:85–93`；`backend/src/main/resources/db/migration/V19__business_identity_and_dispatch.sql`。

自禁用保护用 Java `String.equals` 比较输入账号和当前账号。账号表没有显式指定大小写敏感排序规则；本轮按仓库 V19 建表，实际 `user_id` 为 `utf8mb4_0900_ai_ci`，数据库按不区分大小写匹配账号。

复现：当前管理员是 `admin`，传入 `userId=ADMIN`、`enabled=false`、`admin=false`。Java 检查认为不是本人，数据库却更新现有 `admin`。操作成功后启用管理员数为 0；相关会话也被撤销。启动引导只检查租户是否已有用户，不会因没有可用管理员而自动修复。

影响：有账号管理权限的管理员可误操作锁死系统，需数据库／运维恢复；这不是普通用户未经认证提权。该条件依赖账号列不区分大小写，不能泛化到所有排序规则。

建议：先解析数据库内的规范账号标识，再做本人保护；统一账号大小写语义，并在事务内保护“至少一个有效管理员”。覆盖大小写变体和多管理员并发降权／禁用，避免只修一个字符串比较而遗漏并发锁死。
