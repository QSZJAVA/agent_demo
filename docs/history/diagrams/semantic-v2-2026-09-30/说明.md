> 历史归档：保留原日期、版本与验收范围。当前运行说明以仓库根目录 README 和 demo-baseline.json 为准。

完整图表：[七页 HTML 阅读器](index.html)、[可编辑 draw.io](semantic-v2.drawio)、[七页 Mermaid 源文档](流程图.md)。HTML 无外部脚本或网络依赖，可下载后直接打开，支持分页和缩放。

## 1. 责任与流程分层

| 层 | 输入 | 产物 | 实际责任 |
| --- | --- | --- | --- |
| 前端 | 自由文本、当前会话、表格选择 | POST JSON / SSE 请求，或按钮 REST 请求 | 保留准确选择、预览来源及身份；展示文字、卡片和状态 |
| 身份和请求入口 | Bearer token、message | 可信 CurrentUser、合法消息 | 当前账号状态、租户/权限；非空、trim、2000 字符上限 |
| ModelIntentParser | 本轮受保护文本 + 结构化状态 + 可见目录 | SemanticIntent V2 | 识别本轮动作、范围修改、否定对象、禁止条件和待澄清字段 |
| IntentCodec / coverage | JSON、原文、报表词典命中 | 被接受的结构化意图 | 结构、类型、证据、修改顺序、禁止冲突与已知报表覆盖 |
| SemanticPlanner | 意图、desired、当前用户、目录 | 明确的公司/报表范围 | 将原话链接为稳定实体；按顺序原子合并；校验权限和未解条件 |
| PreviewService / SelectionResolver | 权威范围、当前规则、UI 选择 | 真实预览 + 排除 RecordKey | MCP 读取业务事实、规则求值、记录唯一定位、选择来源校验 |
| PlanService | 固定预览 + 排除项 + 幂等键 | PENDING 清单 | 归属/TTL/版本/规模/选择校验；持久化待确认内容 |
| DispatchService / 业务 MCP | 用户确认的清单 | 逐条结果、审计及核对状态 | 执行权、当前权限/版本/规则/源状态；事务幂等提交；未知结果核对 |

系统由“模型解释意图”与“确定性业务服务”共同工作。当前模型输出没有实际执行派单动作，也没有 SQL、会话 token 或服务密钥字段。权限和实际数据结果来自服务端。

## 2. 用户输入到底发送了什么

自然语言从 AgentChat.send 进入 streamChat，发送：

```json
{
  "conversationId": "已有会话ID；新会话可不传",
  "message": "查询A公司销售报表中可以派单的记录",
  "previewId": "当前表格选择所属预览ID；无选择时可不传",
  "excludedRecords": [
    { "reportId": "rpt-sales-order", "recordId": "2" }
  ]
}
```

excludedRecords 存的是不派的记录，以 `(reportId, recordId)` 复合标识，recordId 为字符串。前端还保留旧 `excludeDocNos` 的兼容参数。用户身份来自 Authorization，而非上述 JSON。

后端依次经过 Trace/CORS/会话认证过滤器、AgentController、AgentChatService。active 时立即交给 SemanticConversationService；只有显式配置 legacy 才进入旧 ChatClient/记忆/工具调用路径。解析失败不会自动转 legacy，也没有 DOMAIN 关键词解析兜底。

表格勾选、报表选择、生成清单按钮、确认按钮使用明确的 REST 参数直接调用服务。这些操作不需要先让模型理解文本。自然语言和按钮可共用后续预览/清单/派单服务，但其返回通道分别为 SSE 与 REST JSON。

## 3. 模型真正收到的上下文

ModelIntentParser 创建独立 ChatClient，调用前构造：

```json
{
  "currentMessage": "本轮文本；敏感实体已替换为随机REF占位符",
  "context": {
    "state": {
      "desired": { "companyCode": "A", "allReports": false, "reportIds": ["rpt-sales-order"] },
      "effective": { "companyCode": "A", "allReports": false, "reportIds": ["rpt-sales-order"] },
      "phase": "READY",
      "unresolvedCompany": false,
      "unresolvedReports": false,
      "unresolvedRecords": false,
      "excludedRecordCount": 1,
      "lastAction": "PREVIEW"
    },
    "reports": [
      { "reportId": "rpt-sales-order", "reportName": "销售报表", "domainCode": "sales", "description": "目录中的报表说明" }
    ],
    "mentionedReportTerms": ["销售报表"]
  }
}
```

该片段说明字段结构，不是本轮实际模型日志。reports 只来自该用户可派单目录。模型不获得完整业务明细、完整历史助手回复、完整排除记录列表或用户权限集合；多轮解释主要依赖结构化状态。服务端保存的 recentUserMessages 也没有在当前解析器的 modelContext 中传入。

手机号、18 位证件号及邮箱样式的文本，会经 SensitiveData.modelText 替换为本轮随机 `REF...`，原值和映射保留在本地。数字单据可能也命中保护模式，因此模型复制占位符，服务端解析后恢复原实体并再次校验。日志/状态/SSE 另走展示脱敏，不能混同为模型前不可逆删除实体。

## 4. 模型如何输出语义

提示词明确要求 JSON，只允许 7 种 action；scopeChanges 是有序程序，先公司/报表，记录变化在末尾；restrictions 只对 THIS_TURN 有效。模型自行理解整句中的动作、指代、否定和修正；后端不能从接口结果观察模型内部推理过程。

| action | 含义 | 服务端后续 |
| --- | --- | --- |
| PREVIEW | 查询、纠正或调整范围 | 刷新/复用预览，返回真实候选 |
| PREPARE_DISPATCH | 请求生成待确认清单 | 完成范围/选择验证后创建 PENDING |
| EXPLAIN_RULES | 查询本范围适用规则 | 从实际预览规则说明构造回复 |
| CANCEL_PLAN | 取消当前清单 | 找当前会话最新清单，仅按其状态允许取消 |
| SHOW_RESULT | 查看已有结果 | 读取持久化清单和计数 |
| HELP | 使用帮助 | 返回服务端帮助文本 |
| CLARIFY | 语义或范围不明确 | 按 COMPANY/REPORTS/RECORDS/ACTION 提示补充 |

| target | REPLACE | ADD | REMOVE | CLEAR |
| --- | --- | --- | --- | --- |
| COMPANY | 一家公司原话 | 不允许 | 不允许 | 全部可见公司 |
| REPORTS | 换成指定报表集合 | 追加报表 | 从范围移除报表 | 全部可见且允许派单的报表 |
| RECORDS | 替换排除集合 | 排除这些记录 | 恢复这些记录 | 清空排除项，恢复全部候选 |

未提及 target 意味着保持原状态，不在线上传 KEEP。公司当前用权威公司代码，并执行 NFKC、去尾部“公司”、转大写；未实现企业名称到组织代码的通用主数据映射。allReports 和公司 CLEAR 均受用户权限约束。

例如：

> 查询A公司销售报表，排除SO2026002，剩下的生成派单清单。

一个符合协议的示例意图如下（实际识别以模型输出和校验为准）：

```json
{
  "version": 2,
  "action": "PREPARE_DISPATCH",
  "scopeChanges": [
    { "target": "COMPANY", "operation": "REPLACE", "mentions": ["A公司"], "evidence": "查询A公司销售报表" },
    { "target": "REPORTS", "operation": "REPLACE", "mentions": ["销售报表"], "evidence": "查询A公司销售报表" },
    { "target": "RECORDS", "operation": "ADD", "mentions": ["SO2026002"], "evidence": "排除SO2026002" }
  ],
  "restrictions": [],
  "clarify": "NONE"
}
```

后端将 A公司 转为 A，将销售报表链接为 rpt-sales-order。若 SO2026002 在最终预览中唯一命中，再转为其 RecordKey 加入排除集合；不存在或重复则澄清。本例不承诺该单据此刻仍是可派候选。

“只查销售报表，不要派单”应为 PREVIEW，并在 restrictions 禁止 PREPARE_DISPATCH；“不要销售报表，其他生成清单”则应移除报表并 PREPARE_DISPATCH。这两种否定绑定不同对象。禁止只属于本轮，下一轮明确要求建单可以重新解释。

真实模式 temperature=0、默认 maxTokens=2400、无内部工具执行或回调。thinking-enabled 为 true 时上限变为 4096。当前 native-schema=true，额外向兼容模型接口设置 outputSchema，同时服务端提示词包含协议 Schema。当前内容通过同步 call().content() 获得；前端看到的 SSE 文字不是该模型的 token 流。

## 5. JSON 为什么不能直接拿来执行

IntentCodec 开启严格反序列化：拒绝未知属性、缺失/null 必填、标量强制类型转换、浮点冒充整数和尾随内容；要求 version=2。它容忍单层完整的 `json` Markdown 围栏，但提示词仍要求直接返回 JSON。

主要硬检查：

1. scopeChanges 最多 8 项，每项 mentions 最多 20 个，mentions 不超过 160 字符；evidence 非空且不超过 1000 字符；输出长度不超过 24000 字符。
2. evidence 经 NFKC/小写/去空白后必须包含在本轮原文中，mentions 经同样归一化后必须属于 evidence。提示词要求局部连续原文；代码并非逐字未归一化匹配。
3. CLEAR 必须空 mentions，其余操作必须非空；公司最多一次，仅 REPLACE/CLEAR 且最多一个 mention；记录变更后不能再修改公司/报表。
4. restrictions 不重复，scope 只能 THIS_TURN；所选 action 不得被本轮禁止。
5. CLARIFY 必须有待澄清字段，其他 action 必须 clarify=NONE；HELP/CANCEL_PLAN/SHOW_RESULT/CLARIFY 不可携带范围变化。
6. 查询/建单/规则说明的 REPORTS 变更必须覆盖本轮已命中的报表词典实体。该检查防止遗漏已知报表，不会代替模型判断这些报表应该追加还是移除。

JSON、证据或报表覆盖校验失败，应用层最多再独立解析一次，同样输入加修复指令；第二次失败则终止。模型/传输异常不进入该格式修复循环。Spring AI 传输重试另有 max-attempts=3，且 400/401/403/404 不重试；因此“至多两次语义解析”不是所有底层 HTTP 请求的绝对次数承诺。

重要限制：这些检查能证明结构和实体证据成立，不能完整证明否定语义一定正确。日期、金额、排序等新增筛选目前不能在协议中表达，提示词要求 CLARIFY ACTION；当前没有独立硬校验器穷举检测所有被模型遗漏的此类条件。不能把提示词要求描述为对任意自然语言的绝对正确保证。

## 6. 多轮语义怎样落地

| 状态 | 含义 | 更新规则 |
| --- | --- | --- |
| desired | 用户最新提出的公司/报表范围 | 明确修改按顺序合并，校验后用于查询；无权限的新公司不会回落旧公司 |
| effective | 最近一次真实查询成功的范围 | 仅预览成功更新 |
| excludedRecords | 对当前预览的排除复合键 | 真实预览唯一定位或匹配 UI 选择后更新 |
| previewId / planId | 当前预览和清单关联 | 新查询/建单后更新，不能由模型任意指定 |
| unresolvedCompany/Reports/Records | 之前请求尚未确定 | 未解条件阻止省略表达继续执行业务，明确替换/CLEAR/UI 重新选择后解除 |
| phase | READY / QUERYING / REJECTED / CLARIFY / PLAN_READY / FAILED | 随查询、建单、拒绝、澄清及异常写回 |

例如先查 A 公司销售，再说“那 B 公司呢”，可生成 COMPANY REPLACE，保持销售报表；用户没有 B 公司权限则 desired 指向 B、查询拒绝、effective 保持 A。下一句“剩下的生成清单”仍验证 desired，不会用 A 的旧预览执行。

公司/报表在 draft 上按顺序计算，全部解析成功才整体提交，避免“先追加成功、后移除失败”留下部分范围。记录变化延后到最终范围的真实预览上应用。RECORDS ADD 的含义是增加排除项，容易与报表 ADD 混淆，图中单独说明。

每轮开始更新 preview_request_version，让后续激活的预览确认自己仍属于最新请求。模型调用、报表扫描不持有长数据库事务；保存状态/激活预览/建单使用租约+version 围栏的小事务。

## 7. 报表与记录实体怎样解析

报表先过滤到当前租户、已发布/生效/可用、有权限且治理可见的可派目录。TextNormalizer 归一化后，TermIndex 使用名称/编码/ID/别名词典的最长不重叠匹配，英文还检查词边界；同一说法的类型优先级为名称、编码、ID、别名。

无词典命中时，ReportResolver 计算编辑距离相似度、二元组 Dice 和包含相似度的最大值，默认最低 0.6，领先差小于 0.15 为歧义，参数可能被当前治理策略调整。不过 V2 Planner 不自动采纳 FUZZY 结果，只允许可靠的 EXACT/唯一 ALIAS，且不接受未识别残片、ALL 作为普通 mention。全部报表应由 REPORTS CLEAR 表达。active 的歧义通常返回澄清文字；legacy/其他 UI 入口才可能走 choice 卡片。

记录必须来自真实预览：先单据号精确匹配，必要时去掉“单据号/订单号”等类别前缀，再匹配 label 描述。必须恰好一条命中；零条或多条要求表格精确选择。单据号不是主键，最终存的是 reportId+recordId，防止跨报表重复编号混淆。

## 8. 真实查询、规则和清单

PreviewService 先确定授权范围并记录目录/规则/权限版本，再通过 MCP report_records 按游标每批最多 500 条取事实。业务服务重新读取账号与公司/报表权限，SQL 按租户、公司、待派单状态和游标粗筛。

当前远端 MCP 适配器不传入 rule expression；候选规则由 Agent 侧 RuleCache/Aviator 确定性求值，具体公司规则优先于通配且按当前生效期选择。Boolean true 才命中；非布尔或单行求值异常按不命中处理并记录告警。模型不编写规则表达式，也不自行选择实际可派记录。

5000 是预览分批持久化阈值和单份清单上限，不是每次数据库查询上限；大预览可分页浏览。语义记录排除超过 5000 会要求缩小范围。active 的查询直接调用 PreviewService；独立的 preview jobs 是 UI/legacy 另一个入口，不能把 active 查询都画成异步任务。

生成新预览时会替代旧预览、作废相关待确认清单。排除项在同范围刷新时验证并迁移；无法完整恢复或 UI previewId 不匹配则阻止建单，不默认为用户恢复全部。预览默认有效 30 分钟，PENDING 清单默认 10 分钟。

PREPARE_DISPATCH 以 `semantic:requestId` 作为建单幂等键，创建 PENDING 后返回计划卡片。用户后来点击 confirm 才进入 DispatchService；active 主路径本身不调用 confirm，即使兼容路径有 require-confirm 配置，也不能据此说当前自然语言自动实际派单。

## 9. 确认与异常恢复

确认先校验清单归属、TTL、版本和权限，通过 CAS 从 PENDING 认领为 EXECUTING，再按清单 ID 复核当前事实。逐条发送前先保存 UNKNOWN 意图和稳定请求号 `planId-itemId`。

MCP dispatch_submit 在业务侧重新验证操作者、公司/报表、幂等负载、持久化确认、executionVersion、当前目录/规则及源记录状态；业务状态和请求结果同事务提交。当前服务更新本仓库业务表，不代表已接入外部 ERP。

Agent 保存 SUCCESS/FAILED/SKIPPED/UNKNOWN。未知结果、进程中断或结果持久化失败需 REVIEW_REQUIRED。核对按原请求号查询；锁定读等待在途提交，明确 NOT_FOUND 才标未发送可重试。失败重试由用户显式发起，仅重试 FAILED，并沿用稳定请求号。管理员可在自身授权范围内核对禁用账号，但不能恢复原账号后绕过权限重发。

SSE 包含 conversation、事实 text、preview、plan、selection、error、done 等业务事件，带 `requestId:seq`，出口脱敏。普通解析/业务澄清通常转为事实 text + selection + done；外层租约失败或超时才可能产生 error 事件，不能只靠有没有 error 判断业务动作成功。

semantic_dialogue 保存状态，semantic_turn 保存脱敏原文/意图/原因/模型/耗时，消息与卡片记录保存历史。断线/刷新通过历史、card-states、selection 和相关任务接口恢复，不保证原始文本流续传。前端若选择恢复失败，先阻止继续建单。
