## 2. J1：全选操作没有固定来源预览

位置：`frontend/src/components/agent/AgentChat.vue:479-481、495`；`backend/src/main/java/com/example/report/agent/DispatchTools.java:219-245`。

触发过程：

1. 标签页 A 展示预览 A，用户保持默认全选。
2. 同一会话在标签页 B 生成预览 B，服务端将 A 作废。A 页面尚未刷新卡片状态，仍显示 ACTIVE。
3. 用户在 A 卡片点击“派单已勾选记录”。`dispatchSelected(m)` 只发送固定文本，没有使用 `m.payload.previewId`。默认全选期间选择恢复事件被抑制，`uiPreviewId` 通常仍为 null。
4. 请求携带 `previewId=null、excludedRecords=[]`。模型省略可选 previewId 时，后端 `targetPreviewId` 为空，`PlanService.usablePreview` 使用服务端最新预览 B。

即使前端在全选时已有 uiPreviewId，后端也只在 `recordExcludes` 非空时强制校验它；单独补前端赋值不足以关闭此问题。

影响：按钮表达的是“这张卡片已勾选的记录”，生成的却可能是另一张卡片的清单。默认仍有确认门槛，因此本次没有证明未经确认就实际派单，也没有调用网关。H2 修复保护了非空逐行排除，这里缺少的是空排除集下的来源约束。

复现脚本输出：`clicked preview A with all rows selected; sent previewId=null, excludedRecords=[]`。前端行为是执行真实组件方法得到；后端选用 B 的分支来自当前源代码检查，本轮未运行 Java 或真实模型端到端。

建议：卡片按钮显式绑定来源预览，并在服务端无论排除集是否为空都校验该来源；过期来源应拒绝，不能自动替换为最新预览。可直接调用确定性的建单接口，减少卡片按钮经过模型后丢失目标的机会。补多标签页 A→B、默认全选、取消后重新全选及模型未传 ID 的回归。

关联：P0-05、P0-07、P0-08、P1-04。

## 3. J2：创建清单的批量写入绕过配额

位置：`backend/src/main/java/com/example/report/web/DispatchController.java:162-180`；`backend/src/main/java/com/example/report/dispatch/PlanService.java:122-228`。

`POST /api/dispatch/plans` 直接调用 `PlanService.create`。该路径没有调用 ResourceQuotaService，WebConfig 和过滤器也没有统一限流覆盖。预览、聊天、确认、重试、核对上的配额不能约束直接调用此接口。

一个用户持有有效、尚未执行的预览后，连续使用不同幂等键（或省略幂等键）创建清单，每次都会读取全量预览明细、冻结规则、插入新清单及全部条目，并生成追溯事件。旧 PENDING 清单会失效，但失效不删除其明细，也不阻止继续创建。会话锁保证串行互斥，不限制累计请求或存储增长。

默认清单上限 5000 条。例如有效期内对 5000 条预览成功建单 100 次，会新增 50 万条清单明细；这是按代码行为计算的放大量，不是本轮压测结果。多个会话还可并行占用数据库连接和写入能力。接口只需用户拥有自己的有效预览，不需要管理员权限。

建议：在建单服务边界接入用户、租户、报表频率和并发配额，覆盖 REST 与工具调用；在读取整份明细和进入大事务前取得配额。重复幂等键应继续安全重放；配额拒绝不得先作废原清单或产生新记录。补“唯一键不断变化仍被限流”和“拒绝前无写入”的验证。

关联：P1-09，也影响 P1-01/P1-07 的容量目标。此项为静态确认的保护缺口，未向当前数据库进行高频写入或耗尽资源测试。

## 4. J3：清单结果被迟到分页响应覆盖

位置：`frontend/src/components/agent/PlanCard.vue:81-99`。

`changePage` 对每个返回值直接赋值，没有请求序号。state watcher、refreshVersion watcher、mounted 和用户翻页都可以触发它。

已复现两种交错：

- 先发第 2 页，再发第 3 页；第 3 页先到，第 2 页后到，界面最终退回第 2 页。
- 旧请求读取 UNKNOWN，核对后新请求读取 SUCCESS；新响应先到，旧响应后到，页面又显示 UNKNOWN 和旧失败原因。

第二种场景会使“已执行”的卡片标题与条目结果冲突。服务端状态没有被改回，不应描述为实际重派或数据库损坏。I2 已修复 PreviewCard 的分页竞态，PlanCard 仍保留同类响应覆盖问题。

建议：为 PlanCard 的所有分页/状态刷新分配递增版本，只应用最新响应；组件销毁和目标清单变化也使旧请求失效。新增分页反序、核对刷新与旧响应交错的回归。

关联：P0-07、P1-01、P1-05 的结果展示。
