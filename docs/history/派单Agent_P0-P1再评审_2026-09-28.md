## N1（新增 P1）：数值规则下推仍会静默漏项

关联 P1-03（规则下推），影响预览和试算的一致性。

主要位置：`backend/src/main/java/com/example/report/catalog/query/RuleSqlPredicate.java:53–54`。相关位置：`RuleEngine.java:25–29`、`StandardReportAdapter.java:248–254`、`StandardReportAdapter.java:201–203`。

SQL 下推把规则里的数字文本直接转换为 `BigDecimal`。实际规则引擎仍使用 Aviator 默认数值语义；同时，适配器允许配置 `long/integer`，通过 JDBC 把源列值转换后再交给引擎。这两种转换没有与 SQL 原列比较统一。布尔比较已回退 Java，但数值分支仍然可能提前过滤掉 Java 本来会判为命中的行。

### 真实 MySQL 复现

探针在独立 UUID 数据库中创建 `DECIMAL(36,16)` 列，使用真实 StandardReportAdapter、RuleEngine 和 DispatchCandidateService。RuleCache 用替身提供固定表达式，目录引用来自测试目录。配置校验和发布探测查询通过；没有启动应用、没有真实派单。

| 场景 | 数据和规则 | 试算 | 正式候选查询 |
| --- | --- | --- | --- |
| 源列和事实均为 decimal | SO1=1、SO3=1.0000000000000001；`amount == 1.0000000000000001` | SO1、SO3 | 仅 SO3 |
| 源列和事实均为 decimal | SO4=9007199254740992、SO5=9007199254740993；`amount >= 9007199254740993.0` | SO4、SO5 | 仅 SO5 |
| 源 DECIMAL 映射为 long/integer | SO1=1、SO2=1.9、SO3=1.0000000000000001；`amount == 1` | SO1、SO2、SO3 | 仅 SO1 |

前两例不依赖事实类型配置与源列类型不匹配。第三例说明当前允许的 JDBC 数值转换也有同类问题：源值 1.9 读取为整数 1，但下推比较源值与 1，导致漏项。

这不是说数学上 1 应等于 1.0000000000000001，而是说明系统现有确定性引擎和优化后的正式查询语义不一致。应先明确统一的数值契约，再实施优化。当前代码的 Java 二次校验无法找回已被 SQL 排除的记录。

探针共发现 **11 组集合不一致**，包含相同原因在多种表达式/字段映射下的复现，不算作 11 个独立 Bug。日志：`backend/target/review-n/numeric-probe.log`。探针退出成功表示缺陷已复现，不能计入业务验收通过数。

影响边界：已证明允许配置和有效表达式下的漏项；未证明三张现有演示报表正在使用这些高精度边界或转换配置，也没有证明实际发生错误派单。该问题足以阻碍 P1-03 的正确性验收。

修复建议：

1. 统一 SQL、JDBC、Aviator 的数字解析及比较语义；或者仅下推能证明等价的数值比较，其余回退 Java。仅对原表达式文本调用 `new BigDecimal` 不能证明等价。
2. 对声明字段类型与数据库物理类型建立校验或明确转换契约；涉及截断、精度损失的映射拒绝发布或关闭下推。
3. 增加真实数据库的“试算记录集合 = 正式预览记录集合”回归，覆盖高精度小数、2^53 附近数值、小数映射整数、负数、NULL、比较运算及 AND。单测 SQL 字符串不足以验收。

## M1/N1 修复记录（2026-09-28）

**两项已确认缺陷已修复，并通过本地及隔离实库回归；不因此将全部 P0/P1 生产验收标记为完成。**

### N1：仅下推有明确等价保证的数值条件

- 保留已有 Aviator 求值语义，不重新解释已发布规则，也没有修改规则版本。
- 标准适配器从真实 ResultSet 元数据检查物理类型、声明类型及有符号属性。仅对无精度损失的映射启用数值下推：如 DECIMAL 到 decimal、可安全容纳的整型到 long/integer。
- 小数映射整数、浮点映射等不确定转换保留 Java 求值；配置仍可接入，但不使用可能漏项的 SQL 条件。
- 数字字面量含小数点时回退 Java。整数也限制在 `[-(2^53-1), 2^53-1]` 内，因为实库回归发现 Aviator 的 decimal 与 long 比较会把 long 经 double 转换；只检查 Long 范围仍不足以保证等价。
- 普通常量如 `amount > 20`、`amount <= 50000` 在类型验证通过时继续下推；NULL 顺序和布尔回退保持。AND 中存在不可安全转换的比较时，整式回退。
- 每次使用数值下推前重新读取零行查询的元数据，避免长期缓存旧物理类型。代价是多一次元数据查询；回退表达式需要扫描更多候选，仍按已有分页执行，真实负载性能需压测。

新增 NumericRuleDatabaseTest **54 项**，使用真实 MySQL、真实 JDBC 映射与 Aviator，对比试算/正式候选完整记录集合；覆盖高精度小数、2^53 附近值、小数映射 long/integer、正负数、NULL、比较运算、AND 和超出 Long 范围的字面量。包含普通安全规则仍在 SQL 侧过滤的断言。

### M1：并发占用持久化，Redis 丢键不再腾出并发额度

- 新增 QuotaLeaseStore 与 Flyway **V16**：`resource_quota_scope` 串行化同租户、同操作准入，`resource_quota_lease` 保存唯一请求 token、用户及到期时间。
- Redis 继续承担用户/租户/报表的分钟频率限制；并发上限由 MySQL 独立维护，仍为每用户 4、每租户 20（按操作分别计数）。Redis 活动键不再作为并发占用的来源，不会因键丢失重新发放已占用的容量。
- 并发准入、续租、释放各自提交独立事务。准入使用无变更 upsert 直接获取范围行排他锁，避免 INSERT IGNORE 的共享锁升级死锁；业务事务回滚不会复活已释放的配额。
- 数据库租约为 300 秒，每 30 秒续期。本地用单调时钟在数据库到期前 10 秒停止承认租约，连接和加锁等待计入本地有效期；失效 token 不能被续租复活。
- 续租失败、记录消失或本地到期都会使 Permit 永久失效。失效信号通知模型流停止订阅；预览扫描/激活、建单、派单、重试、核对和试算在安全边界检查有效性。
- 派单检查在网关调用之前执行；已经发出的请求继续保存明确或未知结果。后续条目停止发送，必要时进入 REVIEW_REQUIRED，沿原请求号核对/重试，不把已发送请求直接重置为可重发。
- 释放只删除自己的唯一 token，且幂等。任务未退出时不因失效信号立即删除其持久化占用；正常结束释放，进程异常退出后由租约到期及后续准入清理回收。Redis/数据库准入不可用时拒绝新任务。
