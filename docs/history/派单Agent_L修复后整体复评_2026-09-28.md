## M1：租约丢失后旧请求不受并发统计约束

级别：P1；关联 P1-09（限流和资源保护），涉及多实例/故障恢复时的容量边界。

位置：`backend/src/main/java/com/example/report/config/ResourceQuotaService.java:30–33、119–125`。调用侧例如 `DispatchService.java:90、169、281` 只持有并关闭 Permit，逐条执行的 `requireExecution` 检查数据库清单执行权，不检查 Redis 配额租约。

触发条件：耗时任务仍在执行，但 Redis 的活动租约键丢失，例如重启未恢复该状态、故障切换丢写或租约过期。故障恢复后 Redis 再次可用。

当前行为：

1. 用户已取得 4 个 dispatch Permit，达到代码规定的单用户并发上限；第 5 次正常被拒绝。
2. 活动租约键丢失后，旧 Permit 的续租 Lua 因 ZSCORE 不存在返回 0。
3. `renew()` 忽略返回值，也忽略续租异常；不会将 Permit 标为失效、通知调用者或恢复计数。其后继续续租仍返回 0。
4. 新请求看到空的活动集合，可以再取得 4 个 Permit；旧调用者没有收到失效信号，仍可继续工作。

影响：故障后旧任务不计入并发数，新的任务同时被放行。正常 Redis 状态下的频率计数和并发限制仍然存在；此处不是“所有限流均无效”，也没有证明重复派单或权限绕过。

### 实际验证

`docs/review/QuotaLeaseReviewProbe.java` 使用真实 ResourceQuotaService、StringRedisTemplate 和本机 Redis 执行原 Lua：

- 创建随机的 `quota_review_<UUID>` 测试租户，取得 4 个许可，确认第 5 个返回 429。
- 只删除该测试租户的两个 active 键，模拟租约状态丢失；没有重启 Redis、FLUSHDB 或修改已有业务键。保留本次测试的频率键，排除绕过频率限制的干扰。
- 通过反射立即执行每个旧许可的原 `renew()`，代替等待 60 秒定时触发；确认没有恢复活动计数，旧许可均未关闭。
- 再成功取得 4 个许可。结果：未关闭许可共 8 个，Redis 用户活动集合仅记录 4 个。
- finally 关闭全部许可、停止本探针的续租线程，并只清理预先列出的 4 个测试键。

日志：`backend/target/review-m/quota-probe.log`。这是**真实 Redis 的配额层故障注入复现**，没有实际发起 8 个业务派单任务，没有制造资源耗尽，不能将“8 个许可”描述成“已实测 8 个任务占满服务”。业务继续运行的风险由 Permit 无有效性接口、调用侧无失效检查的代码路径确认。

### 修复建议及验收

- 续租返回 0/null 或超过允许失联时间时，应暴露租约失效状态，不能一直静默忽略。
- 扫描/模型/派单在可安全中止的边界检查租约。已发出外部请求的派单应保存结果或进入待核对，不能简单重置为可重发。
- Redis 状态丢失后，新任务准入需采用明确恢复策略，例如从可靠运行状态重建占用或在恢复期间拒绝新任务。不能无视容量直接为所有旧 token ZADD，否则只是换一种方式突破上限。
- 验收覆盖用户键丢失、租户键丢失、续租异常、恢复后旧新请求竞争、旧许可关闭不影响新许可，以及派单未知结果恢复。
