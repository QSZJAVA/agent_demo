## 1. 需要修复的问题

### G1 / P1：认领后另读当前版本，旧执行线程可以取得新轮次执行权

- 位置：`backend/src/main/java/com/example/report/dispatch/DispatchService.java:115-126`、`:187-190`；`dispatch/PlanService.java` 的 `claimForExecution`；`dispatch/store/MybatisPlanRepository.java` 的 `claim/claimRetry`。
- 认领接口只返回 boolean；确认和重试均在认领提交之后，另一次 `find` 读取当前 `executionVersion`。该版本不一定属于本次认领。
- 已复现时序：
  1. A 确认成功，清单为 EXECUTING/v1；在第 126 行读版本之前暂停。
  2. 模拟心跳超过五分钟，真实恢复服务将其置为 REVIEW_REQUIRED/v2。
  3. 核对 NOT_FOUND，条目标记 FAILED，清单变为 EXECUTED。
  4. B 重试认领成功，清单变为 EXECUTING/v3；暂停于数据复核。
  5. A 恢复，第 126 行取到 v3，后续 `isExecuting`、`withExecutionRight`、`updateItem`、`finish` 全部通过；A 发出请求并完成清单，B 恢复后反而报 ApiException。
- 独立程序输出：`TOKEN_RACE: revoked owner sent as version 3; sender=old-confirm; oldSuccess=1; newRetry=ApiException`。
- 证据范围：真实 DispatchService、PlanService、DispatchRecoveryService，内存仓库、Mockito 网关和候选替身；latch 控制线程交错，通过修改心跳时间模拟停滞，没有实际等待五分钟，也没有访问 MySQL。本次证明旧执行权失效机制可被绕过，未声称发生两次外部业务副作用。
- 建议：在认领事务内原子取得并返回本次执行令牌，服务只保存和使用该令牌；确认和重试一起修复。可采用条件更新绑定预先生成的 owner token，或加锁递增后在同一事务中返回版本。不要在认领事务外读取“当前版本”作为自己拥有的令牌。
- 回归要求：覆盖“认领成功、返回版本前暂停 → 恢复 → 核对 → 新重试 → 旧线程恢复”的窗口；旧线程必须拒绝发送和写回，新线程应正常完成。原新增测试只暂停在已取得版本之后的数据复核阶段，未覆盖此窗口。
- 影响：P0-07、P1-04、P1-05；F2 仍未完全闭环。

### G2 / P1：清单追溯只校验来源预览，返回的同会话消息可包含已撤权报表数据

- 位置：`backend/src/main/java/com/example/report/dispatch/DispatchTraceService.java:58、74-76`；`conversation/ConversationService.java:155-171`。
- trace 校验当前清单所属预览后，调用不接收 CurrentUser 的 `traceMessages`。后者按租户、会话、起止时间查询全部角色消息，没有按清单/预览归属或当前报表、公司权限过滤。
- 可达场景：同一会话先创建销售清单，随后查询费用报表；销售清单被作废且没有 finishedAt，trace 的结束时间使用当前时间。之后撤销费用权限、保留销售权限，用户仍可通过旧销售清单 trace 读取费用相关用户文本、助手文本或工具结果。只校验销售预览无法授权这部分消息。
- 独立程序同时验证：同一用户的普通历史入口因费用撤权返回 403；销售清单 trace 却返回带费用预览 ID 的工具结果测试消息。真实 trace 和 ConversationService 执行，mapper 用替身返回处于该查询窗口内的跨报表消息。SQL 范围由代码确认，未做真实数据库 HTTP 复现。
- 原始 F3 的管理员拒绝访问问题已修复；本程序也验证同租户、具备全部范围权限的 admin 可以追溯。这不消除上述返回消息的权限缺口。
- 建议：对返回的消息范围单独授权。最小修复可以在 trace 返回整段会话文本前应用会话级当前读取权限校验；若需保留部分报表追溯，必须按消息的预览/清单关联过滤，无法确定归属的自由文本应保守处理，并兼容同租户管理员的授权逻辑。
- 回归要求：混合报表/公司会话中，撤销其中一项权限；普通用户及权限受限管理员的 trace 都不能返回被撤权范围的消息，同时保留全权限管理员读取能力。
- 影响：P0-08、P0-09；原 R2 的读取权限边界仍有遗漏。

## 7. G1/G2 修复记录（2026-09-27）
