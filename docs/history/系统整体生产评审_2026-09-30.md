## 已复现的问题

### B1 / P1：报表页大整数 ID 在浏览器中失真，手工派单可能指向相邻记录

位置：`backend/src/main/java/com/example/report/entity/{SalesReport,ReceivableReport,ExpenseReport}.java:22`；`frontend/src/components/ReportTable.vue:189`、`:204`；`backend/src/main/java/com/example/report/web/DispatchController.java` 的 direct 接口。

三类报表的 `id` 为 Long，返回 JSON 时仍是 number；没有针对 ID 的字符串序列化。前端解析后直接把 `row.id` 提交到手工派单接口，接口接受字符串列表并按收到的 ID 找源记录。

复现：用真实 SalesReport、Result 和 SensitiveData 序列化合成 ID `9007199254740993`，JSON 中保留正确数字。但 Node 与浏览器同样使用 JavaScript number，解析得到 `9007199254740992`，手工请求变为：

```json
{"reportType":"sales","ids":[9007199254740992]}
```

如果相邻 ID 对应同公司、同报表中的另一条可派记录，当前服务端验证的是收到的相邻记录，不能判断用户原来勾选的是哪条；如果不存在则会报记录不存在。这个错误发生在身份和权限校验前的标识传递，不需要绕过权限。默认样例小 ID 不触发；接入大 BIGINT/雪花 ID 时有风险。

当前 FactRow/Agent 预览使用字符串 `recordId`，数据库大整数游标也已有回归；本项针对普通报表页及手工派单链路。建议所有业务 ID 在 HTTP/前端边界保持字符串，并增加“相邻大 ID、同公司、仅勾选其中一条”的端到端回归。

### B2 / P2：真实认证阻断浏览器跨域预检

位置：`backend/src/main/java/com/example/report/security/SessionFilter.java:30`、`:32`；`backend/src/main/java/com/example/report/config/WebConfig.java`。

虽然 WebConfig 支持显式配置 CORS 来源，但 SessionFilter 在进入 MVC CORS 处理前就认证非白名单路径。浏览器访问带 Authorization 的跨域 API，会先发送没有 Bearer token 的 OPTIONS 预检。

复现：OPTIONS `/api/report/sales/page` 带 Origin、Access-Control-Request-Method 和 Access-Control-Request-Headers，真实过滤器返回 HTTP 401，没有 Access-Control-Allow-Origin，后续处理未被调用。因此只设置 `CORS_ALLOWED_ORIGINS` 不能使受保护 API 的跨域访问正常。

当前 Vite/Nginx 同源代理不触发。修复应由服务端 CORS 机制先验证合法预检，放行已验证预检并继续保护真实业务请求；不能简单放行所有跨域业务访问。

### B3 / P1：原操作者禁用后，管理员无法核对遗留清单

位置：`backend/src/main/java/com/example/report/operations/OperationsWorkbench.java:59`；`backend/src/main/java/com/example/report/security/IdentityStore.java` 的 resolve；`business-service/src/main/java/com/example/business/McpConfiguration.java` 的 user/dispatch_lookup。

运营工作台即使已经验证管理员及预览可读权限，仍先调用 `permissions.resolve(原操作者)`，然后以原操作者身份执行 reconcile、close 等动作。真实身份查询只接受 `enabled=true` 的账号。账号禁用后，这一步返回 403，动作根本到不了核对服务。

复现使用真实 OperationsWorkbench/PermissionService，测试替身 隔离数据库与 IdentityStore：管理员有权读取合成预览，原操作者查询返回“用户已禁用”；管理员 reconcile 返回 403，DispatchService 没被调用。代码中的 MCP lookup 同样重新解析有效操作者，单改工作台身份构造不足以完成修复。

影响：员工离职/账号安全封禁后，其 REVIEW_REQUIRED 清单可能无法从现有产品接口核对；明确失败项也无法正常关闭。留存服务又会保护未核对/FAILED/UNKNOWN 记录，可能长期滞留。这里需要区分“查询既有请求结果”和“以原用户权限再次派单”。

建议增加独立运营核对权限，由管理员作为实际行动者并审计，使用持久化原操作者 ID 限定查找目标；允许对禁用账号的既有请求只读核对和安全关闭。重发仍须单独授权及业务复核，不能通过恢复被禁用账号来规避。

### B4 / P2：旧请求的 401 会清除新登录

位置：`frontend/src/api/http.js:24`、`:31`。

响应拦截器看到业务码或 HTTP 401 就无条件执行 sessionExpired，没有比较失败请求携带的 token 与当前 token。

复现直接执行当前 http.js 的错误响应逻辑：当前凭据已是 `new-session`，旧请求携带 `old-session` 的 401 晚到，结果仍清除 new-session 并触发登录失效事件。退出后快速重新登录或切换账号、旧请求还在途时会突然退出新会话。本轮是请求逻辑复现，没有把它描述为已观察到的跨账号数据泄漏。

建议只让当前会话的 401 撤销当前会话，并用会话版本保护请求返回；撤销旧会话时取消其请求。两个 401 分支都需要处理。

### B5 / P2：默认反向代理部署将所有登录者合并到同一个 IP 限流桶

位置：`backend/src/main/java/com/example/report/security/LoginController.java` 的 `request.getRemoteAddr()`；`IdentityStore.java:59`；`frontend/nginx.conf.template:54`、`:55`。

Nginx 传入 X-Real-IP/X-Forwarded-For，但后端没有配置受信任的转发地址解析。普通反代环境中 getRemoteAddr 返回代理地址；每个租户的 IP 限制为 40 次/10 分钟，计数在密码校验前发生，因此合法登录和错误尝试都会消耗这个共享桶。

真实 IdentityStore.login 配合 测试替身 Redis 计数复现：40 个不同账号使用相同代理来源各尝试一次，第 41 个无关账号在密码校验前返回 429。地址合并条件来自上述仓库代理配置与登录代码；本轮未启动 Nginx 进行完整网络链路复现。如果外部部署已经正确配置受信任代理解析，这项条件可被消除。

建议明确可信代理边界，使用框架对可信代理来源的转发地址解析，并保留账号和真实客户端维度的防爆破限制。不能直接信任任意客户端提供的 X-Forwarded-For。

## 必须落实的上线门槛

1. **业务正确性**：优先修复 B1 与 B3，并把复现转为正式回归。若采用跨域和反代部署，B2/B5 在该环境上线前必须解决。
2. **部署模式**：提供 Agent + business-service + DB + Redis 的实际编排；验证监听地址、服务 URL、TLS、健康检查、启动迁移顺序及认证。现有 Compose 尚未提供 real,mcp 双服务及真实会话认证的完整部署；不能把旧编排启动成功认作当前链路的安全验收。
3. **正式业务接入**：把当前示例报表/本地业务表执行切换或接入正式来源；明确业务“派单成功”的含义，验收幂等、超时未知结果、对账与人工处理契约。现在的服务拆分并不自动证明外部工单已经创建。
4. **容量和可用性**：先定义数据规模、并发、P95/P99、错误率、RPO/RTO；实测大数据预览、最长清单、数据库连接池、多实例、模型/Redis/MCP 中断、进程被杀及恢复。当前同步执行和 30 秒前端 HTTP 超时的组合也要在目标清单规模下验证。
5. **安全和运维**：数据库最小权限、TLS、凭据存储/轮换、备份恢复实操、错误码与业务失败告警、审计访问、上线回滚。配置中的数据库 root、useSSL=false 不能直接沿用跨主机生产环境。未找到仓库内完整容量/备份恢复演练证据；外部基础设施可能已有部分能力，需要补验收材料。
