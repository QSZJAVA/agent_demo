## 2. 新问题详情

### H1 / P1：切换账号没有隔离 AgentChat 的内存状态

- 位置：`frontend/src/App.vue:48、103-108`；`frontend/src/components/agent/AgentChat.vue:185-195、221-250、320-330`。
- App 的 `switchUser` 只更新身份、关闭抽屉及刷新报表页；AgentChat 没有绑定用户 key，也没有收到用户变化后清空状态的逻辑。关闭 el-drawer 不会重新创建 AgentChat，`activeId/messages/uiExcludes` 等仍在原实例中。
- 触发：user1 打开自己的聊天并看到 A 公司内容 → 切换 user2 → 重新打开派单助手。会话列表按 user2 刷新，但聊天消息仍是 user1 的。
- 恢复接口和状态接口即使正确返回无权访问，组件也会捕获错误并保留原消息，不能清除客户端已经缓存的内容。
- 复现输出：`USER_SWITCH: currentUser=user2; activeConversation=user1-conversation; visibleContent=user1 A-company confidential data`。
- 影响：同一浏览器切换用户后出现数据串显。这里没有声称 user2 能通过后端 API 查询 user1 数据；后端归属校验与客户端状态隔离是两件事。保留 Demo 用户切换不意味着可以保留上一用户的数据画面。
- 修复建议：按用户身份重建或完整重置 AgentChat，同时终止旧 SSE/轮询，阻止旧异步回调写入新用户状态。测试应覆盖闲置切换、正在查询时切换，以及新用户接口拒绝时的清屏。
- 关联：P0-08、P0-07、P1-06。

### H2 / P1：勾选按 docNo 去重，无法区分不同报表的同名单据

- 位置：`frontend/src/components/agent/PreviewCard.vue:146-153`；`backend/src/main/java/com/example/report/dispatch/PlanService.java:79-97`。
- 表格 rowKey 使用 reportId + recordId，但选中集合、排除集合只使用 docNo。数据库唯一约束是 previewId + reportId + recordId，没有要求跨报表 docNo 全局唯一。
- 已复现：同页销售 `DUP001` 和费用 `DUP001` 两条记录，用户取消销售、只保留费用勾选；`selected` 集合仍包含 `DUP001`，遍历两行时都判定为选中，输出 `excludes=[]`、`selectedCount=2`。
- 将这一空排除列表交给真实 PlanService，生成清单包含两条记录，包括用户取消勾选的记录。后续仍有确认门槛，因此本次证明的是清单范围错误，没有实际调用外部派单网关。
- 不同页出现相同单据号时也无法表达“只排除其中一条”；后端仅按 docNo 排除，会同时影响同号记录。
- 修复建议：界面逐行选择/排除使用稳定的 reportId + recordId 或 previewItemId，并由服务端校验这些键属于对应预览。自然语言按单据号排除可以保留，但同号有歧义时应明确提示范围，不能用它替代精确勾选协议。
- 回归要求：同页/跨页同号、大小写差异、不同报表不同主键；清单内容必须与勾选一致。
- 关联：P0-05、P0-08、P1-01、P1-05。

### H3 / P2：创建清单的幂等查询与插入之间存在竞态

- 位置：`backend/src/main/java/com/example/report/dispatch/PlanService.java:61-74、124-153`；`resources/db/migration/V5__dispatch_state.sql` 的 `uk_plan_idempotency`；`common/GlobalExceptionHandler.java:35-38`。
- `findByIdempotencyKey` 在事务及会话/预览锁之前。相同用户、预览、幂等键的两个重叠请求都可能读到不存在。
- 先行请求插入成功后，后行请求即使等到会话锁，也不再重新查询幂等键，仍然尝试插入，唯一索引抛 DuplicateKeyException。异常未被转成幂等重放，最终响应为 Result.code=500（本项目异常协议 HTTP 状态仍为 200）。
- 复现输出：`IDEMPOTENCY_RACE: overlapping same key=DuplicateKeyException; sequential same key=replayed`。
- 证据使用真实 PlanService、仓库替身和 latch；未连接 MySQL。内存替身不模拟数据库事务回滚，因此不据此判断真实库中原清单是否被作废。真实索引可保护不出现两份同键清单，本次没有复现重复派单。
- 修复建议：在正确的并发边界内重新检查幂等键，或在插入事务回滚后识别幂等唯一键冲突、查询原清单并重新校验归属后返回重放结果；不要吞掉其他唯一键错误。幂等键作用域为租户，还需考虑不同会话的同键竞争。
- 关联：P1-04、P1-05。

### H4 / P2：持久化历史有分页接口，但页面无法继续加载

- 位置：`frontend/src/components/agent/AgentChat.vue:258-295`；`frontend/src/api/agent.js:14-20`。
- 页面只调用无参数的 `fetchConversations()`（默认 50 个会话）和 `fetchMessages(id)`（默认 100 条消息），没有“加载更早消息”、会话分页或滚动加载控件，也没有传递 beforeId/page 的其他调用。
- 一个会话超过 100 条用户/助手/卡片消息后，重开只看到最新 100 条；超过 50 个会话后，较旧会话无法从当前侧栏选择。数据仍保存在服务器，缺的是用户可达入口。
- 影响还包括：结果卡片提示去清单卡片分页查看完整结果，但对应清单卡片若已落到最近 100 条之外，页面可能没有入口可到达它。
- 修复建议：接入已有游标/页码协议，补消息向前翻页和会话列表分页；结果卡片可增加按 planId 直接查看完整清单的入口。
- 关联：P1-07，也影响 P0-09 的用户侧追溯可达性。
