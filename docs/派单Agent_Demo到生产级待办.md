# 派单 Agent：从 Demo 到生产级待办

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 待评审 |
| 适用范围 | 自然语言查询可派单记录、预览、排除、确认派单、结果追踪 |
| 当前基线 | 本仓库 Demo：3 张报表、Redis 快照、规则版本校验、SSE 对话、确认卡片 |
| 目标规模 | 数百至上千张报表，多租户、多组织、多权限范围，持续运行 |

## 1. 结论先行

当前 Demo 的主业务闭环是正确的：

```text
用户表达意图 -> 查询候选记录 -> 生成预览快照 -> 用户调整或排除
-> 生成待确认清单 -> 用户确认 -> 执行派单 -> 返回结果并审计
```

这条闭环可以保留。需要生产化的重点是“报表如何识别、报表如何查询、状态如何持久化和并发控制”，而不是继续向正则表达式中添加报表名称。

`ReportPreviewRequest` 目前把报表名称直接写在 Java 正则中，只适合验证 Demo 流程。生产系统有数百或上千张报表时，应改为“报表目录 + 别名词典 + 权限过滤 + 统一解析服务”。新增报表主要通过配置和发布完成，不应要求修改正则、枚举和提示词。

## 2. Demo 现状与生产差距

| 领域 | Demo 实现 | 生产风险 | 生产目标 |
| --- | --- | --- | --- |
| 报表范围 | `ReportType` 枚举固定 3 张报表 | 每加一张报表都要改代码、提示词和测试 | 报表目录数据化，使用稳定 `report_id` |
| 用户说法识别 | `ReportPreviewRequest` 固定正则 | 同义词、简称、历史名称、错别字和多报表表达无法覆盖 | 目录别名、全文检索、可选语义召回、歧义确认 |
| 报表查询 | 每张报表一个固定事实装配器 | 报表数量和数据量增加后，开发和维护成本高 | 标准报表配置化，复杂报表使用专用适配器 |
| 规则匹配 | 查询后逐条执行规则 | 大数据量下延迟高，规则和数据查询难以优化 | 规则可下推到 SQL/查询引擎，保留确定性校验 |
| 预览数据 | Redis 保存一份完整快照 | 大结果集占用内存，无法分页和长期追溯 | 汇总 + 分页结果，快照保存版本和查询条件 |
| 待确认清单 | Redis 保存会话最新一份清单 | 多标签页、并发请求、重试可能互相覆盖 | 服务端状态机、版本号、原子作废和幂等键 |
| 卡片状态 | 前端按消息下标推导过期 | 页面刷新、历史会话和多端状态可能不一致 | 状态由服务端返回，前端只负责展示 |
| SSE 事件 | 文本和卡片合并输出 | 事件顺序可能不稳定，断线无法续传 | 序列号、事件幂等、断线重连或轮询补偿 |
| 派单执行 | Demo 模拟接口逐条执行 | 外部接口超时、部分成功、重复提交需要恢复 | 幂等、重试、补偿、逐条状态和人工处理 |
| 规则版本 | 全局规则指纹 | 无法精确表达报表目录、权限和查询版本 | 记录规则集、目录、权限和数据快照版本 |
| 对话记忆 | Redis 窗口 + MySQL 日志 | 长会话、跨设备、敏感数据和回灌成本增加 | 结构化会话上下文，业务状态不依赖模型记忆 |
| 监控审计 | 有基础日志和审计 | 难以定位误派、漏派、模型误判和接口失败 | 业务指标、链路追踪、操作审计和告警 |

## 3. 生产目标模型

### 3.1 报表目录代替报表枚举

每张报表需要一个稳定、不可变的业务标识 `report_id`。展示名称、别名和历史名称都属于可维护数据，不写入解析代码。

建议至少维护以下信息：

| 字段 | 业务含义 |
| --- | --- |
| `report_id` | 内部稳定标识，不能因改名而变化 |
| `report_code` | 对外或接口使用的编码 |
| `report_name` | 当前展示名称 |
| `domain` | 销售、应收、费用、采购等业务域 |
| `status` | 草稿、已发布、停用 |
| `query_mode` | 标准查询、SQL 模板、服务适配器、外部接口 |
| `dispatch_enabled` | 是否允许通过 Agent 发起派单 |
| `schema_version` | 事实字段和结果结构版本 |
| `permission_policy` | 报表级权限要求 |
| `effective_from/to` | 生效时间范围 |

别名单独维护，包括：简称、口语、英文名、历史名称、业务部门俗称和常见错别字。例如“销售台账”“订单销售表”“销售明细”可以都指向同一个 `report_id`。

### 3.2 `ReportPreviewRequest` 的生产替代方案

将固定正则替换为通用的 `ReportResolver`。它不负责执行查询，只负责把用户表达解析成结构化意图：

```json
{
  "operation": "preview",
  "reportQuery": "销售台账",
  "filters": {},
  "excludeDocNos": []
}
```

解析过程：

1. 先识别操作：查询、派单、排除、确认、取消、查看结果。
2. 在当前用户有权限访问的报表目录中进行精确名称匹配。
3. 未命中时使用别名匹配，再进行分词、全文检索或语义召回。
4. 唯一命中且置信度达到阈值时继续执行。
5. 命中多个报表时返回选择卡片，不允许模型自行猜测。
6. 没有命中时提示用户补充报表名称、业务域或筛选条件。

大模型可以负责提取 `reportQuery` 和过滤条件，但不能直接决定任意 `report_id`。最终报表必须由服务端结合目录和权限解析。

示例：

| 用户表达 | 解析结果 |
| --- | --- |
| “查销售台账” | 唯一命中，直接预览 |
| “查客户对账” | 命中多个报表，展示候选让用户选择 |
| “查我能派单的报表” | 查询当前用户有权限且启用派单的报表目录，再按规则汇总 |
| “不是刚才那个，是应收发票台账” | 基于当前会话上下文重新解析并生成新预览 |
| “查 XX” | 无匹配，提示补充完整名称或业务域 |

### 3.3 报表查询与派单适配

报表数量多不等于每张都要手写一套代码。建议采用两类实现：

- 标准报表：通过目录配置查询字段、过滤条件、主键、单据号字段、金额字段、日期字段和派单状态字段。
- 复杂报表：实现专用查询适配器，但仍通过统一接口返回候选记录。

统一结果至少包含：

```text
report_id
record_id
doc_no
company_code / organization_id
display_fields
amount
business_date
dispatch_status
matched_rule_id / matched_rule_version
```

规则判定仍由确定性服务完成。大模型不得决定“是否命中派单规则”。

## 5. 业务规则

### 5.1 报表解析规则

1. 报表名称匹配必须先经过当前用户权限过滤。
2. 精确名称优先于别名，别名优先于模糊或语义召回。
3. 多个候选分数接近时必须展示候选，不允许自动选择。
4. 用户纠正报表范围后，必须生成新的预览版本。
5. 新预览生成后，同一会话的旧预览和待确认清单作废。
6. 报表不存在、已停用或用户无权限时，不返回内部报表信息。

### 5.2 预览规则

1. 预览只返回当前用户有权限查看的记录。
2. 预览记录必须绑定报表目录版本、规则版本、权限版本和查询条件。
3. 预览超过有效期、规则变化、权限变化或原记录状态变化后不可执行。
4. 预览可以为空，但必须生成明确的“0 条”结果，不得沿用上一张卡片。
5. 大结果集使用分页，卡片展示总数、各报表汇总和当前页。

### 5.3 待确认和执行规则

1. 待确认清单只允许来自一个有效预览快照。
2. 同一会话同一时刻只能有一份 `PENDING` 清单。
3. 用户取消、生成新清单、超时、规则变化、权限变化都会使清单失效。
4. 确认接口必须校验归属、状态、版本、幂等键和记录当前状态。
5. 执行允许部分成功，但每条记录必须有最终状态和失败原因。
6. 外部接口超时不能直接判定成功，必须进入待确认或补偿状态。
7. 失败重试不能重复调用已经成功的记录。

## 6. 建议数据模型

### 6.1 报表目录和别名

```sql
CREATE TABLE report_definition (
    id                 BIGINT PRIMARY KEY AUTO_INCREMENT,
    report_code        VARCHAR(128) NOT NULL,
    report_name        VARCHAR(256) NOT NULL,
    domain_code        VARCHAR(64)  NOT NULL,
    query_mode         VARCHAR(32)  NOT NULL,
    dispatch_enabled   TINYINT      NOT NULL DEFAULT 0,
    status             VARCHAR(32)  NOT NULL,
    schema_version     INT          NOT NULL DEFAULT 1,
    catalog_version    BIGINT       NOT NULL,
    effective_from     DATETIME     NULL,
    effective_to       DATETIME     NULL,
    owner_user_id      VARCHAR(64)  NULL,
    created_at         DATETIME     NOT NULL,
    updated_at         DATETIME     NOT NULL,
    UNIQUE KEY uk_report_code (report_code),
    KEY idx_report_status (status, dispatch_enabled)
);

CREATE TABLE report_alias (
    id                 BIGINT PRIMARY KEY AUTO_INCREMENT,
    report_id          BIGINT       NOT NULL,
    alias              VARCHAR(256) NOT NULL,
    alias_type         VARCHAR(32)  NOT NULL,
    priority           INT          NOT NULL DEFAULT 0,
    status             VARCHAR(32)  NOT NULL DEFAULT 'ACTIVE',
    created_at         DATETIME     NOT NULL,
    UNIQUE KEY uk_report_alias (report_id, alias),
    KEY idx_alias_search (alias, status)
);
```

生产库需要根据实际搜索方案增加分词索引、搜索引擎索引或向量索引。上面的普通索引不能替代中文全文检索。

### 6.2 预览快照和待确认清单

```sql
CREATE TABLE dispatch_preview (
    id                 VARCHAR(64) PRIMARY KEY,

    created_at         DATETIME     NOT NULL,
    superseded_at      DATETIME     NULL,
    KEY idx_preview_owner (tenant_id, user_id, conversation_id, created_at)
);

CREATE TABLE dispatch_plan (
    id                 VARCHAR(64) PRIMARY KEY,
    preview_id         VARCHAR(64) NOT NULL,
    tenant_id          VARCHAR(64) NOT NULL,

    conversation_id    VARCHAR(64) NULL,

    exclude_json       JSON         NULL,
    idempotency_key    VARCHAR(128) NOT NULL,
    created_at         DATETIME     NOT NULL,
    expires_at         DATETIME     NOT NULL,
    confirmed_at       DATETIME     NULL,
    finished_at        DATETIME     NULL,
    UNIQUE KEY uk_plan_idempotency (tenant_id, idempotency_key),
```

实际项目可以继续使用 Redis 做短期加速，但数据库或可靠任务表必须保存可恢复的业务状态，不能只依赖 Redis 中的“最新一份”。

## 7. 页面和接口行为

### 7.1 对话页面

1. 用户输入报表名称或业务别名。
2. 页面展示“正在识别报表”或“正在查询”。
3. 唯一命中时展示预览卡片。
4. 多个候选时展示报表选择卡片，用户选择后再查询。
5. 无权限或无匹配时只展示业务可理解的提示。
6. 新预览出现后，旧预览显示“已作废”，旧待确认清单显示“已过期”。
7. 页面刷新、重新打开会话或切换设备后，卡片状态以服务端为准。

### 7.2 预览卡片

卡片至少展示：报表名称、命中规则说明、总数、金额汇总、当前页、分页入口、状态、有效期和数据更新时间。

以下操作必须由服务端重新校验：取消勾选、生成清单、确认执行、重试失败记录。

### 7.3 主要接口建议

| 接口 | 作用 |
| --- | --- |
| `GET /api/report-catalog/search?q=` | 按权限搜索报表目录 |
| `GET /api/report-catalog/{reportId}` | 获取报表定义和可用筛选项 |
| `POST /api/dispatch/previews` | 创建预览快照 |
| `GET /api/dispatch/previews/{id}` | 查询汇总、状态和版本 |
| `GET /api/dispatch/previews/{id}/items` | 分页查询预览记录 |
| `POST /api/dispatch/plans` | 基于预览创建待确认清单 |
| `POST /api/dispatch/plans/{id}/confirm` | 幂等确认执行 |
| `POST /api/dispatch/plans/{id}/cancel` | 取消清单 |
| `GET /api/dispatch/plans/{id}/items` | 查询逐条执行结果 |

Agent 工具可以调用这些确定性应用接口，但不能绕过目录、权限和版本校验。

## 8. 异常场景和处理口径

| 场景 | 系统行为 | 页面提示 |
| --- | --- | --- |
| 报表无匹配 | 不创建可执行计划 | “没有找到匹配的报表，请补充名称或业务域” |
| 多个报表命中 | 不自动查询 | “找到多个相关报表，请选择” |
| 用户无权限 | 不泄露报表存在性 | “当前账号没有可访问的报表” |
| 查询结果 0 条 | 创建可查看的空预览或明确空结果 | “当前条件下没有可派单记录” |
| 预览过期 | 禁止创建计划 | “预览已过期，请重新查询” |
| 规则已变更 | 作废预览和计划 | “派单规则已更新，请重新查询” |
| 权限已变更 | 作废预览和计划 | “权限范围已变化，请重新查询” |
| 旧卡片点击 | 服务端拒绝，前端显示作废 | “该卡片已作废，请使用最新卡片” |
| 外部接口部分失败 | 保留逐条结果，可重试失败项 | “部分记录成功，失败项可重试” |
| 外部接口超时 | 状态置为待确认或未知，禁止盲目重试 | “接口结果待确认，请稍后查看” |
| SSE 中断 | 根据事件序号补偿或查询任务状态 | “连接中断，正在恢复结果” |
| 重复确认 | 幂等返回第一次结果 | “该清单已处理” |

## 10. 监控指标和上线门槛

上线前至少具备以下指标：

| 指标 | 说明 |
| --- | --- |
| 报表解析唯一命中率 | 唯一命中 / 总解析请求 |
| 报表歧义率 | 多候选请求占比 |
| 无匹配率 | 无法识别的请求占比 |
| 预览成功率 | 成功生成预览 / 预览请求 |
| 预览 P95 耗时 | 按报表和数据量分组统计 |
| 计划创建失败率 | 过期、版本变化、权限变化分别统计 |
| 派单成功率 | 全部成功、部分成功、失败分布 |
| 外部接口超时率 | 按接口和报表统计 |
| 重复确认拦截次数 | 观察前端重复提交和攻击行为 |
| 模型工具调用错误率 | 参数错误、工具遗漏、模型超时 |

上线门槛建议：核心报表解析回归集通过、旧预览不可执行、重复确认无重复派单、权限越权测试通过、部分失败可恢复、关键链路有审计和告警。

## 11. 实施顺序建议

### 第一阶段：业务模型重构

完成报表目录、别名、稳定 `report_id`、权限过滤、规则和审计字段迁移。此阶段先不引入复杂语义检索，保证精确名称和别名可用。

### 第二阶段：解析和查询生产化

上线通用报表解析服务、歧义选择卡片、标准报表配置查询和复杂报表适配器。将固定的 `ReportPreviewRequest` 和 `ReportType` 逐步降级为兼容层。

### 第三阶段：执行可靠性

完成分页、异步任务、服务端状态机、幂等、部分成功、补偿和事件序号。此阶段重点关注并发和外部派单接口异常。

### 第四阶段：规模化运营

补齐目录管理、解析评估集、灰度发布、指标监控、人工处理工作台和数据留存治理。

## 12. 明确禁止的生产做法

1. 不继续在 `ReportPreviewRequest` 中追加报表名称正则。
2. 不让大模型直接生成 SQL、表名、组织范围或派单记录 ID。
3. 不把 Redis 中的最新快照作为唯一业务事实。
4. 不由前端消息下标决定预览或计划是否有效。
5. 不因外部接口超时就直接重试全部记录。
6. 不把“模型回复说已派单”当作真实执行结果。
7. 不在未校验权限、规则版本和记录当前状态的情况下执行旧卡片。
8. 不用全量结果塞入模型上下文或浏览器页面。

## 13. Demo 保留项

以下设计经过生产化补强后仍建议保留：

- 预览和执行分离。
- 预览快照作为执行依据。
- 派单前确认门槛。
- 服务端从登录态获取身份和权限。
- 规则版本校验。
- 逐条派单结果和审计。
- 对话日志与短期工作记忆分离。
- 真实模型和 Mock 模型使用同一套业务工具协议。
