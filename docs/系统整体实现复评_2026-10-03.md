## 确认的 Bug

### R1 / P1：改密完成后，在途旧密码登录仍能生成有效会话

位置：[IdentityStore.java](../backend/src/main/java/com/example/report/security/IdentityStore.java)，57–67、77–93 行。

登录读取并验证密码后直接插入会话，没有将凭据版本和会话创建绑定。管理员更新密码并删除会话时，会漏掉尚未插入的会话。

本轮再次复现：旧密码验证通过 → 登录暂停于会话插入前 → 改密及会话撤销提交 → 恢复登录 → 返回 token 仍通过 authenticate。影响默认 8 小时会话撤销边界；这是并发窗口，不是“更新后重新发起旧密码登录仍成功”。

建议：增加凭据/会话版本，改密、禁用和授权更新按明确策略递增版本；会话创建必须原子验证它使用的凭据版本仍有效，认证时校验会话版本。也可采用一致的账号锁和重读语义；仅添加事务注解不足以关闭窗口。增加真实数据库并发回归。

### R3 / P1：被降权管理员的在途请求可以把自己改回管理员

位置：[IdentityStore.java](../backend/src/main/java/com/example/report/security/IdentityStore.java)，78–92 行；[LoginController.java](../backend/src/main/java/com/example/report/security/LoginController.java)，20–21 行。

saveUser 只检查调用时传入的 CurrentUser.admin，之后锁定目标账号、更新账号。没有在账号写入事务中重新验证操作者当前仍启用且仍为管理员。控制器在调用服务前认证不能覆盖随后的并发窗口。

确定性复现：

1. 管理员 A 发起更新自己账号、保留 admin=true 的请求，通过管理员检查，在读取目标账号前暂停。
2. 管理员 B 将 A 降为普通用户并撤销会话，事务提交；数据库确认 A 已不是管理员。
3. 恢复 A 的原请求，它仍成功更新账号，数据库确认 A 再次成为管理员。

影响：撤销管理员权限后，在途账号写入仍可重新授予权限。复现需要原请求在撤销前已通过认证/管理员检查；没有证明一个从未具有管理员权限的普通用户可以提权。

建议：在同一写入事务中锁定并重新解析操作者和目标账号，验证最新启用状态、角色及授权版本后更新。锁顺序须一致，避免两个管理员互相修改时死锁；账号授权变更也应纳入租户内统一的并发控制。回归覆盖降权、禁用及在途自更新/第三方授权。

新探针：[IdentityRevocation20261003Probe.java](review/IdentityRevocation20261003Probe.java)、[运行脚本](review/run-identity-revocation-20261003.ps1)。它创建、校验并清理 UUID 隔离库，用锁存器控制真实服务方法的交错；Redis 依赖是测试替身，未调用 HTTP 登录或真实模型。

### R2 / P2：大小写变体可以禁用最后一个管理员

位置：[IdentityStore.java](../backend/src/main/java/com/example/report/security/IdentityStore.java)，85–93 行；V19 账号表定义。

Java 使用区分大小写的 equals 判断是否操作本人；本轮隔离库实际账号列使用不区分大小写的 utf8mb4_0900_ai_ci。当前管理员 admin 提交 ADMIN、enabled=false、admin=false，校验放行，数据库更新同一账号，启用管理员数变为 0。

影响是管理员误操作导致系统无法继续管理，需要运维恢复；不是普通用户越权。依赖实际数据库排序规则。

建议：使用数据库内规范账号标识或不可变账号 ID 校验本人，统一大小写语义，并在事务中保护“至少一个启用管理员”。必须覆盖多个管理员并发互相降权/禁用，仅修 equals 比较仍不充分。

R1/R2 使用历史探针重新执行验证，历史文件保持原样：[IdentityReview20260930V2Probe.java](review/IdentityReview20260930V2Probe.java)。

### 需要专项验证的执行版本风险

[McpDispatchGateway.java](../backend/src/main/java/com/example/report/mcp/McpDispatchGateway.java) 第 21 行在发送前重新读取数据库当前 execution_version，DispatchRequest 未携带执行者原先认领的版本。上游虽检查原版本，但跨服务调用没有持有该行锁。

需要专项覆盖“旧执行者通过检查后暂停 → 恢复/核对/重试产生新版本 → 旧执行者恢复发送”的交错，确认旧请求不能获得新执行版本。建议把原认领版本作为不可变参数传递到业务服务。当前业务服务已有版本复核与幂等保护；本轮没有复现该交错导致实际错误派单，因此此项作为待验证风险，不计入三个确认 Bug。

具体性能优化：

- 当前 HTTP MCP 游标路径没有传递规则表达式；BusinessQueries 的 cursor 调用以 null 谓词读取待派单事实，Agent 再逐行求值。规则选择性很低时，传输和求值量接近全部待派单记录。可以由业务服务根据可信规则 ID/版本选择并安全下推可支持谓词，同时维持精确规则复核和版本约束；不让模型提供可执行查询。先测扫描条数、MCP 调用次数、P95 和数据库执行计划，再决定索引及下推方式。
- 避免每次卡片状态恢复都加载整个会话的全部历史预览/清单，考虑按可见卡片 ID 批量查询，减少长会话中的查询和版本刷新成本。
- 对规则编译缓存和输入长度设预算，增加规则求值错误数及异常数据告警。当前逐行求值失败按不命中处理，用户仅看到命中数时可能难以判断数据质量问题。
- 大清单执行以持久任务分批推进；并行度必须受租户配额、外部业务容量和幂等契约约束，通过故障演练后调整。

模型优化应使用当前真实端点的独立语料，覆盖否定、歧义、长句、多轮纠正、权限拒绝和依赖故障，记录来源 MODEL、澄清/拒绝、时延、成本和业务结果。当前协议明确不支持日期、金额、排序等条件，扩展前保持澄清，扩展时同步修改 Schema、解释协议和业务查询能力，不能只改提示词后静默丢弃条件。

前端目前依赖 Vue 2.7.16、Element UI 2。Vue 2 已结束官方维护，适合分阶段迁移到 Vue 3 及兼容组件库，并保留现有派单交互回归。[Vue 官方 EOL 说明](https://v2.vuejs.org/eol/)、[官方迁移指南](https://v3-migration.vuejs.org/)。

本轮 npm audit 返回 3 个 low 包级告警（vue、element-ui、@vitejs/plugin-vue2），没有 moderate/high/critical；这些项关联同一 Vue 告警及依赖传播，不是三个独立漏洞。没有证明当前页面可利用，也没有执行自动依赖修复。完整 Java 依赖和容器镜像扫描仍待进行。
