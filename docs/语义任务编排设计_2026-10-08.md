# 语义任务编排设计与 15:59 对话排查

日期：2026-10-08。适用基线：当前 V1 Demo，`real,mcp`、`agent.semantic.mode=active`，真实模型及带服务认证的 HTTP MCP。本文区分已查明的事实与待实施方案，不把设计或程序测试写成真实业务验收。

## 已查明的问题

会话 `eed03c8593a247faa3be847e3060b7d1` 属于本机 `report_demo` 的 T001 租户。用户先查询销售报表中的服务器记录，再核验其派单资格。结果已唯一定位 A 公司销售单据 SO2026001，金额 128000 元、未派单，满足当时生效的“金额大于 20 元”规则。

| 时间 | 用户原文 | 实际结果 |
| --- | --- | --- |
| 15:57:55 | 查一下销售报表服务器的数据 | 返回服务器这一条记录 |
| 15:58:19 | 这条数据符合派单条件吗 | 返回符合条件和规则依据 |
| 15:58:35 | 帮我派单这条 | 要求用户重新明确可派单范围 |
| 15:58:59 | 我要派单刚刚那条 | 再次要求用户重新明确范围，回复于 15:59:08 |

问题来自查询与派单之间的通用衔接约束：已有的只读边界标记使后续准备清单被直接拒绝；派单解析使用独立上下文，没有直接承接刚才的唯一业务对象。边界本应阻止未确认执行和沿用过时资格，却同时阻断了明确对象的合法后续动作。

上一轮 12/12 真实模型回放只覆盖查询、资格核验和澄清，不包含“核验之后继续派单”。这不能作为整条派单任务完成的证据。

## 目标行为

用户明确要求对已定位记录派单时，系统应自动引用该对象，重新检查权限、当前来源状态和生效规则，然后生成该对象的待确认清单。用户无需重复公司、报表和单据号。确认执行仍依据清单内容、当前执行版本、幂等请求号和用户确认，不由模型代替。

## 通用任务表达

每轮只形成一份完整的任务计划，查询、核验、调整选择、准备清单、取消和查看结果都从同一份计划取得动作及对象。模型负责将不同说法映射到受控能力和有类型的条件，业务服务负责读取、计算及状态变化。

| 计划要素 | 含义与约束 |
| --- | --- |
| 交际意图 | 区分询问、要求操作、禁止、假设和能力咨询；提到派单不自动构成派单要求 |
| 业务动作 | 只使用当前实际提供的查询、核验、预览、选择调整、准备清单、取消和读取结果能力 |
| 目标对象 | 本轮明确对象，或已展示业务记录、候选集合、清单的服务端引用；保存来源与绑定版本 |
| 条件与数量 | 记录报表、公司、字段比较、AND/OR、范围边界、单条或集合、当前页或完整结果 |
| 延续关系 | 声明继承的上下文、当前被替换或撤销的条件，以及新业务对象；不根据“只读”标记清除对象身份 |
| 用户依据 | 保存本轮支持动作、对象和条件的原文；历史消息和来源数据不能冒充新指令 |
| 依赖步骤 | 表达先读取、再核验、再准备等依赖；前置步骤失败时不能执行后续步骤或静默缩小目标集合 |

对象引用与派单资格独立。已查到的 SO2026001 仍然是同一业务对象，但其金额、状态、规则或权限可能变化；准备清单时必须重新读取并明确反馈变化。旧核验结论不授予执行权限。

## 语义理解与业务校验

1. 向规划器提供授权目录、字段含义、业务动作的前置条件、近期真实对话和有来源的对象引用。只提供经过授权和出站脱敏的有限事实。
2. 规划器输出完整的结构化任务，不分别让多个解析器重新猜测同一句话的动作和目标。
3. 在业务变化之前检查计划是否完整表达用户要求。语义复核关注遗漏、否定、指代、数量、假设和复合操作；错误反馈回规划器，在有界预算内修正。复核者不执行操作，不拥有新的业务权限。
4. 程序校验稳定引用、权限、字段类型、完整性、规则、状态、租约、幂等和版本。业务校验结果不能退化为针对某些词语的意图分支。
5. 执行器按已验证计划完成必要步骤。明确的只读动作保持只读；明确的准备清单动作自动完成目标核验。每一步保存真实结果及关联证据。
6. 只有对象不唯一、条件矛盾、权限不足、能力缺失或事实无法可靠取得时才请求补充信息，并说明具体缺项。

字段值识别依赖实际目录、授权来源事实及模型语义判断。若用户省略字段名称，需要在计划中保留其业务限定；无法确定时澄清，不静默返回整张报表。语义复核仍可能出错，因此执行权限和数据正确性必须独立由程序保护。

## 关键业务规则

| 场景 | 正确行为 |
| --- | --- |
| 唯一查询结果后要求派单 | 自动绑定唯一对象，重新核验后生成该条待确认清单 |
| 资格核验成功后要求派单 | 继续引用同一对象，重新核验当前事实和规则 |
| 多条结果中的含糊单条指代 | 询问具体记录，不猜第一条、不扩大成全部记录 |
| 通过编号、序号、唯一产品或费用类别指代 | 从已展示事实确定稳定对象，再应用当前动作 |
| 对已明确集合要求全部派单 | 完整绑定目标集合；不能把一页当作全部查询结果，也不能静默忽略不符合条件的对象 |
| 只要求查看是否可派单 | 返回资格结论和依据 |
| 先查询、以后可能派单 | 完成当前查询；未来目的不构成本轮准备清单要求 |
| 明确不派单，同时要求查询或核验 | 完成允许的只读步骤，保持本轮禁止约束 |
| 旧候选之后查询了另一张报表 | 后续目标按本轮指代与来源引用解析，不默认套用旧候选 |
| 明确返回之前的候选或清单 | 根据该对象的引用及当前有效性继续处理，不要求重新说出所有业务标识 |
| 来源已派单、金额变化或规则变化 | 返回真实变化和必要恢复步骤，原资格结论不充当当前执行依据 |
| 用户要求绕过确认 | 按当前业务规则保留确认环节，不把自然语言承诺当成确认接口调用 |
| 请求超出实际能力 | 明确缺少的能力；不丢弃该部分后宣称任务完成 |

## 评测与验收

验收单位是完整任务链及最终业务状态。应分别记录以下证据，不把其中一种替代另一种：

- 程序回归：引用绑定、类型、权限、集合完整性、确认、幂等、租约和执行版本。
- 真实模型语义回放：未见过的改写、口语、省略、指代、否定、条件句、数量、条件追加与撤销。
- 真实 HTTP MCP 任务回放：从查询或核验继续生成准确的待确认清单，核对记录集合、规则与状态。
- 浏览器验收：卡片、确认交互、刷新恢复、切换会话和重复操作。

| 任务链类别 | 最小验收点 |
| --- | --- |
| 查询 → 核验 → 准备清单 | 全程保持同一记录；清单恰好包含目标记录 |
| 查询 → 直接要求派单 | 自动完成必要核验，不要求用户机械复述范围 |
| 候选查询 → 排除 → 恢复 → 准备清单 | 集合操作和最终清单完全一致 |
| 查询集合 → 唯一属性或序号指代 → 操作 | 指代绑定准确，分页顺序和范围不混淆 |
| 查询 → 否定/假设/能力咨询 | 不产生未经要求的清单或执行 |
| 中途失败 → 澄清 → 恢复 | 保留可靠对象信息；不会通过省略操作使用错误范围 |
| 只读与派单话题切换 | 依据真实目标引用恢复相应对象，不依赖关键词重置焦点 |
| 数据、规则或权限变化 → 再请求操作 | 在当前状态下复核并给出准确结果 |

泛化集应在实现前固定预期，并与开发用语料分开。失败应保留，不能通过删改问法提高通过率。有限评测不能保证任意自然语言都正确；目标是在已声明业务能力范围内泛化表达，对无法可靠完成的任务说明具体原因。

```sql
SELECT id, role, content, card_type, created_at
FROM report_demo.agent_message
WHERE tenant_id = 'T001'
  AND conversation_id = 'eed03c8593a247faa3be847e3060b7d1'
ORDER BY id;

SELECT utterance, outcome, reason, model, latency_ms, created_at
FROM report_demo.semantic_turn
WHERE tenant_id = 'T001'
  AND conversation_id = 'eed03c8593a247faa3be847e3060b7d1'

SELECT version,
       JSON_EXTRACT(state_json, '$.businessQuery') AS business_query,
       JSON_EXTRACT(state_json, '$.businessReferences') AS displayed_objects,
       JSON_EXTRACT(state_json, '$.businessQueryAfterPreview') AS read_boundary,

WHERE tenant_id = 'T001'
  AND conversation_id = 'eed03c8593a247faa3be847e3060b7d1';
```

本轮设计不要求改变数据库名称、清空数据或升级依赖。真实外部认证、ERP 接入与生产容量、灾备仍须独立完成并依据真实证据验收。后续若实施产生破坏性结构变化，需要先明确 `report_demo` 重建影响并取得针对该数据操作的授权。
