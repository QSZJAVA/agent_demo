## K1：整批复核结果在后续发送时已经过时

位置：`backend/src/main/java/com/example/report/dispatch/DispatchService.java:455、470–475`；重试也存在同类结构（198、206 行）。最终演示回写：`backend/src/main/java/com/example/report/catalog/query/StandardReportAdapter.java:155–172`。

触发条件与行为：

1. 清单包含 SO1、SO2，两条记录起初均属于 A 公司，用户只能访问 A。
2. `qualifiedKeys` 一次性复核清单，得到两条记录的 key，然后完成版本检查。
3. 发送 SO1 时，业务系统将 SO2 转移到 B 公司；SO2 仍为待派单。也可以是金额等规则字段变更，使其不再满足规则。
4. 发送 SO2 时仅检查清单执行权和旧 `qualified` 集合，未重新读取业务记录。业务表变更不会改变目录/规则/用户权限版本。
5. `MockDispatchGateway` 最终调用 `markDispatched`，UPDATE 的条件只有记录 ID、待派单状态和租户，没有公司范围、业务版本或规则字段条件。因此同租户内转移公司的记录仍可以被回写。

影响：用户在确认后可能派出已经不在其公司权限范围的记录，或已经不符合规则的记录；整批逐条发送耗时越长，后面的记录暴露窗口越大。清单 CAS、会话锁和请求号幂等控制的是清单执行，不会锁住业务系统对源记录的修改。此处没有证明跨租户派单，租户谓词仍保留。

验证：独立 `DispatchReviewKProbe` 使用真实 PreviewService、PlanService、DispatchService 和现有内存测试仓储；在发送第一条的回调中，将第二条当前数据改为 B 公司，最终仍观察到两条网关调用、成功计数为 2，且只复核一次。另调用真实 StandardReportAdapter，捕获其 UPDATE，确认 WHERE 没有公司谓词。网关和 JDBC 为替身，**没有在真实 MySQL 上实施越权回写**；完整实库交错仍需补验。

修复要求：在产生副作用的最后边界，原子验证源记录的当前公司/待派单状态及用于规则判定的数据版本。可采用业务记录版本条件更新或在同一事务中锁定、复核和回写；接入外部网关时需把等价约束纳入网关协议。仅在循环内再 SELECT 一次只能缩小窗口，仍不能保证检查与执行之间不被修改。补“发送第一条期间第二条改公司/规则字段”的确认与失败重试回归。

## K2：试算的 20 条展示上限没有限制后端资源

位置：`backend/src/main/java/com/example/report/rule/DispatchCandidateService.java:142–155`；`backend/src/main/java/com/example/report/catalog/query/StandardReportAdapter.java:72–73`；`backend/src/main/java/com/example/report/rule/RuleService.java:92–97`。

`POST /api/rules/dry-run` 经过管理员鉴权后，直接调用 `RuleService.dryRun` → `DispatchCandidateService.dryRun`。该链路没有 ResourceQuotaService 配额。它调用 `pendingRows` 全量加载公司范围内待派单记录，随后为全部命中行创建 Candidate 并保存在 `hits`，最后返回时才 `limit(20)`。标准适配器把此调用转为 `Integer.MAX_VALUE`，生成的 SELECT 没有 LIMIT。

影响：正常管理员在百万行报表上试算规则就可能产生大量事实 Map 和 Candidate，占用堆、数据库连接和请求线程；多次并行试算会放大影响。不是普通用户越权，也不依赖恶意规则。已配置的单条 JDBC 查询 60 秒超时不能限制短时间返回的大结果集内存，以及随后的 Java 求值时间。前端展示样例上限不能替代后端扫描/内存限制。

验证：独立探针给真实 DispatchCandidateService/RuleEngine 输入 10,001 条符合规则的事实，确认调用全量 pendingRows，并实际执行 10,001 次求值，最终仅返回 20 个样例；另捕获真实标准适配器查询，确认没有 LIMIT。全量 `hits` 与入口缺少配额由代码路径确认。**本轮没有执行百万行压测，也未制造 OOM。**

修复要求：以批次/游标扫描，命中数用计数器累计，只保存前 20 个样例；按用户、租户、报表限制频率与并发。大范围精确试算走有总截止时间和取消能力的异步任务；若改用抽样，必须明确告知结果是抽样，不能继续标作全量统计。

## 修复记录（2026-09-28）

### K1：派单最终边界原子复核

- DispatchGateway 请求新增 `enforceRules`，确认和失败重试的 Agent 路径均为 true，手工派单为 false；网关契约明确要求在副作用边界原子检查公司范围、待派单状态和规则条件。
- MockDispatchGateway 改走 `markDispatchedGuarded`。StandardReportAdapter 在现有网关事务内，按租户、记录 ID、原公司和待派单状态 SELECT FOR UPDATE，取得当前事实后检查规则 ID/版本及表达式，再回写状态。源行锁保留到事务提交，避免检查与回写之间被其他事务修改。
- 手工派单继续不套用自动规则，但不能跳过公司及待派单校验。未知/失败结果仍通过原有请求号、清单和核对流程恢复。
- 没有活动数据库事务时拒绝原子写入；自定义写入适配器若未实现原子校验接口，不会退回不受保护的旧写入接口。真实外部网关接入时必须实现等价原子约束，不能依靠远程调用前的本地 SELECT。
- 新增 AtomicDispatchGuardTest：复核后改公司、复核后改金额、失败重试到恢复、手工派单范围、规则版本变化、无事务禁止写入。

### K2：试算有界扫描与配额

- RuleService 强制注入 ResourceQuotaService，试算在查询前取得 `rule-dry-run` 用户/租户/报表配额，成功与异常均释放 permit，拒绝时不开始扫描。
- 标准适配器按主键游标每批最多 500 条读取，不按试算表达式预过滤，保留总条数和错误数语义。命中项只保留前 20 个样例，其余只计数，返回 JSON 字段保持不变。
- 同步试算最多扫描 10,000 条。第 10,001 条触发 422，提示缩小范围，不返回被截断的“全量统计”；恰好 10,000 条仍成功。此修复未新增大范围异步试算产品功能。
- 批次及每行求值间检查线程中断和 120 秒截止时间；单条 JDBC 查询继续使用已有 60 秒超时。截止检查是协作式的，不能中断正在执行的单次 Java 表达式，不应描述成硬实时 120 秒返回保证。
- 自定义适配器必须实现专用有界试算扫描，不实现就明确报错，不回退全量 pendingRows。
- 新增 BoundedDryRunTest：跨页精确统计、20 样例上限、10,000/10,001 边界、空结果、中断、未支持适配器、配额拒绝不查询和异常释放。
