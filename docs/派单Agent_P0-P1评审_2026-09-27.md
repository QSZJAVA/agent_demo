## 1. 问题清单

### R1 / P1：无会话 REST 预览可以认领两份执行清单

- 位置：`backend/src/main/java/com/example/report/dispatch/PlanService.java:123-147、217-234`；`dispatch/store/MybatisPreviewRepository.java:35-38`；Flyway V5 的 `pending_guard`。
- 触发：通过允许省略 `conversationId` 的 REST 接口创建预览，使用不同幂等键或省略幂等键，连续创建两份清单，再并发确认。
- 原因：会话为空时不加锁、不作废旧清单；唯一索引的生成列也为 NULL。认领执行只检查当前清单和预览，没有检查同一预览是否已经存在另一份 EXECUTING 清单。
- 复现：同一预览创建两份清单后，两次 `claimForExecution` 均返回 true，且未消费预览。测试使用真实服务和仓库测试替身，并核对了 MySQL 仓库和索引实现。
- 影响：同一批记录可能以不同 `planId-itemId` 请求号进入网关，按请求号幂等无法去重。当前 Mock 网关的待派单状态条件更新可挡住重复业务回写，但不能据此认定真实外部网关安全。
- 建议：所有入口统一使用服务端会话或操作范围；同一预览的创建、认领采用预览行锁和执行占用状态，不能只依赖可空的会话锁。
- 对应：P0-07、P1-04、P1-05。

### R2 / P1：撤销报表或公司权限后仍能读取旧快照数据

- 位置：`backend/src/main/java/com/example/report/dispatch/PreviewService.java:201-208`；`PlanService.java:159-168`。
- 触发：用户生成预览/清单后被收回公司或报表权限，仍以相同租户和用户身份访问 `/previews/{id}/items`、`/plans/{id}/items`。
- 原因：分页接口只调用 `findOwned` 校验租户、用户，不校验当前数据权限。预览汇总的 `getOwned` 即使标记为 EXPIRED，也继续返回明细；会话历史消息同样直接反序列化已有卡片。
- 复现：用同一 tenant/user、空公司和空报表权限的 `CurrentUser` 读取，预览和清单仍各返回原记录。
- 影响：执行权限有拦截，但查询权限边界未闭合。Demo 用户权限静态不变掩盖了该问题，接入可变权限服务后会直接暴露。
- 建议：为快照、清单、会话卡片及追溯建立一致的当前读取权限策略；撤权后拒绝或按当前可见范围裁剪数据。若历史访问有独立授权，应显式建模，不能默认“本人创建即永久可读”。
- 对应：P0-08。

### R3 / P1：旧慢查询完成后会覆盖用户后发起的范围纠正

- 位置：`backend/src/main/java/com/example/report/dispatch/PreviewService.java:127-141、406-420`；`PreviewJobService.java:44-70`。
- 触发：同一会话从两个标签页或客户端发起查询 A（销售，慢）和后续查询 B（费用，快）。B 先完成，A 后完成。
- 原因：激活只判断任务自身仍为 RUNNING，并把当前 ACTIVE 快照全部作废；没有会话请求版本，也不校验当前任务是否已被后续请求替代。会话锁只保证写入串行，不保证请求语义顺序。
- 复现：用 latch 阻塞 A 的候选查询，先完成 B，再释放 A；最终 A 成为最新 ACTIVE，B 变为 SUPERSEDED。
- 影响：用户已纠正为费用范围，稍后系统却切回销售；后续“剩下的派单”可能针对错误范围。SSE 请求序号只解决单条流，无法解决多个后台任务的完成顺序。
- 建议：提交任务时递增会话预览版本，激活时 CAS 校验仍是最新请求；旧任务完成后应为 SUPERSEDED/CANCELLED，不能作废新结果。
- 对应：P0-07、P1-02、P1-04、P1-06。

### R4 / P1：确认和失败重试仍把整个报表范围的候选加载进内存

- 位置：`backend/src/main/java/com/example/report/dispatch/DispatchService.java:178-179、374-375`；`rule/DispatchCandidateService.java:38-60`。
- 触发：预览通过摘要排除等方式仅保留少量记录，但报表/公司范围内有大量规则命中记录；或生成预览后大量记录变为可派单。
- 原因：执行前调用无上限的 `findCandidates`，其上限为 `Integer.MAX_VALUE`，先构造完整 Candidate 列表，再转换为 key 集合。扫描虽然每批 500 条，最终结果仍全量驻留内存；也未限定到清单 recordId。
- 影响：一个很小的确认清单也可能扫描、收集百万级候选。预览分页和 5000 条清单上限不能保护这一条执行路径，可能长时间占用线程并造成内存压力。
- 建议：按清单里的报表、主键分批读取当前记录，仅对这些记录校验租户、公司、状态及规则；避免重新求出整个报表的可派单集合。
- 验证方式：调用链静态确认，未进行百万级内存压测。
- 对应：P1-01 的整体容量目标、P1-03、P1-09。

### R5 / P1：确认、失败重试和核对接口没有接入资源配额

- 位置：`backend/src/main/java/com/example/report/dispatch/DispatchService.java:89、156、251、327`；`web/DispatchController.java:190-206`。
- 原因：`DispatchService` 中只有手工 `/direct` 调用了 `quotas.acquire`；计划确认、重试、核对没有相同保护。预览阶段获取的 permit 已在预览结束时释放。
- 触发：用户提前准备多个会话的清单，同时请求确认，或反复请求待核对清单；即使重复确认同一已执行计划，也会读取其全部条目进行重放。
- 影响：同计划 CAS 只防止该计划重复执行，不能限制用户跨计划并发，也不能限制对网关查询和数据库的请求频率。与 P1-09 的用户、租户资源保护承诺不一致。
- 建议：确认、重试和核对统一经过服务层配额，覆盖频率、用户/租户并发以及涉及报表；确保异常路径释放租约。
- 验证方式：调用链静态确认，未进行并发压测。
- 对应：P1-09。

### R6 / P2：UNKNOWN 核对成最终结果后缺少审计事件

- 位置：`backend/src/main/java/com/example/report/dispatch/DispatchService.java:251-289`。
- 触发：首次网关结果 UNKNOWN，之后 `reconcile` 查询到 SUCCESS、FAILED 或 NOT_FOUND。
- 原因：核对更新 plan_item、plan 和会话结果卡片，但没有调用审计服务记录最终结果和核对动作。
- 复现：首次确认返回 UNKNOWN，清空审计 mock 调用记录，再核对为 SUCCESS；结果成功数为 1，但审计服务没有任何新调用。
- 影响：审计中的结果仍可能为 UNKNOWN，条目已为 SUCCESS；仅依赖审计统计会得到错误结果，也无法从操作审计完整还原是谁何时进行了核对。条目中的最终状态仍然存在，不是所有结果数据都丢失。
- 建议：在条目 CAS 核对成功后，记录带请求号、执行版本、旧/新状态、核对用户和时间的幂等审计事件，必要时使用事务性 outbox。
- 对应：P0-09、P1-05。

### R7 / P2：超过 50 条的失败原因无法在界面完整回看

- 位置：`frontend/src/components/agent/ResultCard.vue:25-26`；`PlanCard.vue:17-28`。
- 触发：一个清单有超过 50 条失败记录。
- 原因：结果卡片只保留前 50 条失败项，提示用户去清单卡片分页查看；清单表格只显示 `status`，没有展示 API 已返回的 `errorCode/errorMessage`，也没有错误详情入口。
- 影响：第 51 条之后只能看到 FAILED/SKIPPED 等状态，用户不能在界面获知具体失败原因，难以决定重试还是处理业务数据。
- 建议：清单分页补充失败原因列或详情弹层，并在重试/核对后刷新当前页。
- 验证方式：载荷截断及模板静态确认，未运行浏览器端到端测试。
- 对应：P1-05、P1-07。
